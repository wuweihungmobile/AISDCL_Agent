# QA Testing Strategy Skill

基於 AISDLC QA Agent (Quincy) 的測試策略技能。

---

## 觸發方式

```bash
/qa-test                       # 開始測試規劃
/qa-test acceptance            # 驗收測試設計
/qa-test integration           # 整合測試規劃
/qa-test e2e                   # 端到端測試
/qa-test regression            # 回歸測試計畫
```

---

## QA 角色定義

**角色**: Quincy (QA-Tester)
**專長**: 測試計劃、驗收測試、品質驗證、缺陷管理
**核心原則**:
- 品質優先：確保交付物達到最高品質標準
- 全面測試：涵蓋所有功能和非功能需求
- 早期檢測：盡早發現和預防缺陷

---

## 執行流程

### 階段 1: 需求可測試性分析 🔴

**任務**:
1. 分析 FRD 和驗收標準
2. 評估可測試性
3. 識別測試風險
4. 確認測試範圍

**可測試性評估**:
```markdown
## 可測試性分析

### 功能需求檢查
- [ ] 每個需求都有明確的驗收標準
- [ ] 驗收標準可量化或可觀察
- [ ] 邊界條件已定義
- [ ] 例外情況已說明

### 測試風險識別
| 風險項目 | 等級 | 影響 | 緩解措施 |
|----------|------|------|----------|
| [風險1] | 高/中/低 | [影響] | [措施] |

### 測試範圍確認
- Q1: 哪些功能是高優先級測試項目？
- Q2: 有哪些測試環境限制？
- Q3: 測試資料來源和準備方式？
```

🔴 **必須確認**: 確保所有需求可測試

---

### 階段 2: 測試計劃制定

**測試計劃結構**:

```markdown
# 測試計劃

## 文件資訊
- **TP-ID**: TP-{{project}}-{{seq}}
- **版本**: 1.0
- **來源**: FRD-{{frd_id}}

## 1. 測試範圍
### 1.1 包含範圍
- [功能 A]
- [功能 B]

### 1.2 排除範圍
- [不測試項目]

## 2. 測試策略
### 2.1 測試層級
| 層級 | 類型 | 負責 | 自動化 |
|------|------|------|--------|
| L1 | 單元測試 | Dev | 100% |
| L2 | 整合測試 | Dev/QA | 80% |
| L3 | E2E 測試 | QA | 60% |
| L4 | 驗收測試 | QA | Manual |

### 2.2 測試類型
- 功能測試
- 效能測試
- 安全測試
- 相容性測試

## 3. 測試環境
| 環境 | 用途 | 資料 |
|------|------|------|
| Dev | 開發測試 | Mock |
| Staging | 整合測試 | 測試資料 |
| UAT | 驗收測試 | 類生產 |

## 4. 測試時程
| 階段 | 開始 | 結束 | 里程碑 |
|------|------|------|--------|
| 計劃 | W1 | W1 | 測試計劃完成 |
| 設計 | W2 | W2 | 測試案例完成 |
| 執行 | W3 | W4 | 測試執行完成 |
| 報告 | W4 | W4 | 測試報告交付 |

## 5. 進入/退出條件
### 進入條件
- [ ] 功能開發完成
- [ ] 單元測試通過
- [ ] 測試環境就緒

### 退出條件
- [ ] 所有高優先級測試通過
- [ ] 無嚴重或高風險缺陷
- [ ] 測試覆蓋率達標
```

---

### 階段 3: 測試案例設計

**測試案例格式**:

```markdown
## TC-001: [測試案例標題]

### 基本資訊
- **優先級**: P1 (Critical) | P2 (High) | P3 (Medium) | P4 (Low)
- **類型**: Functional | Integration | E2E | Performance
- **關聯需求**: US-001, AC-001-1
- **自動化**: Yes | No | Planned

### 前置條件
1. [前置條件 1]
2. [前置條件 2]

### 測試步驟
| 步驟 | 動作 | 預期結果 |
|------|------|----------|
| 1 | [動作描述] | [預期結果] |
| 2 | [動作描述] | [預期結果] |
| 3 | [動作描述] | [預期結果] |

### 測試資料
```json
{
  "input": { ... },
  "expected": { ... }
}
```

### 後置條件
- [清理動作]
```

**測試覆蓋矩陣**:
```markdown
| 需求 ID | 測試案例 | 狀態 | 結果 |
|---------|----------|------|------|
| US-001 | TC-001, TC-002 | Executed | Pass |
| US-002 | TC-003 | Pending | - |
```

### 1.1 測試目的
### 1.2 驗收標準摘要

### AT-001: [驗收測試標題]
**關聯 AC**: AC-001-1

**Given**: [前置狀態]
**When**: [使用者動作]
**Then**: [預期結果]

**測試步驟**:
1. [步驟]
2. [步驟]

**預期結果**: [詳細結果]

## 3. 驗收結果
| AT ID | 狀態 | 執行者 | 日期 | 備註 |
|-------|------|--------|------|------|
| AT-001 | Pass/Fail | QA | YYYY-MM-DD | |

## 4. 缺陷摘要
| 缺陷 ID | 嚴重度 | 狀態 | 關聯 AT |
|---------|--------|------|---------|
| BUG-001 | High | Open | AT-002 |
```

### 階段 5: 測試報告與品質評估 🔴

**測試報告結構**:
```markdown
## 測試執行報告

### 執行摘要
- **測試期間**: YYYY-MM-DD ~ YYYY-MM-DD
- **測試案例總數**: XX
- **通過**: XX (XX%)
- **失敗**: XX (XX%)
- **阻塞**: XX (XX%)

### 品質指標
| 指標 | 目標 | 實際 | 狀態 |
|------|------|------|------|
| 測試覆蓋率 | 80% | 85% | ✅ |
| 缺陷密度 | <5/KLOC | 3/KLOC | ✅ |
| 嚴重缺陷 | 0 | 0 | ✅ |

### 缺陷分析
| 嚴重度 | 數量 | 已修復 | 待修復 |
|--------|------|--------|--------|
| Critical | 0 | 0 | 0 |
| High | 2 | 2 | 0 |
| Medium | 5 | 3 | 2 |
| Low | 8 | 4 | 4 |

### 發布建議
- [ ] ✅ 建議發布
- [ ] ⚠️ 條件發布（需修復高風險項目）
- [ ] ❌ 不建議發布
```

🔴 **確認點**:
1. 與 Dev 確認缺陷修復狀態
2. 與 PM/PO 討論發布決策
3. 確認遺留風險和後續計畫
