## §2 途中發現（本輪親踩或現查推翻，逐點附機制）

### 1. 否定宣稱鎖只判**最新**一份交棒書 ⇒ 施工順序被判準決定

`tools/tests/test_negative_existence_claims_r82.py` 的
`test_no_negative_claim_is_contradicted_by_the_disk` 只對 `newest_handoff()` 那一份生效；
舊交棒書只受「未帶標記數只准縮小」的存量棘輪管。

**這件事決定了本輪的施工順序**：上一份交棒書〈還沒做〉節有三筆 `absent-if` 錨，本輪的落地
動作（R121 檔頭落款、`DEF-200-264` 接線、側軌複查日）正好會讓它們的字面出現在磁碟上。
若在寫出本輪交棒書**之前**跑那支鎖，它會判上一份交棒書的宣稱為假——而那些宣稱在當時是真的，
只是被本輪兌現了。⇒ 正解是「先落地、最後寫交棒書、然後才跑全套」，這也正好與循環令
「帳本主檔編修後、最後一次全套之前，不再寫任何文件」同向。

### 2. 上一份交棒書有一個錨的**字面選得不會命中**（錨與宣稱不同軸）

上一份交棒書為「R121 呈報單檔頭仍是 Proposed」這筆否定宣稱登記的證偽標的，是一段把檔名
輪號夾在狀態字後面的字面。但 R121 檔頭真正落款時不會自稱自己的輪號（本輪實際寫的是
落款日期），⇒ 那個錨無論落款與否都不會命中。

**這與上一輪記載的「裁決卡引用的座標也要現查」是同一族**：錨、座標、指針三者都是
「寫下時看起來對、之後沒人回頭驗」的東西。本輪不去把 R121 檔頭改成能命中那個錨的寫法——
那是為了讓鎖開心而扭曲內容，方向錯了。

### 3. `lint_powershell_command.py` 當場擋下「rc 讀取接管線」

本輪有一次把「跑閘門 → 管線篩輸出 → 讀 `$LASTEXITCODE`」寫在同一次呼叫裡，PreToolUse 守衛
當場擋下並逐字指出 pwsh 7.x 提前中斷管線時不更新 `$LASTEXITCODE`。改成「先落檔、rc 自成
一句、篩輸出分第二次呼叫」後通過。**這是守衛在正確的時點抓到正確的形態**，記在此作為
該守衛有鑑別力的實證。

### 4. 三列帳本餘裕極小，落款前必須先量**整列** bytes

本輪要動的三列現值：`DEF-101-736` 635／`DEF-101-856` 631／`DEF-200-182` 654（上限 700）。
餘裕分別只剩 65／69／46 bytes。⇒ 落款文字必須先算再寫：`736` 用「移除一個子項 ID ＋ 塞一個
短括號」淨增約 42 bytes 過關；`182` 因為連短落款都塞不進，改走 R124 瘦身體例（現象欄長文
搬進證據檔逐字保全）。

**700 bytes 是整列，不是狀態欄**——狀態欄能寫多少，取決於前面幾欄先吃掉多少。

### 5. `current_round()` 不是零參數函式

`check_defect_log_crossref.current_round` 需要 `ledger_text` 參數。第一次以零參數呼叫得到
`TypeError`。現查值＝**100**（時鐘刻意凍在此，因「發現情境」欄零輪號解析不出新輪號）。
狀態欄寫 `fixed@R128`／`wontfix@R128` 安全：吃 `current_round()` 的判準是
「未結列的**承接輪次**」與 `check_script_parity` 的**腳本錨點**，都不是結案落款字面。

### 6. `_LEGACY_UNMARKED_CEILING` 現值零餘裕且雙邊帶

`--print-baseline` 印出的舊交棒書未帶標記總數正好等於棘輪值 14，而該測試在
「總數 < 棘輪值」時**也會 fail**（要求同步下修）。⇒ 舊交棒書這一面現在動不了：加一筆無錨
否定宣稱會撞上限，而讓總數變小又必須同時改常數。本輪的新交棒書逐筆帶錨，不動這個面。

### 7. 一筆已落款裁決的理由被本輪推翻（連帶影響它的整份呈報單檔頭）

`DEF-200-182` ② 的 `closed-by-decision` 理由建立在「那次 push 繞過了 pre-push」之上，而本輪

**這改變了本輪對呈報單第①項的落款寫法**：落款當回合先寫了「本檔的推薦從未被逐筆覆核為錯」，
隨後查出這一筆，於是把那句話刪掉並改成明文劃界——「一份文件的推薦被整體採用，不等於其中
每條理由都經過覆核」。**落款範圍不含已被推翻的那條理由**，且該筆就地加了訂正註記。

### 8. 🔴 兩道交棒書鎖的要求**方向相反**，本輪親踩（規避一道就違反另一道）

本輪寫交棒書時，為了讓〈還沒做〉節少一些需要 `absent-if` 錨的否定宣稱，把每筆的措辭都從

| 鎖 | 要求 | 我的規避造成什麼 |
|---|---|---|
| `test_negative_existence_claims_r82.py` | 否定宣稱必須帶機讀的證偽錨 | 規避成功（宣稱變少） |

第二道鎖的 docstring 逐字寫明它就是為了防這個形態（「用散文寫變成一個免費的逃逸口，而且是

**正解是三者並存**，不是二選一：觸發字（讓宣稱進得了分母）＋現查指令 code span（讓它可查）

**兩個附帶事實**（都是實測，寫下來省下一次重踩）：

- 現查指令的 code span 必須**帶動詞**才算數，判準認的動詞是一份白名單

  `docker exec …` **不在**白名單 ⇒ 一筆只有 docker 指令的宣稱若帶了觸發字，會被判「無現查指令」。
  本輪第 3 筆因此刻意維持肯定敘述。

  的立案形態**——寫交棒書時要同時想兩道，不能逐道各過一次。

### 11. `Set-Content` 在 Windows 預設寫 CRLF，把行尾漂移帶進 `eol=lf` 的檔

本輪用一次 `(Get-Content $t) -replace … | Set-Content $t -Encoding utf8` 重編節號，事後
`git ls-files --eol` 現查發現該檔變成 `w/crlf`（`.gitattributes` 宣告 `attr/text eol=lf`）。
`-Encoding utf8` 只管**編碼**，不管**行尾**；PowerShell 的 `Set-Content` 在 Windows 預設
以 CRLF 寫出，於是一次「純文字替換」就製造了行尾漂移。

**為什麼這件事在 `git status` 上看不見**：git 的行尾正規化只作用於 index，`git status` 兩側
套同一份規則 ⇒ 工作樹漂移結構上不可見（本 repo R78 已記載同一機制）。唯一看得到的是
`git ls-files --eol` 的 `w/` 欄，或本地那道「活躍面止血」判準。

**本輪處置**：兩支檔（一支 `.md`、一支 `.py`）以 Python 讀 bytes、`replace(b"\r\n", b"\n")`
寫回，`git ls-files --eol` 覆核兩支皆回到 `w/lf`，並重跑針對測試確認 rc=0。

**紀律**：文字替換一律走 `Edit` 工具或 Python（`newline="\n"`）；要用 PowerShell 就得顯式
處理行尾。**改完務必用 `git ls-files --eol` 現查**——這是唯一看得見工作樹行尾的取數管道。

### 13. 🔴 背景任務的 `completed` 通知**先於行程真正結束**抵達（本輪實測，直接命中鐵律六）

本輪最後一次全套用 `run_in_background` 跑，harness 送來 `status: completed, exit code 0`。
**當下 log 只有 12,467 字元、且不含 `Ran`／`OK`／`FAILED`／`full_rc` 任何一個字面**——也就是
連測試摘要都還沒寫出來。當回合現查 `Get-Process python` 發現該行程仍在、CPU 從 252.4s → 258.2s
→ 269.4s **持續增加** ⇒ 行程還在跑，通知講的不是它。

改掛一個以**精確 PID** 為條件的 until-loop（`while (Get-Process -Id <pid>) { Start-Sleep 10 }`，
背景執行）等它真的退出，log 才長到 55,519 字元並出現末尾判決
`Ran 3932 tests in 802.800s`／`OK (skipped=42)`／`full_rc=0`。

**為什麼這件事重要**：如果照那個 `completed` 通知就去讀 log 尾端，讀到的是**半套輸出**——
而半套輸出裡沒有 `FAILED` 字樣，看起來與「跑完且全綠」**難以分辨**。這正是鐵律六
「等待／確認機制自己靜默壞掉 ⇒ 無做工空轉」的具體實例，只是方向相反：不是永不退出，
是**過早宣告完成**。

**紀律（本輪起）**：全套這種長任務，`completed` 通知只是「該去看一眼」的提示，**不是憑證**。
憑證是 log 尾端真的出現 `Ran N tests` ＋ `OK`／`FAILED` ＋ `full_rc=`。三者缺一就當它還在跑，
改用 PID 條件的 until-loop 等它。🔴 用 PID 而不是 `pgrep -f <字面>`：後者在兩支並行時會兄弟
互匹而永不退出（本 repo 既有判例）。

**附帶**：本輪也因此多學到一件事——`TaskStop` 停掉的是 PowerShell 包裝行程，不保證一起帶走

## §3 `DEF-200-265`（本輪新立）：隨機重生的 fixture 被 tracked

**怎麼發現的（含一筆歸因訂正）**：跑完 ONBOARDING 表② 回填後 `git status --short` 多出兩個
本輪沒碰過的檔。**當時寫下的因果歸因是錯的**——訂正見本節末〈歸因訂正〉。

| 檔 | 實測 diff | 判讀 |
|---|---|---|
| `AutoClaude/.perf_baseline.toml` | 20 行變動；`git_sha` 指向上一輪 commit、`captured_at` 更新、四個 p50／p95 值變動 | **量測值的自然重播種**，歷輪皆隨全套一起 commit。本輪照舊入庫 |
| `AutoClaude/tests/fixtures/pgvector_real_ground_truth.json` | 單檔 `git diff --numstat` 實測 **1000 插入／1000 刪除**（整檔 2000 行全改），內容是 `q0` 起的隨機 UUID 陣列 | **缺陷**，立列 `DEF-200-265` |

**兩層危害**：

1. **噪音蓋掉訊號**：每跑一次全套就固定產生 2000 行 diff。任何一輪只要跑過全套，這一檔的
   變動就會淹沒同一個 commit 裡真正的改動 ⇒ 「這輪改了什麼」在 `git diff --stat` 上不可讀。
2. **判準基準的意義可疑**：一份名為 ground truth 的檔，若內容每次 seed 都重新隨機生成，它就
   不是任何東西的「真值」——recall@10 拿它當基準比對，量到的是「這次 seed 出來的東西跟這次
   seed 出來的東西一致」。**這與 `DEF-101-856` 的 mock 語料是同一軸**：兩者都是「測試的輸入面
   不是真實資料」，只是一個在容器裡（100 列 mock 向量）、一個在 repo 裡（隨機 UUID）。

**二擇一的處置（未落地，本輪只立列）**：

- (a) 改為衍生產物不入庫（`.gitignore` ＋ 在測試 setup 或 ONBOARDING 補上生成步驟）——噪音
  歸零，但要確認沒有任何消費者依賴它「在 repo 裡就存在」。
- (b) 改為固定種子讓內容可重現——檔留在庫裡但跑全套不再改它，且 ground truth 這個名字才站得住。

🔴 **不要用「把它加進某個豁免清單」當解**：那讓 diff 噪音變成看不見，而不是不存在。

### §3-a 歸因訂正兩筆（本輪自查與複審鏡各抓到一筆）

**訂正① 寫入者不是 ONBOARDING 回填，是本機 nightly 排程**（勘查鏡誠實揭露「在程式碼裡定位不到
ONBOARDING 那條路徑如何觸發寫入」，據此回頭查 mtime 才查出真凶）：

| 事件 | 實測時刻 |
|---|---|
| `AutoClaude_Nightly` 排程 `LastRunTime` | 22:30:01（`LastTaskResult=1`） |
| `pgvector_real_ground_truth.json` 寫入 | 22:51:52 |
| `.perf_baseline.toml` 寫入 | 22:52:14 |
| `nightly_latest.log` 寫入 | 22:52:59 |
| 本 session 開工（`--pace` 量測時刻） | 22:38:57 |

三個寫入時刻連續且都落在 nightly 啟動之後、而 ONBOARDING 回填是在遠晚於 22:52 才啟動的
⇒ **寫入者是 nightly 排程**。原本寫的「回填跑完全套後多出兩個檔」在**時序**上為真，但把它寫成
**因果**就是錯的：我第一次跑 `git status` 就已經在回填之後，從來沒有「回填之前的乾淨對照」。

**附帶查到、本輪不展開**：`AutoClaude_Nightly` 的 `LastTaskResult=1`，nightly summary 逐字
`local_ci_gate=1`，log 內同一 stage 有多次 PASS 與一次「例外：stage 內部炸掉」，時刻 22:48:17
——**那正好落在本 session 正在改帳本主檔的區間內**。nightly 的 `local_ci_gate` 會跑帳本閘門，
而帳本當時是半套狀態 ⇒ 這個紅**很可能是本 session 造成的假紅**，不是真缺陷。**未證實，不塗綠
也不立列**；真正的結構問題是「排程與人工窗口重疊時沒有互斥機制」。

**訂正② 「1010 插入／1010 刪除」是兩檔合計，不是單檔**（SD 鏡實查抓到，主控親驗確認）：
`git diff --stat` 對**兩個檔**的合計行是 `2 files changed, 1010 insertions(+), 1010 deletions(-)`，
而單檔 `git diff --numstat` 是 `1000 1000`。我引用了合計行卻寫成單檔的數字，且該數字與同一列
自己寫的「整檔 2000 行」自相矛盾（1010+1010=2020≠2000）——**內部矛盾當場就可以自檢出來，
我沒有做那一步**。這與本 repo 記載的「取數管道給假數字」同族：`--stat` 的末行是**聚合**，
要單檔數字就得用 `--numstat` 並指名那一個路徑。
