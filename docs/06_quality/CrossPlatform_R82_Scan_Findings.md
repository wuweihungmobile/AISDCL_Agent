### A.1 三個跨面重複出現的形態（比任何單筆都重要）

1. **鎖在守、但守的是別的東西**（Q4-01／MAC-02／CARRIER-01 皆屬此形）。
   分母崩塌時 rc 與「正確地全部通過」一模一樣，**這是本 repo 第 N 次踩到同一個形狀**。
2. **reason 字串是自我宣稱，不是事實**（skipped 面直接推翻三處）。
   `skip` 的理由寫「需要 X」不蘊含 X 缺席——多半只是環境變數沒設或 extras 沒裝。
3. **「掃出沒問題」與「沒掃」在文件上長得一樣**。mac 面刻意把 NFD 那一格的**零命中**寫進交件，
   就是為了讓 R83 知道那是「量過了、是綠的」而不是「沒人看」。

### C.1 HELM-01（P0）使用者三度回報的模態彈窗，真凶是本 repo 自己的額度哨兵

`[他包回報]`，歸因鏈與實測憑證：

| 環節 | 事實 |
|---|---|
| 發出者 | `tools/lib/quota_escalation.py` 的 `notify()` → Windows `msg.exe * /TIME:600`（**模態**，杵 10 分鐘） |
| 觸發點 | `tools/session_resume_planner.py` 在 `transcript.is_file()` 為 False 時**硬編** `action=escalate` |
| 歸因確定的依據 | 使用者截圖的畫面逐字與該分支的 `reason` 字串**完全一致** |
| 排除的假設 | 逐字稿真的不存在（`Get-ChildItem` 對該 session id 零命中）⇒ **不是**路徑解析／大小寫 bug |
| 殘骸規模 | `%TEMP%\autosdd_resume_plan_*` 實測 **26 份**任務書（含三份測試殘骸） |

🔴 **根因（值得記住的那一句）**：SessionStart **無條件**武裝哨兵，但**開了沒做事就結束的
session 不會產生 `.jsonl`** ⇒ 哨兵 15 分鐘後醒來找不到檔就走 escalate。
**設計把「session 沒留下逐字稿」與「哨兵失明」混為一談，而前者是正常且常見的情形。**
⇒ 一次正常結束換來一個模態彈窗，而且會重複發生。

已三面修（`[他包回報]`）：判定面改 **silent disarm**（寫 log、移除排程、不叫人）／
武裝面收緊前提／載具改非模態。**機械物要求是雙向的**：合成注入「逐字稿不存在」必須驗證
**不會**呼叫 `notify()`；合成注入「有未處理撞線＋有扇出死者」才驗證會叫人。

### C.4 HELM-04（P0）掌舵者當場抓到：額度水位取錯桶

掌舵者原話：「額度 50% ⇒ 這個你抓的額度，應該是抓到 Weekly，是錯的」。**屬實。**
`[他包回報]` 的當回合實測：

```
pct=54.0  kind=weekly_all  resets_at=2026-08-14T21:59:59Z     ← 被當成「額度水位」報出去的那個
buckets=[weekly_all:54, seven_day:54, session:33, five_hour:33, weekly_scoped:0, ...]

伺服器原始 payload（尚未被 worst() 壓扁）：
  limits[0] => {"kind":"session",    "percent":34, "resets_at":"2026-08-09T04:59:59Z"}
  limits[1] => {"kind":"weekly_all", "percent":54, "resets_at":"2026-08-14T21:59:59Z"}
```

時區換算：`04:59:59Z` → 本地 **12:59:59**；量測時刻 12:25 ⇒ **34 分鐘後 reset**。
掌舵者 UI 顯示「Current session, Resets in 37 min, 31% used」⇒ **逐格吻合**。

**缺陷一（P0）：一個數字代表不了兩個時間尺度。**

| 桶 | 現值 | reset | 撞到的後果 |
|---|---|---|---|
| session／five_hour | 34% | **34 分鐘後** | 停約 34 分鐘，等一下就回來 |
| weekly_all | 54% | **5 天後** | 停 5 天 |

`worst()` 取跨桶最大值 ⇒ 永遠回 weekly。於是「還有 34 分鐘就 reset、可以放手跑」被讀成
「54% 了要收斂」——**方向剛好相反，而且錯的方向是「該加速時減速」**。
反向同樣壞：session 衝到 95% 而 weekly 才 60% 時 `worst()` 回 60% ⇒ **該停的時候不停**，
這一向會真的撞線。

**缺陷二（P0，更嚴重）：per-bucket `resets_at` 被丟掉 ⇒ 訴求 6b 的演算法結構上算不出來。**
6b 的輸入是二元組 `(usage%, 距 reset 幾分鐘)`，而正規化後只留**一個** top-level `resets_at`
且是 weekly 那一個；`buckets` 陣列只有 `kind` 與 `pct`。
⇒ 「session 桶還有幾分鐘 reset」這個欄位**伺服器有給、本機收到、正規化時丟掉**。
🔴 **R81 曾宣稱 6b 落地——那個宣稱在這一點上不成立**（結構上算不出來，不是算錯）。

已落地（`[他包回報]`，本包只複驗 rc）：`tools/lib/quota_policy.py` 純函式判讀層
＋ `tools/lib/quota_gate.py` 接線 ＋ meter schema `/2` 吐 `axes[]`（每格帶 `resets_at`／`group`）。
本包當回合複驗：於 `tools/tests/` 跑 `& $p -m unittest test_quota_policy` → **rc=0，Ran 90 tests，OK** `[本包實測]`；
`test_context_budget_guard` → **rc=0，Ran 273 tests，OK** `[本包實測]`。

🔴 **三鏡對抗複驗全 FAIL，抓到 10 筆**（`[他包回報]`），其中最值得記住的一筆：
**多軸下加速訊號被跨軸 `min` 吃掉**——也就是 HELM-04 要治的那個病，在治它的新程式碼裡復發。
收斂後錨點「0% + 30m ⇒ 多派」的建議值由 `{4}` 變成 `{16, 8, 4}`，回到 16。
**這是「同一個病換個地方長回來」的又一個實例**，而它是被對抗式複驗抓到的，不是被閘門抓到的。
