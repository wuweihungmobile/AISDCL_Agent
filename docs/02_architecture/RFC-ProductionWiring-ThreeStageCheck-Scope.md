## 2. 問題陳述

本輪四方複審反覆挖出同一類缺陷形狀：**程式碼「看起來」接上生產路徑，但沒有人／沒有機制驗證過它在真實環境下真的會被觸發、真的會執行、真的會產生預期斷言結果**。已知具體案例：

- DEF-101-064：`tools/tests/**` 的測試從未在真實 Windows/macOS runner 上跑過一次，CI workflow paths 甚至未涵蓋該目錄。
- DEF-101-065：`windows/macos-nightly-alert` 的「紅色路徑」（`gh issue create`/`gh issue comment`）歷史 run 中 0 筆由真實 `schedule` 事件觸發過失敗分支。
- DEF-101-069：`tools/tests/` 首次真實 Windows 執行後，立刻炸出 16 個此前完全無人發現的真實失敗。

`simulate_nightly_failure`（DEF-101-065 的修復手段）是這類問題的一個**具體、局部**解法：對單一 workflow 補一個 `workflow_dispatch` boolean input，讓人可以在不等真實失敗的情況下手動走到紅色分支。QA 在 DEF-101-068(f) 中觀察到：這個手法本質上是「三段式檢核」（觸發 / 執行 / 斷言）的一次具體實踐，值得問「能否制度化成可重用的 meta-lint，而非每次人工複審碰運氣才發現」。

## 3. 為何不能直接動工（本輪已確認的設計未決問題）

三段式檢核要機械化，必須先對以下三個問題有共識答案，否則寫出來的只會是一支綁死本輪已知案例、日後改個 workflow 就要重寫的一次性腳本：

### 3.1 「觸發」怎麼機械判定？
- 一段邏輯宣稱由 `schedule` 事件觸發，如何不必真的等到排程時間到、也能確認它「有能力」被觸發？
- `workflow_dispatch` 手動模擬（如 `simulate_nightly_failure`）與真實 `schedule` 事件是否**等價**？目前已知反例：`docker_available()` 探測（DEF-101-061/062）證明「同一段程式碼在不同真實觸發下行為不穩定」，代表「能手動觸發一次成功」不足以推論「排程觸發也會成功」。
- 判準草案（待下一輪定案，非本文件終局）：至少要能區分「邏輯上可達（reachability，靜態掃描 workflow YAML 的 `on:` 區塊 + 手動模擬 input 是否存在）」與「經驗上已驗證過（用 `gh run list --json event` 核對歷史是否真的有該事件類型的 run）」兩個層級，不可混為一談。

### 3.2 「執行」怎麼機械判定？
- 只看 exit code 不夠——DEF-101-069 的教訓是「測試套件跑起來 exit 0」不代表它真的在目標平台上被完整執行過（此前根本沒接線，是「從未執行」而非「執行後通過」）。
- 需要區分「這段程式碼被排進執行圖」vs「這段程式碼實際執行到底」vs「執行時的環境與正式場景一致（如是否真的在 windows-latest 而非 ubuntu-latest 跑）」。
- stdout/日誌關鍵字比對（如 DEF-76-001 的 marker 教訓，見 MEMORY `ab-carrier-production-blind-marker.md`）是一種可行手段，但需要每個受檢邏輯自行定義 marker，非通用。

### 3.3 「斷言」要斷言什麼？到什麼邊界？
- 副作用類分支（如 `gh issue create`）的斷言，若要求「真的建立一個 GitHub issue」，會在每次 lint 執行時弄髒真實 issue tracker；若要求「mock 到 gh CLI 呼叫層」，又可能與 DEF-101-065 的教訓（連 green path 都從未真實觸發過）背道而馳——mock 掉的東西還是没有被真實驗證過。
- 目前唯一已知、已驗證可行的折衷是 `workflow_dispatch` + boolean 手動覆寫（DEF-101-065 的解法）：讓「斷言」發生在真實 CI 環境、真實呼叫 `gh` CLI，但由人主動選擇時機觸發、不必等待真實故障。這是否可以泛化為所有「等真實失敗才走到的分支」的標準模式，是下一輪需要驗證的假設，而非本文件可以斷言的結論。

## 4. Non-Goals（本文件明確排除）

- 不在本輪／本文件內產出任何可執行的 meta-lint 程式碼。
- 不承諾「三段式檢核」最終會是單一泛用工具；也可能收斂為一份「檢核清單 + 每案例各自手動落地」的治理規範（比照 DEF-101-065 對每個 workflow 個別補 `simulate_nightly_failure`），而非強行寫一支自動化程式去掃描任意 workflow。
- 不處理與本問題無關的既有 defer 項（DEF-101-068 其餘各子項已各自有獨立定案條目，見 DEF-101-070/071/073~076，不在本文件重複討論）。

## 5. 下一輪建議範圍（提案，非本文件拍板實作）

1. **先窄後寬**：下一輪若要動工，範圍限定在「本輪已知三個具體案例」（DEF-101-064／065／069 各自對應的接線）能否用同一份判準描述清楚，而非一開始就設計「任意 workflow 皆適用」的通用工具。
2. **先做靜態可達性掃描，暫緩動態驗證自動化**：§3.1 判準草案中「邏輯上可達」（掃描 `on:` 區塊 + 是否存在手動模擬 input）是靜態、無副作用、可低成本先做的部分；「經驗上已驗證過」（比對 `gh run list` 歷史事件）需要呼叫 GitHub API，屬於下一輪才評估是否值得自動化，或維持人工複審時手動跑指令核對（即本輪 DEF-101-065/069/077 已示範的做法）。
3. **明確排除自動建立真實副作用**：任何 meta-lint 都不應該在一般 CI/pre-commit 執行時真的觸發 `gh issue create` 等具真實副作用的呼叫；斷言層仍以 `workflow_dispatch` 手動模擬為主要驗證手段。
4. 下一輪動工前，須先對本文件 §3 的判準草案做出明確定案（哪些留在人工複審、哪些收斂進機械檢查），而非直接開始寫程式。
