## 1. 為什麼需要這份文件

Copy-on-Evolve 的鐵律是「凍結版本唯讀、不回改」。這條規則在 44 輪內被打破 **3 次**（§3），
每次都經使用者當場核准，但**判準只散落在缺陷帳本的散文欄位裡**：

- 帳本 `docs/06_quality/AutoSDD_Defect_Log.md` 是一份逼近 262,144 bytes 輪替上限、
  已歸檔 30 份的檔案；要回答「Copy-on-Evolve 曾在什麼條件下被打破」只能 grep 它。
- `AISDLC_SDD/AISDLC_SDD_v0.30/EVOLUTION_LOG.md` 於 R44（`DEF-101-370`）被指定為
  「例外是否發生過」的權威索引，但**只有 R44／R45 兩節，缺 R46**（R60 實查，見 §7）。
- 兩筆 open watch item（`DEF-101-392`／`DEF-101-401`）曾把破例次數記成「**兩度**（R44／R45）」，
  **與帳本自己在 R46 寫下的「經使用者核准第三次打破」直接矛盾**（§3.4）。
  該矛盾已於同輪由帳本補記訂正列 `DEF-101-549`（`fixed@R60`）訂正為 **3 次**；
  本節保留敘述是為了記錄「為何需要本檔」的成因，不是未結落差（見 §7）。

於是同一件事在三個地方有三種說法，而下一位遇到「這個跨平台缺陷要不要回補 29 版？」
的人沒有可執行的判準可查。本檔補上該判準。

## 2. 機械事實（R60 親自實測，非引述）

```
$ ls -d AISDLC_SDD/AISDLC_SDD_v0.* | wc -l
30                                        # v0.01 ~ v0.30
$ SDD_GATE_DRY_RUN=1 bash AISDLC_SDD/scripts/ci-gate.sh
SDD_GATE_VERSIONS=AISDLC_SDD_v0.01 AISDLC_SDD_v0.30      （rc=0）
```

- 官方閘門（`AISDLC_SDD/scripts/ci-gate.sh:62-77`）只跑 **雙軌**：
  `FROZEN_BASELINE="AISDLC_SDD_v0.01"` ＋ 動態解析的 `LATEST`。
- 因此 **中間 28 個版本（v0.02～v0.29）不在任何自動閘門的執行面內**。
  它們的程式碼只會被「repo-wide 靜態掃描鎖」摸到（例如
  `tools/tests/test_sanitize_component_frozen_sdd_versions_lock.py`），不會被執行。
- 這是本 ADR 全部分診邏輯的物理前提：**回補中間 28 版不會讓任何自動測試變綠或變紅**，
  它的價值只有「防禦縱深」與「有人真的 cd 進舊版目錄時不炸」。

## 3. 歷次破例的實際判準（**共 3 次，不是 2 次**）

### 3.4 帳本次數記載錯誤（本 ADR 順帶訂正）

`DEF-101-392`（2026-07-26，R48）寫「已**兩度**（R44／R45）被迫打破鐵律回補」；
`DEF-101-401`（2026-07-26，R50）寫「亦未發現 R49 之後出現第三次…新事證」「`DEF-101-357/358`（R44/R45）**兩次**破例」。
但 `DEF-101-379`（archive_22，日期 2026-07-**25**）狀態欄已逐字寫「經使用者核准**第三次**打破 Copy-on-Evolve」。
時間序：R46 破例（07-25）→ R48 寫「兩度」（07-26）→ R49 四方複審未訂正 → R50 再覆核仍以 2 為基數。

**正確次數＝3**（R44／R45／R46）。影響：`DEF-101-401` 的升級理由建立在「復發頻率」上，
實際是**三輪連續各一次**而非兩輪兩次——它低估了自己要主張的那個趨勢，而這兩筆正是送 PM／ADR 的決策依據。
依帳本「只增不刪」政策，帳本端以**補記訂正列**處理（不改 `DEF-101-392`／`401` 原文）：
**已完成**＝`DEF-101-549`（`fixed@R60`，主控執行）。本 ADR 不改帳本。

## 4. 分診規則（可執行）

遇到「LATEST 已修好、凍結版還有同一個缺陷」時，**依序**回答：

### 步驟 0（前置，不可跳過）— 先取證，再談判準

必須先產出下列三項，任一項拿不出來就**不得進入步驟 1**，一律先走 §4.3「只動 LATEST」：

1. **可觸達性**：列出凍結版**生產碼**（非測試、非註解）的實際消費者。
   零消費者＝孤立鷹架，可觸達性為 **否**——但**只有在實驗組 `rc=1` 且控制組回非零命中時才算數**。

   ```
   grep -rn "<入口符號>" --include='*.py' AISDLC_SDD/; echo "rc=$?"    # 實驗組
   grep -rn "def " --include='*.py' AISDLC_SDD/ | wc -l                # 控制組：必須 > 0
   ```

   🔴 **R67 訂正（本行原指令在 macOS 上使本閘門恆答「否」）**：本項原文的 glob 寫作
   `--include=` 後面直接跟裸 `*.py`（未加引號）。macOS 預設 shell 是 zsh、`nomatch` 預設開啟，
   而 repo 內不存在名為 `--include=<某字元>.py` 的檔案 ⇒ **zsh 在呼叫 `grep` 之前就跳過整條命令**，
   stdout 全空、`rc=1`；本判準卻明文把零輸出定義為「可觸達性＝否」，且 §4「任一項拿不出來就
   **不得進入步驟 1**」⇒ 這道不可跳過的前置閘門在 macOS 上**結構性恆答否**，每一次 Copy-on-Evolve
   回補評估都被自動路由到 §4.3「只動 LATEST」，而評估者看到的是一個與 grep 無關的 shell 錯誤，
   或（腳本吞掉 stderr 時）一片空白。R67 於 `Darwin 25.5.0` 實測同一符號同一 shell：
   未加引號 → `zsh:1: no matches found: --include=*.py`、`rc=1`、零命中；  <!-- zsh-glob-ok: 訂正段必須逐字引述壞形態，否則讀者無從辨認自己手上那條是不是同一個 -->
   加單引號 → **7 行命中**、`rc=0`（bash 3.2.57 對照組同為 7 行、`rc=0`）
   ⇒ 零輸出來自 **shell 層**而非 grep 的判定。單引號在 bash／zsh／PowerShell 三側皆正確，
   與根 `CLAUDE.md` 對 `'.[dev,notifications]'` 已採的統一政策同型（DEF-101-479／507／508 同族）。
   **控制組是這條訂正的另一半**：硬規則① 明文「『綠』或『零輸出』不得直接當成好消息」，
   而本項恰恰是拿零輸出當判準——故此後零消費者的結論**必須同時出示控制組的非零命中**，
   否則只證明了「載具沒跑起來」，沒證明「沒有消費者」。
2. **可利用性**：對**修復前的原始碼**用真實 payload 實跑一次，貼出真實輸出。
   R46 的教訓：不做這一步就會用「P1／可觸達」的錯誤前提去換核准。
3. **平台歸屬**：這是跨平台缺陷（Windows/macOS 行為差異）還是與平台無關的一般缺陷？
   後者不走本 ADR。

### 步驟 1 — 有沒有結構性根因（同一份邏輯散落 N 份拷貝）？

**有** → 首選 **§4.1「抽共享層」**，不是逐版打補丁。
R45 判例：「若繼續維持 N 份複本，未來每次發現新盲點都要重複走一次破例流程」。
**沒有**（缺陷只在一支檔案的一個位置） → 步驟 2。

### 步驟 2 — 缺陷在凍結版上是否「真實可利用」？

| 判定 | 依據（步驟 0 的取證） | 處置 |
|------|----------------------|------|
| **是**：有生產碼消費者 ＋ 實跑重現越界讀寫／執行 | R44：203 呼叫點逐版證實可逃逸 | **§4.2 逐版回補**，P0/P1，須 signoff |
| **否，但一行等價修法、機械可套用、零行為風險** | R46：零消費者、`FileNotFoundError`；修法＝加一層既有淨化函式 | **§4.2 逐版回補**，P3，須 signoff；核准理由只能寫「防禦縱深＋跨版本一致性」，**不得**宣稱可利用 |
| **否，且修法需要改邏輯／換 API／新增依賴** | DEF-101-004（`declare -A` → bash 3.2 重寫）、DEF-101-040（settings.json 結構） | **§4.3 只動 LATEST**，wontfix ＋ known-gap 入 `ONBOARDING.md` §9 |
| **否，且觸發需要「人工 cd 進舊版目錄」** | DEF-101-056／057（`install_post_commit` 編碼／worktree 路徑）、DEF-101-359（`run_self_evolution` guard 缺口） | **§4.3 只動 LATEST**，wontfix；帳本明文寫「若未來有文件/流程引導使用者手動 cd 進舊版目錄執行，屆時重新評估」 |

### 4.1 首選：抽共享層（免破例，成本最低）

把重複邏輯抽到 **不屬任何版本目錄** 的共用檔（`AISDLC_SDD/scripts/…`），各版以
`importlib.util.spec_from_file_location` 依**絕對路徑**載入（**不**插 `sys.path`、
**不**寫入 `sys.modules`，避免跨版本模組快取污染）。

- 先例：`copy_on_evolve.sh`／`sdd_version.py`（`EVOLUTION_LOG.md::DEF-15-001`「共享 infra 同輪修，免 Copy-on-Evolve」）、
  R45 的 `component_sanitizer.py`。
- **仍算破例**（要動 29 版的 `state_loader.py` 去改成委派），但**只需破例一次**，
  之後同類強化零破例。
- **必須明文記載的代價**：該函式的「凍結」自此只涵蓋原始碼層級、不涵蓋行為層級。

### 4.2 逐版回補（真正的破例）

強制條件（缺一不可）：

1. **修法必須是「套用該版本既有能力」的最小改動**，不得把 LATEST 的新實作搬進舊版
   （R44 明文：呼叫**該版**既有的較弱版淨化函式；強化版另案處理＝後來的 R45）。
2. **機械套用腳本一律 `newline=""`**（R44 踩過：LF 被靜默改成 CRLF，違反 `.gitattributes` `eol=lf`）。
3. **落地後逐版驗證**並貼出真實輸出（R44 用 `python -m pytest tools/fsm_runtime/tests/ -m "not chaos" -q`）。
4. **必須同輪補上機械回歸鎖**——這是 `DEF-101-367`（P2）的教訓：R44 的 203 處修復
   當時**零自動化回歸測試**，只靠工程師手跑過。鎖的形狀照
   `tools/tests/test_sanitize_component_frozen_sdd_versions_lock.py`：
   ① 掃描邊界鎖（凍結版本數 ≥ N、目標檔案皆存在，防掃描面靜默縮小）；
   ② 逐版正向斷言修復字面存在（非註解）；
   ③ 用 `git show HEAD:<path>` 重放「修復前」的真實歷史內容，證明正向斷言真的會判「未通過」
   （**不得**用合成範例——合成範例證明不了對真實迴歸有鑑別力）。
5. **必須同輪在 `AISDLC_SDD/AISDLC_SDD_v0.<LATEST>/EVOLUTION_LOG.md` 新增「凍結基線例外」章節**
   （`DEF-101-370` 拍板：帳本是逐版驗證細節的權威出處，`EVOLUTION_LOG.md` 是
   「例外是否發生過」的索引入口），欄位比照既有兩節：
   範圍／日期+signoff／打破理由／修法／驗證／殘留落差／回退指引。

### 4.3 只動 LATEST（預設答案）

- LATEST 照修。凍結版列 **wontfix**，理由寫「凍結基線治理規則優先於個別 bug 回補」。
- **C1｜known-gap 必須寫進根層 `ONBOARDING.md` §9**（DEF-101-004／019／020／040 的統一處置），
  否則「不修」會退化成「沒人知道」。
- **C2｜帳本分流欄或狀態欄必須寫出重新評估的觸發條件**（例：「若未來有文件/流程引導使用者
  手動 cd 進舊版目錄執行 hook 安裝，屆時需重新評估」），不得只寫「不修」。
  🔴 **掃描面為何是「分流欄或狀態欄」而非只有狀態欄**（R60 round 2 訂正）：本條的正例
  `DEF-101-056`／`DEF-101-057`（上面那句例文就是逐字抄它們的）把觸發條件寫在**分流欄**，
  狀態欄沒有。舊文只寫「狀態欄」，機械化時本 ADR 自己舉的兩個正例會被判不合格——
  判準與例證互相打臉。改為與 §4.3.1 同一掃描面（分流欄或狀態欄），例證即成立。

#### 4.3.1 觸發判準（誰要滿足 C1／C2 —— 不留解讀空間）

一筆帳本列**只要分流欄或狀態欄同時出現「凍結版／凍結基線」與「不回補／wontfix」兩類
字樣**，即落入本節，C1／C2 皆為**強制**（不是「視情況」、不是「建議」）。
C2 的「重新評估的觸發條件」判準字樣＝「重新評估／屆時」（與 §4.3.2 ③ 的 grep 同一組）。

上面三組字樣（含分隔號寫法）是機械鎖 `tools/tests/test_adr_xplat001_c1c2_lock.py` 的
**唯一判準來源**：該鎖從本節這幾句話裡把字樣抽出來與自己的常數雙向比對，任一邊被改動
（本節改字 或 鎖改常數）都會翻紅並指出兩邊不一致——**散文與程式不得各走各的**。

#### 4.3.2 落地自檢（人工複核用；正式判準是機械鎖）

```bash
# ① 粗篩：列出可能落入 §4.3 的帳本列（⚠️ 這是「整列」比對，比 §4.3.1 寬）
grep -nE '凍結版|凍結基線' docs/06_quality/AutoSDD_Defect_Log.md | grep -E '不回補|wontfix'
# ② 逐筆確認 ONBOARDING §9 表內有對應列（C1）
sed -n '/^## 9\. 已知缺口/,/^---/p' ONBOARDING.md
# ③ 逐筆確認分流欄或狀態欄有「重新評估／屆時」字樣（C2）
grep -nE '重新評估|屆時' docs/06_quality/AutoSDD_Defect_Log.md
```

🔴 **①只是粗篩，不是判準**（R60 round 2 實測訂正）：它比對**整列**，會把字樣落在
「現象與證據欄」「發現情境欄」的列也算進來，故它的命中數恆 ≥ 依 §4.3.1 真正落入本節的
列數。差集的具名案例＝`DEF-101-358`：它的「凍結版」「不回補」字樣寫在現象欄，而該筆實際
走的是 §4.1（R45 抽共享層、30 版全數委派），**本來就不該被 C1／C2 管**。
（刻意不在本節寫死兩邊的列數——那會多一個 stale 站點；要現查就跑 ①，要正式判準就看鎖。）
正式判準一律以 §4.3.1 的欄位範圍為準，由機械鎖執行；① 保留給人工快速掃讀。

⚠️ 同時記下 §4.3.1 判準的天花板（`DEF-101-552` 順帶暴露）：關鍵字比對**分不出「宣稱不予
回補」與「引述並否定該宣稱」**。一列若在敘述中引用舊措辭來否定它（例如訂正列寫「§4.3
對本項是 N/A、不該虛構 §9 列」），關鍵字仍可能命中。欄位範圍（只看分流／狀態欄）已把
「純敘述引述」擋掉大半，剩下的由機械鎖的**具名豁免＋WHY**承接——這也是那張表存在的
第二個理由，不只是為了 grandfather 舊列。

#### 4.3.3 未滿足時的處置（硬規則）

C1 或 C2 任一項未滿足時，該筆帳本列**不得**寫成 `fixed@R<n>`——只能寫
`partial@R<n>（§4.3 條件未滿足）`，並在本檔 §7 立一列指定承接者。
**理由**：`fixed` 是「這件事處理完了」的宣稱，而 §4.3 的「處理完」在定義上就包含
C1／C2；少了它們，凍結版那半邊只是消失在紀錄裡，不是被決定不修。

#### 4.3.4 機械鎖（R60 round 2 落地）與它的邊界

C1／C2 已由 **`tools/tests/test_adr_xplat001_c1c2_lock.py`** 機械強制
（根層 `unittest discover` → `tools/run_root_unittests.py`，pre-push root-infra leg
＋ `root-infra-ci.yml` ＋ 兩份 compat-ci 皆執行，非只在 CI）。它做三件事：

1. **判準與本節散文雙向綁定**：從 §4.3.1／C2 的句子裡抽出三組字樣，與鎖內常數互相比對，
   任一邊改動即紅。散文改了而程式沒跟（或反之）不可能靜默。
2. **硬擋新列**：落入 §4.3.1 而 C1 或 C2 未滿足的帳本列 → 紅，逐列指名缺哪一項。
   合法出口有兩個：補齊 C1／C2，或依 §4.3.3 把狀態降為 `partial@R<n>（§4.3 條件未滿足）`
   ——**後者不需要任何豁免登記**，所以「非得加豁免才過得去」從一開始就不成立。
   🔴 **掃描面＝帳本家族全檔（主檔＋全部 archive）**，枚舉走 `tools/archive_defect_log.py`
   的 `_family_files()`（家族 SSOT，鎖只 import 不自寫 glob——ARCH-R60-09 明文批評過
   「一個 finding 一支鎖、掃描面各自為政」）。WHY（R60 round 3 補，SA-R60R2-04）：落入
   §4.3.1 的列典型狀態是 `wontfix`，而歸檔工具判準① 對 `wontfix` 是**允許搬遷**的
   ⇒ round 2 的鎖只掃主檔時，「新增一筆違規列 ＋ 同輪把它歸檔」可以整條繞過硬擋。
   擴面後的射程分兩層：**ADR 落地後的新列（ID > 上界）在家族任一份檔都擋，且不接受豁免
   登記**；ADR 落地前的舊列只在主檔要求合規或具名登記，已歸檔者不在射程（設計上不追溯）。
   該繞道面在被發現時**尚未被利用**——擴面後實測 archive 側落入 §4.3.1 而條件未滿足者只有
   `DEF-43-011`／`DEF-101-357`，兩者都遠早於本 ADR 落地 ⇒ 零假紅。
3. **既有舊列具名基線豁免（grandfathered），且豁免自己會過期**：本 ADR 是 R60 才寫成的，
   落入 §4.3.1 的列大多在它之前（2026-07-09～07-26）就已判定，而 C2 這條規則正是 R60 寫
   本 ADR 時從 `DEF-101-056`／`057` 的既有寫法**反推**成明文的——那批舊列缺 C2 是規則追溯
   適用，不是當時漏辦。若鎖一上線就對它們全紅，下一個人會直接把鎖關掉——那道鎖就等於沒加。
   故以 `_BASELINE_WAIVERS` 逐列具名登記（每筆必附「為何當時沒滿足」與「承接者」，缺一即紅；
   筆數以該表為唯一真相源，本節刻意不寫死數字），並用三道自檢阻止它變成永久豁免：
   - **stale 自檢**：被豁免的那一項一旦真的滿足了，鎖立刻紅並要求刪掉該筆登記
     （對照 R60 被四方拆穿的 `_PENDING_MIGRATION_SITES`——它刻意不加 stale 自檢，
     於是「pending」名義下事實上永久豁免；本表不重犯）。
   - **基線 ID 上界（刻意不綁日曆）**：**ID 上界**＝`DEF-101-526`（鎖內 `_BASELINE_ID_CEILING`）
     ＝本 ADR 落地前的最後一筆帳本列。登記的每一列，其帳本 ID 必須 ≤ 該上界；本 ADR 落地
     之後才開的列，ID 必然大於它 ⇒ **結構上不可能被塞進基線**。該上界同時寫在本節與鎖內
     常數，由鎖雙向比對，改一邊即紅。
     🔴 **為什麼不用「發現日期 ≤ 落地日」**（R60 round 3 訂正，SD-R60-R2-05 ①）：本 ADR 的
     落地日與本輪全部新列的發現日期**是同一天**，而日界用嚴格大於比較 ⇒ 對「同日新列」
     完全不設防。SD 以 monkeypatch 合成列實測：日期填落地當日＋登記進表＋上限加一，
     round 2 的鎖**全綠**；日期改成隔天才紅。也就是說「日界之後的新列在結構上不可能被塞進
     基線」這句話對落地本 ADR 的那一輪自己的產出根本不成立。改用與日曆脫鉤的單調量（帳本
     ID），同 `ADR-SD09-011` 把「源碼演進證據」從「日曆天數」解綁的先例。
     鎖另以**上界列自身的發現日期**（從帳本現查，不寫死日期常數）作輔助判準，擋「回填一個
     未用過的舊號碼」這種繞法的一半；ID 與日期兩個欄位都造假仍可逃過，此邊界已寫在鎖的
     docstring，並須經 `check_defect_log_crossref.py` 與 diff 兩道人眼可見面。
   - **shrink-only 棘輪**：`_MAX_BASELINE_ENTRIES`（筆數上限）與 `_BASELINE_ID_CEILING`
     （ID 上界）皆只准往下改，由鎖以 `git show HEAD:<鎖檔>` 取上一版常數機械比對，調升即紅
     （`TestShrinkOnlyRatchet`）。
     🔴 **round 2 這一條原本只是人審慣例冒充機制**（SD-R60-R2-05 ②）：當時唯一的斷言是
     「筆數 ≤ 上限」，SD 實測把上限往上改**不會紅**、改小才紅 ⇒ 檔頭宣稱的「只准往下改」
     沒有任何機制支撐。現版才是真棘輪。已知空轉窗口：鎖檔自身的**首個 commit** 上 HEAD 還
     沒有它可比，該情形一律 `skipTest` 並印出理由（`run_root_unittests.py` 逐處列印全部
     skip），鑑別力另以合成上一版永久釘住。

**首例的結案記錄（本 ADR 自己的信用紀錄，留在此節而非 §7——§7 只收未結項）**：R60 落地本節的同一輪，自己就有兩列走 §4.3 而 C1／C2 未滿足（ARCH-R60-05）。round 2 的處置**不是把它們 grandfather 掉**，而是逐列查清後真的結掉：
- `DEF-101-534`：C1（`ONBOARDING.md` §9 表末列補列並回指該 ID）＋ C2（狀態欄列出三條
  重新評估觸發條件）皆補齊，機械鎖實測兩項通過 ⇒ `fixed@R60` 據此才成立。
- `DEF-101-552`：逐版實查 `requires_docker_success` 在 v0.01~v0.29 **全 29 版 0 命中**、
  v0.30 才有 ⇒ **不存在凍結版落差**，§4.3 對它是 **N/A 而非豁免**，§9 不該為它虛構一列；
  該列敘述已據實訂正，因此不再落入 §4.3.1。
兩列一度以 provisional 形態登記在 `_BASELINE_WAIVERS`，鎖的 stale 自檢在兩包落地的當下就翻紅並逐字指名該刪哪一筆——**那道自檢的鑑別力是在真實資料上被證實的，不是靠合成情境**。

**邊界（誠實劃界，勿超譯）**：C1 的機械判準是「該 `DEF-ID` 出現在 `ONBOARDING.md` §9
區段內」（§9 的表列與其下方「對應缺陷帳本」註腳都算——`DEF-101-003`／`004` 的 ID 就只
寫在註腳裡）。它保證**追溯鏈存在**，但**不保證那一列描述的就是同一個缺口**；語意對應
仍是人審責任（同 `test_defect_id_reference_integrity.py` 已劃的同型邊界）。同理，C2 只
保證字樣在，不保證那句觸發條件寫得好。**不要因為這道鎖是綠的就以為 §4.3 已被完全保證。**

## 6. 反面清單（明確**不**構成破例理由）

- 「順手一起改比較整齊」／「跨版本一致性看起來比較好」——單獨不成立（R46 是搭在
  「一行等價修法＋零風險」上才過，且核准依據事後被證偽）。
- 「掃描器新增了判準，凍結版全部命中」——掃描器擴面本身不是回補授權；
  先問步驟 0/1/2，命中數量不是判準。
- 「這也是跨平台缺陷」——`DEF-101-004`（bash 3.2 `declare -A`）就是純跨平台缺陷且
  必炸，仍判 wontfix，因為修法要改邏輯（步驟 2 第三列）。
- 「LATEST 已經修好了所以舊版也該修」——`ci-gate` 從不執行中間 28 版（§2），
  修它們不會讓任何閘門變綠。
