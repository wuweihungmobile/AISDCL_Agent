（它是正常退出，不是異常死亡）⇒ 缺陷③ 的**內容**改寫於 **§4.0**（D1~D4）；
② §4.3 的探針設計照 **F1~F7** 修訂（§4.3-a），含一格「預測證偽」；
③ **`AUTOSDD_RESUME_OFF` 這個 User 層變數的去留與 §3 的授權裁決是同一題兩面**
⇒ 進 §3.5 **Q7**。

**三者的共同形狀**，也是本 ADR 的統一命題：

> **每一環都能拿到憑證，而憑證都不回答那個問題。**
> 排程成立（`NextRunTime` 非空）但醒在錯的時刻；那一跑 rc=0 但一個檔都沒改；
> armed stamp 存在但排程器裡沒有那支工作。
> ADR-XPLAT-004 §2.1 已為這種失效命名——「憑證存在、但憑證不回答那個問題」是**最難看見的假綠**。
> 本 ADR 的三項改善，每一項都必須交付**一個會回答那個問題的新憑證**，而不只是多一段程式。

## 2. 缺陷①：排程時刻退回 `now+5h` 假設值

### 2.1 現況（實讀，非推論）

| 事實 | 出處 |
| --- | --- |
| `DEFAULT_AT_EXPR = "(Get-Date).AddHours(5)"` | `tools/session_resume_planner.py:287`〔實讀〕 |
| `--at` 的 default 就是它 | 同檔 `:933-934`〔實讀〕 |
| `--register-schtasks` 直接把 `args.at` 交給 `_register_at_expr()`，**全程不碰額度快取** | 同檔 `:1560-1562`〔實讀〕 |
| 該常數的 docstring 自己已經寫著「它是**猜的**，不是 reset 時刻」 | 同檔 `:278-286`〔實讀〕 |

⇒ 這不是「有人忘了」，是**設計上被留下的一條猜測路**，而 R107 那一窗剛好走了它兩次。
它與根 CLAUDE.md〈額度哨兵〉逐字要求的「解不出時刻一律**拒絕武裝**，不准退回『假設 5 小時』」
**直接衝突**——衝突之所以能存活到今天，是因為那條紀律的機械物
（`relay_problems()` 的 `reset_source` 白名單，`:488-489`〔實讀〕）**只守續航狀態塊那條路**，
`--register-schtasks` 這條手動路壓根不寫狀態塊，於是判準的射程外。

### 2.2 設計：時刻解析階梯（**不新增第二個判斷家**）

🔴 **本節最重要的設計決定是「不發明新東西」**：`repo` 裡已經有一支函式在回答
「該等哪一個 reset」——`tools/lib/quota_messages.py:101-105` 的 `halt_resets_at(decision)`
（R95 修4，取 ≥halt 各軸中最早可解析者；全軸皆無 ⇒ 回 binding 原值）〔實讀〕。
排程時刻的解析必須**接到它**，而不是在 planner 裡長第二套。

🔴 **第二個設計決定是「不排第二套優先序」**：優先序這份知識的家＝ADR-XPLAT-005 §2.7
（`:244-251`〔實讀〕「1. `endpoint-authoritative` → 2. `transcript-verbatim`／
`probe-verbatim` → 3. 拒絕武裝」）。下表**就是那三段**，只是把「誰去取值、取不到往哪走」
補成可執行的階梯——🔴 **除 L0 外**，階梯的排序與字面一格都不是本 ADR 自訂的
（二審 Architect-N4 承接：上一版寫「階梯的排序與字面**一格都**不是本 ADR 自訂的」是一句
過寬的宣稱——**L0 與它的字面 `operator-asserted` 正是本 ADR 自訂的**，理由見約束 3，
而該字面同時要進 `relay_problems()` 的白名單（A4）⇒ 它是一個**新增的裁決**，
不是 005 §2.7 的落地。把它算進「不是自訂」裡，會讓下一個讀者以為那一格已經被 005 審過）：

```
L0  --at 有顯式值（人打的）           ⇒ 直接用；reset_source="operator-asserted"
                                        （🔴 新字面，理由見約束 3；**不是**既有的 "operator"）
L1  endpoint 的 resets_at             ⇒ reset_source="endpoint-authoritative"
      取值：quota_gate.read_quota()（F1 紅時允許同步刷新一次）
            → quota_policy.decide() → quota_messages.halt_resets_at()
      （005 §2.7 第 1 位。字面**沿用 005 已裁決的那一個**，本 ADR 不另立名字）
L2  逐字稿觀測值（guard.parse_reset_at） ⇒ "transcript-verbatim"（005 §2.7 第 2 位：離線 fallback）
L3  探針輸出觀測值                     ⇒ "probe-verbatim"（同上）
L4  解不出 / 死窗值 / 太遠             ⇒ 🔴 拒絕武裝，rc≠0，出聲說「解不出」
                                        絕不合成假時刻、絕不退回 (Get-Date).AddHours(5)
                                        （L4 有兩臂，見 §2.4）
```

🔴 **與本 ADR 上一版的差異，照實記**：上一版把這條階梯排成「L1 逐字稿 → L2 探針 →
L3 快取」並給快取一個新字面 `meter-observed`。兩處都撤回：**排序**撤回是因為 005 §2.7
已經逐字裁過「權威通道存在時，解字面／猜時區那些問題整組消失……而且**在撞線之前就拿得到**」
（`:242`〔實讀〕）——把撞線後才有的字面解析排在權威通道之上，等於在本 ADR 內部反轉 005 的
裁決；**字面**撤回是因為那會讓同一個值有兩個名字（見 §8 被否決清單新增列）。

五條約束，缺一則階梯本身變成新的假綠來源：

1. **階梯只准往上走，不准往下退**。L1 解不出時的下一站是 L2／L3，全數落空的下一站是
   **L4**，不是「回到 5 小時」。`DEFAULT_AT_EXPR` 這個常數應在本項落地時**整支刪除**
   （不是改小、不是加註解），因為只要它還在 argparse 的 `default=` 上，
   任何忘了帶 `--at` 的呼叫都會靜默走它。
2. **`reset_source` 白名單只加 005 已裁決的那一格**。實作面＝`relay_problems()` 的白名單
   （`tools/session_resume_planner.py:488-489`〔實讀〕，現為
   `("transcript-verbatim", "probe-verbatim", "operator")`）加入 `"endpoint-authoritative"`
   ——這正是 005 §2.7 `:250` 逐字要求的那一格〔實讀〕，本 ADR 只是它的落地。
   🔴 **兩份 ADR 指的是同一格，落地時只加一次**：005 §2.7 與本節不是兩件待辦，
   哪一份先落地就由它加，另一份的該項隨即視為已落地（避免同一格被加兩次或加成兩個字面）。
   （附註：005 §2.7 把座標記成 `planner:476-477`，本輪實讀已漂到 `:488-489`——
   **行號漂移，內容是同一格**；本 ADR 用本輪實讀的座標，不改 005。）
   🔴 **不得**借用 `transcript-verbatim` 蒙混過去（借用會摧毀那道守衛僅有的鑑別力），
   也**不得**新造第三個字面。
3. **`operator` 這一格不得擴大解釋，L0 必須自立字面**。`:486-489` 的註解逐字說明
   `operator` 是給哨兵巡邏間隔用的、「那不是在宣稱任何 reset 時刻」〔實讀〕——
   而那道白名單的鑑別軸就是「**有沒有在宣稱一個 reset 時刻**」。
   人手打 `--at 14:00` **正是在宣稱**一個 reset 時刻 ⇒ 它落 `operator` 會把該軸的語意
   反轉（原本「不宣稱時刻」的免檢格，變成「宣稱了時刻但不必是觀測值」的放行格）。
   故 L0 用**自己的字面** `operator-asserted`，白名單兩格並存、語意各自單一；
   `operator` 的既有射程（哨兵巡邏）一格都不動。**工具自己猜的值兩格都不准借用。**
4. **`resets_at` 的比較與去重一律截到分鐘**（承接 005 §1.3 A5／§2.7 `:251`〔實讀〕：
   實測次秒級抖動 `13:39:59.297723` vs `13:40:00.815928`，皆 UTC）。
   🔴 少了這一條，L1 每次巡邏都會判「reset 變了」而重排——而重排要走 §2.5 的
   unregister→重註冊，於是一個抖動會反覆重建排程、每次都短暫沒有排程。
   **實作要求**：階梯內部一切「這個時刻跟上次一樣嗎」的判斷，比較前先
   `replace(second=0, microsecond=0)`；**禁止字串相等比較**。
5. **時區收斂不下沉**。`register_endurance()` 的 `at.astimezone().strftime(...)`
   （`:821-825`〔實讀〕）必須保留在 L1 的路徑上——`quota_meter.bucket_readings()`
   逐桶保留的是**伺服器原字串**、不轉本地（`tools/lib/quota_meter.py:421-431`〔實讀〕），
   而 `New-ScheduledTaskTrigger -At '<字串>'` 一律以機器本地時區解讀。少了這一步，
   排程照樣成立、`NextRunTime` 照樣拿得到，只是醒在錯的時區。

### 2.3 新鮮度判準：**快取在 TTL 內 ≠ `resets_at` 還活著**

這是本項最容易做錯的一格，而它已經有前科。`DEF-200-200`（帳本 `:206`〔實讀〕）
記載同一個欄位「已過去的 `resets_at`」在**四層各自誤判**：

| 層 | 誤判形態 | 對本設計的意義 |
| --- | --- | --- |
| ① | 快取在 TTL 內但**已跨窗** ⇒ `--pace` 拿死窗值當現值 | **L1 直接踩的就是這一格**：`QUOTA_CACHE_TTL_SECONDS = 180`（`tools/lib/quota_gate.py:144`〔實讀〕）只保證「這筆讀數 180 秒內量過」，**不保證它的 `resets_at` 還在未來** |
| ② | `_delta_minutes` 把任何負值標 `clock-skew`（本機時鐘實測無偏移） | 診斷會把 operator 指向錯的子系統 ⇒ L4 的出聲訊息**不得**沿用 clock-skew 措辭 |
| ③ | 呈現層把已過去的時刻播報成「很快會自己解除」 | L1 若採信死窗值，`NextRunTime` 會落在過去 ⇒ 排程器立刻觸發或永不觸發，兩種都不是設計意圖 |
| ④ | `quota_pace.row_of()` 不落 `resets_at` ⇒ 歷史落款上「reset 有沒有漂掉」結構性不可回答 | 這是**驗證本項有沒有修好的前提**：沒有這一欄，事後無從判斷當時排的時刻對不對 |

⇒ **新鮮度判準（三道，順序不可調換）**：

```
判準 F1（鮮度）：快取 measured_at 與 now 的距離 ≤ QUOTA_CACHE_TTL_SECONDS
                 —— 這一道 quota_gate.read_quota() 已經做了（:413-422 stale-cache〔實讀〕），
                    本設計不重寫，只要求呼叫端不得繞過它去直接 read_cache()。
判準 F2（活性・下界）：解出的 resets_at 必須 > now（帶 ≥ 一個 RESET_SKEW 的餘裕）。
                 —— 這一道今天不存在。F1 綠而 F2 紅的組合，就是 DEF-200-200 ① 的定義。
判準 F3（可等性・上界）：quota_messages.reset_branch(<解出的值>, now) 必須 == "arm"。
                 —— 這一道**今天已經存在、只是沒有接在這條路上**：既有的 6 小時視界
                    （RESET_ARM_HORIZON_SECONDS，quota_messages.py:53〔實讀〕，
                    方向鎖逐字＝「七天後才 reset 的線不得被排程」）。
三道都綠 ⇒ L1 成立。F1 紅 ⇒ 允許同步刷新一次再判（既有 refresh_quota_blocking 有界逾時）。
F2 或 F3 紅 ⇒ 🔴 一律降到 L4（拒絕武裝／叫人，見 §2.4 兩臂）。
```

🔴 **F2 紅時為什麼不能「排在 now+skew」**：那正是把一個死窗值當成活值使用。
`resets_at` 已過去只有兩種解釋——額度早就回來了（那就不需要排程，該做的是直接續跑），
或那筆讀數屬於上一個視窗（那就沒有任何資訊）。兩種都不該產生一支排程。

#### 為什麼一定要 F3，以及為什麼**不是** `decision.band` 白名單〔本輪實測〕

F1／F2 兩道**不足**，這是本輪對真 `quota_policy.decide()`／`quota_messages` 注射四個情境
量出來的（唯讀呼叫生產純函式、零網路；now 固定 2026-08-28T12:00Z）：

| 情境 | 注入 | `band` | `halt_resets_at()` 距 now | F1／F2 | `reset_branch()` | 少了 F3 會怎樣 |
| --- | --- | --- | --- | --- | --- | --- |
| **S1** | `seven_day` 40%、reset=+6000 分 | `free` | **+6000 分（4.2 天）** | 皆綠 | `notify` | 🔴 **人在未撞線時跑 `--register-schtasks`，排出 4.2 天後才響的工作，`NextRunTime` 照樣拿得到＝痕跡全綠**（R59 事故同形）。這正是 SD 一審 B1 指出的那條路 |
| **S2** | `seven_day` **97%**、reset=+6000 分 | **`halt`** | +6000 分 | 皆綠 | `notify` | 🔴 **`band ∈ {halt, unmeasured}` 白名單在這一格照樣放行**——週軸自己撞線時 band 是 halt，而該等的 reset 仍在 4.2 天後 |
| **S3** | `five_hour` 97%、reset=+90 分 | `halt` | +90 分 | 皆綠 | `arm` | 唯一該武裝的一格 |
| **S4** | 零軸（量不到） | `unmeasured` | `None` | F2 紅 | `escalate` | 由 F2／L4 接手，白名單反而會**放行**它 |
| **S5** | `five_hour` **40%**、reset=+90 分 | `free` | +90 分 | 皆綠 | `arm` | **應該放行**（人在水位還低時預排下一輪）——F3 放行、**band 白名單會 REFUSE** ⇒ 這一格是白名單的**假紅**證明 |

⇒ **裁定：第三道判準採 F3（沿用既有 6 小時視界），不採 band 白名單。**
理由是 S1／S2 兩格構成雙向反證：band 白名單既**不必要**（S1 的 `free` 帶被它擋掉，
而該擋的理由其實是距離不是水位）也**不充分**（S2 的 `halt` 帶被它放行，距離卻是 4.2 天）。
「該不該排程等它」這件事的判準軸從頭到尾是**reset 有多遠**，而那條軸已經有一個家。
**兩道都上（AND）呢？也不採，但理由是反方向的**——那不會產生假綠（S2 仍被 F3 擋下），
而是產生**假紅**：本輪多測一格 **S5**（`five_hour` 40%、reset=+90 分）〔本輪實測〕
⇒ `band=free`／`reset_branch=arm`，**F3 放行、band 白名單 REFUSE**。
那一格是**正當用途**：人在水位還低的時候手動預排「等這一輪 reset 再接回去」。
擋掉它沒有換到任何安全性（時刻是權威觀測值、距離在視界內），而
「**擋到讓人無法工作的守衛會被整個關掉**」是本 repo 已判過的形態
（見根 CLAUDE.md 鐵律五對判準精準度的要求）。⇒ **只上 F3。**

🔴 **F2 與 F3 必須並存、不能只留 F3**（「下限型判準要雙邊帶」，R75 判例）：
`reset_branch()` 是**純上界**——本輪實測 reset 在 **-30 分**與 **-3000 分**（皆已過去）
時它一律回 `arm`。單靠 F3，死窗值會被判成「可以排程」。
🔴 **上界是閉區間，這一格必須寫出來（二審 SD-N4）**：`RESET_ARM_HORIZON_SECONDS`
現查 **21600** 秒（＝360 分），而〔本輪實測逐字〕`+359 min -> 'arm'`、
**`+360 min -> 'arm'`**、`+361 min -> 'notify'` ⇒ 區間為 **`(-∞, +360]`**。
上一版只記 359／361 兩格，那讓「`<` 還是 `<=`」在判準上失明（機械物＝§6 **A7-b**）。

🔴 **判準的家在哪**：F3 直接呼叫 `quota_messages.reset_branch()`，
**不得**在 planner 裡複寫一次 6 小時或那個比較式——那個常數與方向鎖已經有一個家
（同 §8 對「把時刻解析寫在 planner 內部」的否決理由）。

### 2.4 buffer 的語意，以及與 15 分巡邏的分工界線

**buffer 是什麼**：reset 是滾動視窗，踩點觸發會在邊界上失敗——這是 `RESET_SKEW_SECONDS = 120`
（`tools/session_resume_planner.py:296`〔實讀〕）的既有立案理由，本 ADR **不改這個值**。

**兩個常數、兩個家的問題要在本項一併結清**：PRD 另有 `RESET_BUFFER_SECONDS=30`
（`docs/01_requirements/AutoClaude_Token_監控與喚醒機制_PRD_v2.1.md:1843`〔實讀〕，
§4.5.2 的 `target_wall = reset_timestamp + RESET_BUFFER_SECONDS`，`:1053`〔實讀〕）。
兩者是**同一個語意的兩個家、兩個值**。本 ADR 的立場：

- 實作側的 `RESET_SKEW_SECONDS`（120s）是**已被端到端實測過**的那一個
  （ADR-XPLAT-004 §2.7 記載 `arm_reset → reset=01:50 → 01:52 探測`）；
- PRD 的 30s 屬 in-process 分片休眠那條路（§4.5.2），而本 repo 走的是 OS 排程交棒
  （`CrossPlatform_R98_PRD_Gap_Analysis.md:68`〔實讀〕明載這一點）⇒ 兩條路的邊界成本不同；
- ⇒ **建議：不合併數值，改成合併「這個語意只有一個名字」** —— PRD 側該列標註
  「OS 排程交棒路徑的對等常數＝`RESET_SKEW_SECONDS`，值不同源於載具不同」。
  **這需要動 PRD ⇒ 屬修憲級，列入掌舵者裁決清單（見 §3.5 Q4）。**

**與哨兵 15 分巡邏的分工界線**（這條界線今天沒有寫下來，是三缺陷共同的模糊源）：

| | 一次性續航排程（`--register-schtasks`／`--arm-endurance`） | 哨兵巡邏（`--arm-sentinel`，`SENTINEL_INTERVAL_SECONDS = 900`，`:315`〔實讀〕） |
| --- | --- | --- |
| 它回答的問題 | 「**在那個時刻**把工作接回去」 | 「撞線了沒？撞了的話 reset 是幾點？」 |
| 觸發時刻的來源 | 一個**具體觀測到的** reset 時刻 ＋ skew | 一個**人選的固定間隔**（不宣稱任何 reset 時刻） |
| 成本 | 醒來會探測（ADR-XPLAT-004 §5 E3 記載一次冷探針 31,847 tokens） | 零 token（讀逐字稿 ＋ 一次 `stat`） |
| 解不出 reset 時 | **拒絕武裝**（本 ADR L4；兩臂見下） | 照常巡邏（它本來就不需要 reset 時刻） |
| 誰兜底誰 | — | **巡邏兜底一次性排程**：`tick_plan()` 的 `patrol_handback`（`:606,611`〔實讀〕）已把「探測上限用完／解不出新 reset」導回零成本巡邏，不再永眠 |

⇒ **界線一句話**：**猜測不得進入一次性排程那條路；巡邏不得宣稱 reset 時刻。**

#### 🔴 L4 有兩臂（不是一個動作），且第二臂由 PRD 逐字指定

上一版把 L4 寫成單一動作「拒絕武裝＋確保哨兵在武裝著（掛回零成本巡邏）」。
那對**一種**情形是對的，對另一種是**違反 PRD**：PRD §4.5.10 `:1596-1599`〔實讀〕逐字要求
「🔴 **兩個例外必須繼續走 `escalate`（叫人），不得掛回巡邏**：1. 月度支出上限
（SSOT＝`tools/lib/quota_limits.py::LIMIT_SPEND`）——等到天荒地老都不會回來，只有人去提額」
（該字面＝`"quota_spend"`，`tools/lib/quota_limits.py:54`〔實讀〕）。
🔴 **上段引文是壓縮引述，省略標記本版補上（三審 QA）**：原文 `:1597-1599` 尚有兩處本處未引——
SSOT 括號內的「**，hook 側為再匯出**」，以及該項末句「**既有鎖
`test_a_spend_limit_escalates_instead_of_waiting` 不得因本節而鬆掉**」（後者本 ADR 在
下方 L4-b 的表格裡另有引用）。⇒ 上段引文應讀作
「……`LIMIT_SPEND`**……**）——等到天荒地老都不會回來，只有人去提額**……**」，
**不是**逐字全文；逐字全文一律回頭讀 PRD `:1596-1600`。

🔴 **PRD 那句寫的是「兩個例外」，而上一版只引了第一個（二審 SA non-blocking 承接）**。
第二個逐字在 `:1600`〔實讀〕：「2. 逐字稿判定『工作已結束』（自我解除門檻成立，見
R-4.5.10-3）——**那是正常下班**。」⇒ **一句劃界**：那一格**不在 L4 的射程內**，因為它
不是「解不出 reset 時刻」——它是**根本沒有工作要續**。L0~L4 階梯回答的問題是「該等哪一個
reset」，而自我解除回答的是「還要不要等」；兩者是**前後兩個問題**，前者在後者答「不要」時
連求值都不該發生。**實作要求**：階梯的入口必須先問一次自我解除門檻，成立則
**直接 escalate（正常下班的那一句話）並且不進 L0~L4**，不得走 L4-a 的「掛回巡邏」
（掛回去等於把一個已經下班的 session 排成明天早上再叫人）。⇒ 本 ADR 不重述該門檻的
判準與常數（家＝PRD R-4.5.10-3 指名的 `sentinel_lifecycle` 那一側），只登記這條界線。

故：

| 臂 | 觸發條件 | 動作 | rc | 為什麼不能與另一臂合流 |
| --- | --- | --- | --- | --- |
| **L4-a**｜解不出／死窗／太遠 | F2 或 F3 紅，或 L1~L3 全數落空，且**不是**下一列 | 拒絕武裝 ＋ **確保哨兵在武裝著**（掛回零成本巡邏；判準＝§6 A6） | ≠0 | 這一臂的前提是「reset 存在、只是我們現在不知道它是幾點」⇒ 零成本巡邏有機會發現它 |
| **L4-b**｜**沒有 reset 可以等** | `reset_branch()` == `escalate`（`resets_at` 不可解析），且撞線類別是 `LIMIT_SPEND`（月度支出上限） | **escalate（叫人）**，**不得**掛回巡邏 | ≠0 | 巡邏永遠不會發現一個不存在的 reset ⇒ 掛回巡邏＝安靜地永眠。既有鎖 `test_a_spend_limit_escalates_instead_of_waiting`（PRD `:1599` 具名）**不得因本 ADR 鬆掉** |

🔴 **兩臂的訊息必須不同字串**（同 `quota_messages.reset_horizon_phrase()` 的既有紀律：
三支分支字串必須彼此不同，否則「不排程」與「排不了」外觀相同）。
L4-a 與 §4 的存活監測直接接上；L4-b 不接。

🔴 **與 `PRD_Amendment_R108_Pacing` §2.3 M197-4 ⑥ 的同畫面互斥（二審 Architect N6 承接；
兩份文件一句對一句、不留兩個家）**：那一批的 ⑥ 會在同一種姿態下印「**這道節流會在
`<時刻>` 自己解除**」（來源＝遙測端點的 `Retry-After`），而 L4-a 印的是「**解不出 reset
時刻、拒絕武裝**」。兩句擺在同一個畫面上會讀成互相否定。**劃界（兩把尺，不是同一把）**：
⑥ 量的是**遙測通道**的速率限制（metering 端點自己被限流，與模型額度無關）；
L4-a 量的是**模型額度**的 reset 時刻（`resets_at` → `halt_resets_at()`）。⇒ 兩條規範性要求：
① **兩者的字面必須各自具名自己量的是哪一把尺**（例：「遙測通道限流」vs「額度視窗」），
不得共用「節流」這個中性詞；② 🔴 **`Decision.retry_after` 不得成為 L0~L4 的取值來源**
——那會把一個 60 秒的遙測退避變成一支排程，而它連 F3 的視界都不該進。

### 2.5 機制約束：改排程時刻的唯一安全路徑

🔴 **本節是設計約束，不是操作建議** —— 它必須寫進實作的註解與測試，否則下一個人一定重踩。

R107 實測三次（`R107_RESUME.md:107-109`）：`schtasks /change`（空密碼）與
`Set-ScheduledTask -Trigger` **都會把 Interactive principal 的 `NextRunTime` 弄空**。
後果不是「改失敗」而是**改成功了但憑證沒了** —— 而本 repo 全部「已排程」宣稱的憑證
就是 `NextRunTime` 這個值（根 CLAUDE.md〈反事後諸葛〉、ADR-XPLAT-004 §6）
⇒ 一個 mutate 動作可以在不報錯的情況下把整套取證體系變成假紅（或更糟，被人加個
`|| true` 繞過去變成假綠）。

**約束（規範性）**：

> **任何要改變既有排程觸發時刻的動作，一律走「`unregister` → planner 重註冊」，
> 禁止任何形式的 in-place mutate（`schtasks /change`、`Set-ScheduledTask -Trigger`、
> `Set-ScheduledTask -Settings` 等）。**

它為什麼成立而不是麻煩：planner 的註冊腳本本來就是 `Register-ScheduledTask @common -Force`
（`:767-779`〔實讀〕），對同名工作是**整支重建**語意（Trigger＋Principal＋Settings 一起換）
⇒ 重註冊路徑天生就把 Principal 一起帶回去，而 mutate 路徑只換 Trigger、把 Principal
留在一個 `NextRunTime` 算不出來的狀態。**「重建比修改安全」在這裡不是風格偏好，是實測。**

附帶：該註冊腳本有一條 S4U → Interactive 的 catch 回退（`:777-779`〔實讀〕，
非提權時是唯一能成立的路），而**回退之後正是本約束所指的那種 principal** ⇒
本約束的射程涵蓋哨兵與續航兩支工作，不能只寫在其中一支的註解裡。

## 3. 缺陷②：headless 續跑窗口許可層無 Edit／Write（安全 vs 自動化）

### 3.1 現況（實讀）

`choose_resume_route()` 產出的 argv 是（`tools/session_resume_planner.py:1134-1136,1141-1143`〔實讀〕）：

```
[claude, "-p", "-r", <session_id>, "<prompt>", "--add-dir", <plan.parent>]   # RESUME
[claude, "-p",                     "<prompt>", "--add-dir", <plan.parent>]   # FRESH 降級
```

非互動的 `-p` 模式沒有人可以按「同意」，需要許可的工具呼叫一律得不到授權。
**這就是 R107 說的「喚醒後空轉」的機制**。

```bash
       --allowed-tools "Read,Edit,Write,Bash(npm test:*),Bash(git status)" \
```

「**只有**在容器／VM 等隔離環境且**使用者明確設定** `ALLOW_PERMISSION_BYPASS=true` 時，
才可使用完全跳過權限的旗標」（`:1104` 逐字，含「使用者明確設定」**七字**——

但一個數不對的逐字宣稱會讓抽驗者對整段引述失去信任。該七字正是那條例外的**唯一**授權要件。
附帶：PRD 原文那七字**沒有**粗體，本 ADR 上方的粗體是本文件自己加的強調）。

⇒ **② 這件事的性質要分兩塊講，不能一句「不需修憲」帶過**（判例有**兩臂**，
`CrossPlatform_R100_Scan_Findings.md:195`〔實讀〕逐字：「依憲法（PRD 為最高法）：
『**實作沒照 PRD 做』修實作、『PRD 與實測不符』才修憲**」）：

| 塊 | 事實 | 落哪一臂 | 處置 |
| --- | --- | --- | --- |

### 3.4 建議案：**B**（`--permission-mode acceptEdits`），並**明確不推 C／D**

三條理由，每一條都可以獨立成立：

1. **B 的增量剛好等於缺陷的定義。** ② 的字面是「許可層**無 Edit／Write**」；
   `acceptEdits` 打開的正是 Edit／Write，一格不多。**最小增量原則**在安全裁決上不是懶惰，
   是可審計性：事後要回答「這一跑多了什麼權限」只有一個答案。
2. **既有三道防線與 B 的新增面正交互補，不重疊也不留縫。** B 開的是「寫檔」，
   三道防線守的是「動 git 歷史」「毀滅工作樹」「治理檔」——
   ⇒ 續跑那一跑可以改生產碼與文件、**不能** commit／push、**不能** 毀掉未提交的工作、
   **不能** 改治理面。這正是 ADR-XPLAT-004 §2.5「昂貴的那部分兩種模式都完成；
   被關住的只有最後那個模型回合」的自然延伸：現在被關住的是**最後那個 commit**，
   而 commit 本來就是掌舵者在場才做的事。
3. **C 的白名單會製造第二套語彙。** repo 既有的授權判準全部長在**指令字串形態**上
   （`unattended_authz.GIT_WRITE_RE`／`block_destructive_git` 的形態列舉）；
   `--allowedTools "Bash(git status)"` 是**工具名＋glob**的另一套語彙。
   兩套並存時，「哪一個說了算」需要第三份知識來回答——那正是本 repo 判過的
   「同一份知識兩個家」。**若掌舵者要更窄，正確的收法是往既有那一套加形態，不是開第二套。**
   （D 更糟，見矩陣的紅字。）

**建議案的實作約束（規範性，缺一則等於沒修）**：

```
argv = [claude, "-p", ("-r", sid)?, "<prompt>", "--permission-mode", "acceptEdits",
        "--add-dir", <plan.parent>]
```

- 🔴 **`--permission-mode` 取單值，可放在 prompt 之後**；但 `--add-dir` 與（若日後採 C 的）
  `--allowedTools` 都是**變長參數**〔本輪實測〕⇒ **prompt 必須排在所有變長旗標之前**。
  ADR-XPLAT-004 §5 E10 已為此付過一次代價（五段稽核痕跡全綠、那一跑什麼都沒做）。
  現有回歸鎖 `test_the_variadic_add_dir_does_not_swallow_the_prompt` 必須**擴面**到新旗標。
- 授權選擇必須**進狀態塊並進稽核痕跡**（`route_chosen` 那一行，`:1163`〔實讀〕已有先例）：
  「這一跑帶了什麼權限」事後必須查得到，不能只存在於 argv。
- 授權必須有**關掉的出口**，且出口是模型碰不到的：沿用既有 `AUTOSDD_RESUME_OFF`
  的形狀（環境變數，須在啟動前設），不新增旗標。
- 🔴 **本設計刻意不帶 `--allowed-tools`，而 PRD `:1099` 的建議形式帶著它**〔實讀〕
  ⇒ 這是本 ADR **自己新增的第三處 PRD↔實作歧異**（理由＝§3.4 第 3 條「第二套語彙」）。
  它**必須**進裁決清單（§3.5 Q4 第 ③ 項）：不進去的話，掌舵者會在一份不完整的清單上
  拍板，而下一輪稽核會把它當新發現重開（DEF-200-206 族的形狀）。
  **「設計上刻意不做」不等於「不必裁決」**——它動到的是 PRD 的建議條文。

### 3.5 掌舵者裁決清單（白話，非術語堆疊）

> 這七題請直接回「可以／不可以／改成 X」，不需要讀完上面的矩陣。
> （Q1~Q3＝授權面；Q4＝PRD 對齊；Q5＝Mac 射程；Q6＝③ 的誠實劃界要不要接受；
> **Q7＝R108 修復包 #4 新增：你機器上那個 `AUTOSDD_RESUME_OFF=1` 的去留**，

- **Q1｜要不要讓半夜自動醒來的那一跑「能改檔案」？**
  現在它醒了也只能看不能動，所以每次都白醒。開了之後它能改程式碼和文件，
  但**仍然不能 commit、不能 push、不能砍掉你沒存的東西、不能改治理規則**（這四樣有機械鎖）。
  → 建議：**開**。

- **Q2｜開了之後，最壞的情況你能接受嗎？**
  最壞是：它改了一批檔案、改錯了，而你早上起來才看到。
  補救成本＝`git diff` 看一遍、`git restore` 還原（人手動，不受無人看管鎖限制）。
  它**不會**把你的東西弄不見（未提交的工作有 `block_destructive_git.py` 守著）。
  → 需要你確認這個最壞情況可接受。

- **Q3｜要不要再多綁一層「只准用這幾個工具」的白名單？**
  可以更安全，代價是多維護一份清單，而且那份清單跟我們現有的鎖是兩套寫法，
  日後容易對不上（歷史上這種「兩個家」出過好幾次事）。
  → 建議：**先不要**，先用 Q1 那一層看半年。

- **Q5｜Mac 那一側要不要一起做？**
  Mac 的排程器（launchd）跟 Windows 不同，它**從不告訴你下次幾點跑**，
  而且**睡著的 Mac 不會被叫醒**（這是已知邊界，不是待修 bug）。
  → 需要你裁決：Mac 側是「一起做到能驗證的程度」還是「明說做不到、先不做」。

- **Q6｜③ 這個修法**（哨兵死了自己救回來）**只在「你人還在用 Claude Code」時有效。
  立案那一晚正是沒人在用——所以那一晚的病，這個修法治不了。你接受嗎？**
  白話講清楚為什麼：偵測哨兵死亡的那個東西，掛在「你每按一次工具」上。你不在，
  它就不跑。**額度用完之後更糟**——那時整個 session 連工具呼叫都發不出去
  （這是 API 層的失敗，不是工具失敗；`ADR-XPLAT-004:114` 逐字：
  「Pre/PostToolUse 一次都不會被叫到」），所以連「你還在鍵盤前」都救不了那一段。
  它**真的**治好的是另一件事：以前哨兵一死就**永久**失明（stamp 還在 ⇒ 每次都回
  `latched` ⇒ 這台機器再也不會重新武裝，直到你開新 session）；改完之後，
  **你下次動手的那一刻它就會自己修好**。也就是把「永久失明」換成「失明到你下次動手」。
  → 需要你裁決三選一：
  (a) **接受這個劃界**（本 ADR 的建議：先把永久失明消掉，無人期間仍只有你一鍵現查）；
  (b) 要求**另尋跨基質事件源**（例：作業系統層的登入／喚醒事件、路由器級心跳、
      第二台機器——都是新的移動零件，且各自有自己的「它死了誰知道」問題）；
  (c) 兩者都不做，把 ③ 整項退回。
  🔴 這一題**不是**技術細節：不裁決的話，§4 會被讀成「哨兵死亡已解決」，
  而那是本 ADR 一審被打回的原因之一。

- **Q7｜你電腦裡設著一個「永不自動續跑」的開關，要留還是要拆？**（🔴 **R108 修復包 #4
  新增；它與 Q1／Q2 是同一題的兩面，不能各自回答**）
  白話講：你的 Windows **使用者層環境變數**裡設著 `AUTOSDD_RESUME_OFF=1`
  〔本輪親驗三層值：`User=1`／`Machine=`（空）／行程＝`1`；**不在 repo 裡**，
  所以換一台機器 clone 下來不會有它〕。後果是**每一支**哨兵武裝時都被烙上
  `allow_resume:false`（傳遞鏈＝§1 修訂段），於是半夜「探測到額度真的回來了」那一刻，
  它走的是**不續跑**那條路——而那條路順手把排程刪掉、唯一的告知寫給一個不存在的視窗
  （§4.0 的 D1~D4）。**8/28 那次哨兵死亡就是這麼死的，而且現在還是這個狀態。**
  → 兩種裁決，各自的落地義務**不同**，請直接選一個：
  (a) **開放受控續跑**（＝Q1 回「開」的自然延伸）：R109 落地時**必須同時**
      ① 移除／改設那個 User 層變數（否則 ② 的 `--permission-mode acceptEdits` 開了也沒用，
      那一跑**根本不會發生**）。🔴 **這一格的射程本版說清楚（三審 Architect A5）：清的是
      「User 層那個值」，不是那個機制** —— `RESUME_OFF_ENV = "AUTOSDD_RESUME_OFF"`
      （`tools/session_resume_planner.py:277`〔實讀〕）這個逃生口**語意一個字不動**、
      不改名、不刪、不改預設方向（不傳＝允許續跑、傳了＝不續跑）。⇒ 本項要做的是
      **把那台機器上的持久環境值移走**（或改成只在需要時於行程層設），使逃生口回到
      「刻意時才生效」的狀態；**不是**把逃生口拿掉（拿掉會讓「我今晚不要它自己動」
      這個合法需求沒有出口，那是本 repo 反覆判過的「擋到讓人無法工作的守衛會被
      整個關掉」形態）；② 修 **D1~D4** 四筆。
      🔴 **這一格是 ② 驗收的隱性前提**：不處理它，B1~B5 全綠也只證明「argv 帶了旗標」，
      **證不到「那一跑真的做了事」**——而後者正是缺陷② 的定義。
  (b) **維持唯讀**（＝Q1 回「不開」）：那個變數留著，**但至少要修 D2／D4**，
      理由是「決定不續跑」與「靜默地什麼都沒發生」現在**外觀相同**：
      D2 讓那個決定**出聲**（走 `escalation.alert(..., loud=True)` 那條既有的桌面告警路，
      不是 `print()`）、D4 讓它**可稽核**（清 stamp ⇒ 「stamp 在但工作不在」唯一代表外部刪除）。
      🔴 **(b) 不是「什麼都不做」**：不修 D2／D4 的話，每一次「不續跑」都是一次無聲失蹤。
  🔴 **本 ADR 不裁決那個變數該不該存在**（它可能正是 R107 註 #2「headless 續跑窗口許可層
  不足」的手動應對——取證報告 §5-6 明文不裁決此事），只指出：**它的去留決定了
  ①③ 落地後喚醒鏈能不能真的閉環**，因此不能留在裁決清單外。

### 3.6 跨平台：兩側的授權載體不同，不得互相推論

| | Windows（schtasks） | macOS（launchd） |
| --- | --- | --- |
| 排程載體 | `Register-ScheduledTask -Force`，S4U 失敗回退 InteractiveToken（`:767-779`〔實讀〕） | `StartInterval`／`StartCalendarInterval` plist（`tools/lib/schedule_backend.py`，ADR-XPLAT-004 §2.9 標記 R83 落地） |
| 「已武裝」的憑證 | **`NextRunTime` 這個值**（rc 不算數） | **`launchctl print` 的 rc**（不存在時 113）＋ plist 回讀。launchd **從不**報下次幾點跑（`tools/lib/quota_messages.py:108-110`〔實讀〕明載） |
| 續跑那一跑的授權 | 走 argv 旗標（本節 B 案），與載體無關 | **同一條 argv**——授權面是 CLI 的事，兩平台共用；**不得**因為載體不同就寫兩套授權邏輯 |
| 環境繼承 | Action 帶 `-WorkingDirectory`，`_run_resume` 另帶 `cwd=_REPO_ROOT`（兩層都要，`:1167-1173`〔實讀〕） | 同左，plist 的 `WorkingDirectory` 與 `cwd=` 同樣是兩件事 |
| 已知邊界 | — | 🔴 **睡著的 Mac 不會被喚醒**（根 CLAUDE.md〈mac 已知邊界〉：`pmset repeat` 需 sudo、本專案刻意不碰）。交付的是「醒著必動作＋失效可偵測」，**不是**「必然喚醒」。**這一條不得寫成待修 bug** |

🔴 **設計結論**：授權面（②）**兩平台同一份 argv**；排程面（①③）**兩平台各一條憑證規則**。
把這兩件事混在一起講，就是 ADR-XPLAT-004 §2.9 那次「憑證是真的、指路是假的」的復發形狀。

### 4.2 根因：自癒住在**它要救的那個東西裡面**（循環依賴）

逐環實讀，三條再武裝路徑各自的觸發條件：

| 路徑 | 觸發者 | 哨兵已死時還成立嗎 |
| --- | --- | --- |
| `_heal_armed_drift()` | `patrol_housekeeping()`（`quota_escalation.py:335`），而它**只**被 `_sentinel_tick()` 呼叫（`tools/session_resume_planner.py:1422`） | ❌ **結構上不可能**——哨兵死了就不會 tick，不 tick 就不會自癒。**自癒是哨兵的一個功能，不是哨兵的看護者** |
| PostToolUse `maybe_arm()` | `.claude/hooks/context_budget_guard.py:820` | ❌ `maybe_arm()` 第一件事是 `if marker.exists(): return "latched"`（`tools/lib/sentinel_lifecycle_arm.py:170-172`）——**stamp 還在，所以它認為已經武裝過了**。R107 那一窗正是這個狀態：stamp 在、工作沒了、每次工具呼叫都回 `latched` |
| SessionStart `--arm-sentinel`（＋`clear_arm_latch()`，`:148-158`） | 開新 session／`claude -r` | ⚠️ 成立，但要**人先回來**——而「人不在」正是整套續航存在的理由 |
| `--pace` / `--check` 的 `liveness_line()`（`tools/session_resume_planner.py:1487,1517`） | **人手動下指令** | ⚠️ 成立且**它就是 R107 那次真的報出來的東西**（`R107_RESUME.md:115-117` 逐字「planner 自診斷『哨兵已死、喚醒鏈斷線』」）。但它是 **pull**，不會自己找上你 |

🔴 **一句話根因**：**三條路都要求「有人／有東西還活著」，而哨兵死亡的定義就是那個東西不在了。**
`latched` 那一格尤其貴——它把「已經武裝過」與「現在還武裝著」當成同一件事，
而這正是本 repo 反覆判過的「量不到 ≠ 量到零」的鏡像：**「曾經有 ≠ 現在有」**。

**取證設計**：新增一支**唯讀探針**（`tools/probe/` 下，不接任何閘門），在被要求驗屍時：

🔴 **本步驟清單於 R108 修復包 #4 依實機取證改寫**（上一版的順序與假設有兩處被證偽，

1. **先讀 `%TEMP%` 的 `autosdd_resume_log_*.jsonl`（第一順位）**：哨兵四分支決策

2. **查排程器事件日誌（主通道，不再是候選）**。Windows＝
   `Get-WinEvent -LogName 'Microsoft-Windows-TaskScheduler/Operational'`
   （🔴 **「該日誌預設可能未啟用」在本機證偽**：實測 `IsEnabled=True`、`LogMode=Circular`、

   只是**預期值要改**。未啟用時回「量不到」而**不得**回「沒有刪除事件」。
   需要開啟時的指令＝`wevtutil set-log Microsoft-Windows-TaskScheduler/Operational /enabled:true`，

   mac 側對等物＝`log show --predicate 'subsystem == "com.apple.xpc.launchd"'`（**仍未實測**）。
3. **在動用 Security 4698/4699 這條替代路之前，先取「量不到」的憑證**：
   必須先 `Get-WinEvent -ListLog 'Security'`（F3：非提權查 4698/4699 拋的訊息與「真無事件」
   **逐字相同**）；`System32\Tasks` 只准**以完整工作名點查**，禁用枚舉（F4：枚舉是
   fail-open 假陰性）；並排除 `AutoSDD_Sentinel_UNITTEST_GHOST` 的噪音（F6）。
4. 全部皆量不到 ⇒ **明說「死因不可知」**，並在下一次武裝時記下更多欄位（見下，含 C11'
   的 `allow_resume`）。

🔴 **順帶要修的一格**：`_abort_and_unregister()`（`:1212-1217`〔實讀〕）與哨兵的
`disarm` 分支都會刪掉工作，但**armed stamp 沒有被同步清掉** ⇒ 事後看到的狀態
（stamp 在、工作不在）與「被外部刪除」**完全相同**。這是一個**可以零成本消除的歸因盲區**：
自己走的時候順手刪 stamp，此後「stamp 在但工作不在」就**唯一地**代表外部刪除。
**這一格建議與 §4.4 同輪落地**——它讓 §4.4 的判準從「有噪音」變成「無噪音」。

🔴 **R108 修訂（F5）：這一格實測成立，價值比上一版說的更高，且射程要補第三條臂。**
本輪實測 stamp mtime＝09:03:02、工作死於 14:02:09〔取證報告 §2.4(a)〕⇒ 盲區確實存在。
修掉之後「stamp 在但工作不在」就**唯一地**代表外部刪除——而本案**不是**外部刪除，
所以這一格會把歸因成本從「三通道交叉比對」降到「一眼可辨」⇒ **建議提前，不要等 §4.4 同輪**。
🔴 **射程**：上一版只點名 `_abort_and_unregister()` 與哨兵的 `disarm` 分支，
**漏了本案真正走的那條**——`_resume_tick` 的 `quota_back_no_resume` 臂
（`:1308-1314`〔本輪實讀〕，它同樣 `_schtasks_remove()` 卻同樣不清 stamp）
⇒ §6 的 **C10'** 就是這條臂的擴面判準。

### 4.4 「誰來監測監測者」：**縮小失明窗口**的跨基質互監（不是消除它）

🔴 **本節標題與定位在 R108 一審後改寫**。上一版把 L-a 寫成「**主力**」，讀起來像
「哨兵死亡已解決」，而 §5-4 同時承認它蓋不到無人期間 ⇒ **正文與劃界節互相否定**。
本節現在的宣稱是可辯護的那一個，且**比上一版小**：

> **本設計交付的是「把永久失明換成有界失明」，不是「哨兵死亡可偵測」。**
> DEF-200-231③ 的**立案窗口**（2026-08-28 12:00~14:00，無人、且有工作要續）
> **在本設計落地後仍然沒有機械覆蓋**——那一段的看護者只有 L-c（人）。

**設計約束（來自本輪任務書，也是本 ADR 認同的）**：不得引入第二個**同型**單點。
一支「監視哨兵的 schtasks 工作」與哨兵**同基質、同失效模式**（同一個排程器、
同一個清理腳本、同一次服務故障會一起帶走）⇒ 它不減少單點，只是把單點換了個名字。

**建議設計（三層，基質各不相同）**：

```
L-a  互動 session（PostToolUse hook）——**機會性自癒**，基質＝正在跑的 claude 行程
     （🔴 定位不是「主力」也不是「監測」：它不會在哨兵死掉的那一刻告訴任何人，
       它只保證「下一次有人動手時，這台機器會自己把哨兵掛回去」）
     修法：把 maybe_arm() 的 `latched` 那一格，從「有 stamp 就不管」
           改成「有 stamp ⇒ 節流地現查一次排程器；查得到就安靜，查不到就重新武裝」。
     · 它真正消除的缺陷（**這才是它的價值，一句話**）：
       `latched` 是一個**永久**閂鎖——stamp 在、工作沒了之後，這台機器**再也不會**
       重新武裝，直到有人開新 session（SessionStart 的 clear_arm_latch()）。
       R107 那一窗逐字就是這個狀態。改完之後失明窗口從「永久」變成
       「到下一次工具呼叫為止」。**有界，而且界由使用者的作息決定、不由 bug 決定。**
     · 判準本體已存在：armed_but_missing()（不必新寫）
     · 🔴 成本閘是必要的：現查要 spawn powershell.exe，不能每次 PostToolUse 都跑。
       用既有的 quota_ledger.claim_once(<stamp>, <interval>) 形狀節流
       （🔴 該判準的**家**＝tools/lib/quota_ledger.py:177〔實讀〕；
         tools/lib/quota_gate.py:509,567 是兩處**消費端**先例〔實讀〕，不是它的家），
       週期取 SENTINEL_INTERVAL_SECONDS 同級。

L-b  哨兵自己（既有 _heal_armed_drift）——**保留不動**
     它治的是「續航排程漂移」，不是「哨兵自己漂移」；本 ADR 不動它的射程。

L-c  掌舵者一鍵現查——**遞迴的終點**
     `python tools/session_resume_planner.py --pace`（liveness_line 已接在裡面）
     ＋ `Get-ScheduledTask | Where-Object TaskName -like 'AutoSDD_*' | Get-ScheduledTaskInfo`
     這一層**刻意是人**：問「watchdog 死了誰知道」的正確答案不是再加一層，
     而是「**任何一層都死光時，掌舵者用一個指令就能問出來**」。
     ⇒ 本 ADR 要求：這兩條指令必須進根 CLAUDE.md 的〈現查指令速查表〉（已在表內，
        本項只需確認 --pace 那一列的說明有提到它會報哨兵活性）。
```

**為什麼 L-a 值得做**（三條；🔴 上一版的論證 1 已被一審證偽，本輪改寫）：

1. **它的觸發源與哨兵的失效原因無關——但這只在一條很窄的軸上成立，必須把界說清楚。**
   哨兵死於排程器面的事；PostToolUse 死於「沒有人在發工具呼叫」。兩者**成因**確實不相交。
   🔴 **上一版接著寫的那半句是假的**：原文寫「後者發生時，哨兵是否活著暫時也不重要
   （沒有工作要續）」——**立案那一晚正好反例**：沒有人在用，**而且有工作要續**
   （那正是續航協定存在的全部理由）。故本 ADR 撤回那半句，改為劃出真正的界：
   > **劃界軸＝「額度耗盡使 session 發不出工具呼叫」之後。**
   > 那一刻起 L-a **結構上**無法觸發：額度耗盡是 **API 層**失敗，不是工具呼叫失敗
   > （`ADR-XPLAT-004:114`〔實讀〕逐字「PreToolUse／PostToolUse 一次都不會被叫到」；
   > 同檔 `:363-364`〔實讀〕逐字「解除後結構上無人 re-arm：重新武裝依賴該 session 的
   > PostToolUse，**而撞線後 session 發不出任何工具呼叫**」）。
   ⇒ L-a 的有效射程是「**撞線之前**、有人在動手」那一段；
   **撞線之後與無人期間，看護者只有 L-c（人）**。
2. **它不新增任何持久物**。沒有新排程、沒有新常駐行程、沒有新檔案格式；
   只改一個 early-return 的條件 ＋ 借一個既有節流器。
3. **它有紅綠可證的判準**：`latched` 那一格的行為改變，可以用注入的 `jobs` 清單
   （`[]` / `[task]` / `None`）三態直接驗——而 `None`（量不到）**必須**走「不動作」，
   這一條已由 `armed_but_missing()` 的語意保證（`jobs is None` 不算漂移）。

**誠實記下 L-a 的代價**：它讓 PostToolUse 這條**每次工具呼叫都會跑**的路徑，
每 N 分鐘多一次 `powershell.exe` 外呼。ADR-XPLAT-004 §4 逐字寫過
「不得讓每一次工具呼叫都碰網路」——本設計不碰網路（只查本機排程器），
但**同一條理由的精神適用**：節流器不是可選項，是這個方案能不能成立的前提。
若複審認為節流器不足以壓住成本，退路是把 L-a 掛在**更稀疏的事件**上
（例如只在 `Stop` 事件），而不是放棄互監改回第二支排程。

🔴 **本節結論（與 §5-4、§6 缺陷③、§3.5 Q6 三處必須逐字一致）**：
**無人期間的哨兵死亡，在本設計下仍然不可偵測——這是已知未解，不是已解。**
要不要接受這個劃界（或另尋跨基質事件源）是**裁決問題**，見 Q6。
本節**不主張**任何形式的「哨兵死亡已解決」。

### 4.5 憑證紀律（規範性）

> **任何「哨兵已武裝／續航已排程」的宣稱，Windows 側的憑證是
> `Get-ScheduledTask -TaskName '<名稱>' | Get-ScheduledTaskInfo` 回出的
> `NextRunTime` 這個「值」，不是任何指令的 rc。**

理由已在 repo 內三處獨立記載，本 ADR 只是把它綁到本項的新程式上：
`Get-ScheduledTask` 對**不存在的工作回 rc=0**（非終止錯誤，根 CLAUDE.md〈反事後諸葛〉；
ADR-XPLAT-004 §6；`next_run_time()` 的實作註解 `:414-422`〔實讀〕）。

三條具體要求：

1. L-a 的重新武裝路徑**必須**走既有的 `--arm-sentinel`（它自帶 `NextRunTime` 憑證閘），
   **不得**自己拼一段 `Register-ScheduledTask` 繞過憑證閘。
2. 重新武裝的成敗**都要**落痕跡，且事件名與既有家族互異
   （沿用 `sentinel_armed_drift_healed` 的既有紀律，`quota_escalation.py:308-310`〔實讀〕）。
3. mac 側**不得**沿用 `NextRunTime` 這個鍵名——launchd 從不提供它，
   憑證走 `CRED_KEY_LAUNCHD`（`relay_problems()` `:469-481`〔實讀〕已把兩個鍵分開，
   本項不得把它們併回去）。

   本身可能就是錯的／已漂移，本設計沒有任何辦法驗證它——只能保證「我們沒有自己編一個」。
   （字面仍用 005 §2.7 的 `endpoint-authoritative`：**權威指的是「誰說的」，
   不是「一定對」**；快取只是轉手，不改變出處。）
3. **②開了 `acceptEdits` 之後，那一跑寫出的內容沒有任何機械物在審。**
   三道防線守的是 git 與治理面，**不守「改得對不對」**。這一格結構上只能靠
   「重啟後第一件事是重驗」（任務書第 4 節既有禁令）——而那是散文，對 print 模式的模型
   零攔阻力（ADR-XPLAT-004 §2.5 已記載過同一句）。
4. 🔴 **③ 蓋不到 DEF-200-231③ 自己的立案窗口——這一格是已知未解，不是已解。**
   L-a 只在「有人在發工具呼叫」時成立，而**額度耗盡之後連那個都沒有**
   （API 層失敗，`ADR-XPLAT-004:114`／`:363-364`）。⇒ **無人期間的哨兵死亡在本設計下
   仍然不可偵測**；那一段的看護者只剩 L-c（人）。本設計交付的是「永久失明 → 有界失明」

5. **`%TEMP%` 仍是地板的單點失效，但後果只在一半的路上**（ADR-XPLAT-004 §7-3 未變；
   🔴 上一版把後果寫大了，本輪照實改）。armed stamp 與任務書都住在那裡，被清掉時：
   - **武裝那一路不會退化**：`maybe_arm()` 的第一格是 `if marker.exists(): return "latched"`
     （`tools/lib/sentinel_lifecycle_arm.py:170-172`〔實讀〕）⇒ stamp 不在時它**往下走**、
     照常評估門檻並重新武裝（`Force=$true` 冪等）。這一路是**自癒**，不是失效。
   - **真正靜默的是回報那一路**：`liveness_problem()` 的 `if not stamped: return ""`
     （`tools/lib/sentinel_lifecycle.py:122-123`〔實讀〕）⇒ stamp 被清掉之後，

6. ~~**死因取證的排程器日誌那一路完全未實測。**~~ 🔴 **本項已由 R108 修復包 #4 承接，
   照實改寫**（原文保留在刪除線內，供對照）：該路已**實測**——`IsEnabled=True`、

   ② mac 側對等物（`log show … com.apple.xpc.launchd`）**仍然未實測**；
   ③ 探針必須把「量不到」與「沒有事件」分開回報——而 R108 實測發現這件事**比原文說的更難**：
   非提權查 Security 4698/4699 時，**rc 與訊息都與真無事件同形**（F3），

與本節「①③ 同輪、② 待裁決」的分批**不一致**。⇒ **①③ 落地那一輪，把 ② 拆成一筆新列**
（`DEF-200-` 家族新號，狀態＝待裁決／blocked-on-decision，指向 §3.5 Q1~Q3），
**原列收斂為索引列**（≤700 bytes，指向本 ADR 與新列；詳情不進帳本，走具名證據檔）。
不這麼做的話，①③ 綠了而 ② 沒動時，原列既不能結案也不能說明卡在哪。

**順序的理由**：② 是三者中唯一需要**人的安全裁決**的（另兩者是純技術缺陷），
把它排在前面會讓整個 R108 卡在等裁決；而 ①③ 落地之後，即使 ② 還沒開，
喚醒鏈至少「醒在對的時刻、且醒得來」——那已經比今天好，而且 **② 的價值完全依賴 ①③ 先成立**
（醒在錯的時刻的話，給它再多權限也沒用）。

🔴 **⓿ 與「①③ 排 R108 本輪」不衝突，但順序不可調換**：⓿ 是同一輪之內的**第一步**
（單人窗口、純減法、跑完全套後才開 ①），不是另一輪的工作。
**若 ⓿ 當輪做不完，① 就必須延後**——沒有餘裕時硬寫的結果是破線阻塞，
而那會把整輪的閘門染紅，比延後貴得多。**規模估計裡沒有「擠一擠」這個選項。**
🔴 **③ 不在這條「⓿ 做不完就延後」的射程內（二審 SD-N2 承接）**：它的增量全落在
餘裕 219~326 的 lib 檔上，`.claude/hooks/context_budget_guard.py` 零增量（見 §7.0 表）。
⇒ **⓿ 當輪做不完時，③ 仍可照排**；只有 ① 必須跟著延。這一格上一版寫錯的代價是
「把一個沒有阻塞的項綁在一個硬前置上」，那會讓整輪的可交付面莫名縮小一項。
