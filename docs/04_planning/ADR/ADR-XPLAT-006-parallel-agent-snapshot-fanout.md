## 1. 脈絡：問題不是一個，是三個獨立的軸

舵手把工作切成 N 個包同時派給 N 個 subagent，全部在同一棵工作樹寫檔，包與包的檔案互斥只靠任務書散文約定。已實際發生五類失效。三方獨立分析後**一致**同意它們分屬三個互相獨立的軸——這是本 ADR 的地基，因為每一軸需要不同的機制：

| 軸 | 本質 | 失效 | 本 ADR 對它做到什麼 |
|---|---|---|---|
| **A 爆炸半徑** | 一個 agent 的毀滅性動作波及他人 | 事故：`git stash -q -u --keep-index` 清空 16 改檔＋4 未追蹤檔 | **本 ADR 不處理**。它由指令阻斷器負責（§3 爭點 10） |
| **B 量測穩定性** | rc／掃描結果是「別人鍵盤的函數」 | 同指令一紅一綠；驗證者結構上不能跑全套；收到與自己無關的紅 | **只消掉時變成分**（rc 不再隨量測時點漂移），**不消掉跨包內容干擾**。誠實射程見 §2.4 |
| **C 階段共識** | 「我是不是最後一個工作者」無判準 | 收尾重釘紀律至少失守 11 次，留下一連串中途值 | 🔴 **Stage-1-only 之下本 ADR 一項都沒解**（訂正，見 §3 爭點 8） |

🔴 **訂正：上一版此表把「能治它的機制」寫成方案的賣點，而那三格有兩格靠 Stage 2 才成立。**
Stage 2 既已放棄，本表改成「**本 ADR 實際對它做到什麼**」——欄名的改動就是這次降級的全部誠實內容：
本 ADR 現在只認領軸 B 的**一半**（時變成分），軸 A 交給 hook、軸 C 未解。

## 2. 決策

採用 **快照 ＋ 唯讀驗證樹**：以一個**零副作用的快照 commit** 當基準，**只給驗證者／複審者**一棵不會動的樹。
**寫檔包照舊留在共用主樹，不隔離。**

### 2.1 三階段（不是四階段——收斂站整個不存在）

```
Phase 0  SNAPSHOT   整合者把「當前工作樹（含未追蹤檔）」凍結成一個真 commit SNAP 並 tag
Phase 1  VERIFY     驗證／複審包在「拷貝自主樹的唯讀樹」內跑全套；寫檔包照舊在主樹寫
Phase 2  RE-PIN     常數（測試數下限、護欄層行數、基線格）在主樹量
```

🔴 **上一版的 Phase 1 FAN-OUT（寫檔包各開一棵 worktree）與 Phase 2 INTEGRATE（`git diff` → `git apply`）已刪除**，
不是重新編號。刪除的依據是兩筆 blocking：收斂站買到的互斥偵測在**檔案粒度上是假的**（§3 爭點 2），
而它同時是「讓一整族未來的鎖失去立案理由」那段論證的唯一支撐（§6）。
**依據沒了，論證也沒了；不留一個「擱置」的空位，因為那會讓下一輪有人以為它只是還沒做。**

### 2.2 Phase 0 的快照：本 ADR 唯一的新原語

用 git plumbing 搭一個臨時 index，把整棵工作樹（**含未追蹤檔**）寫成一個真 commit：

```bash
export GIT_INDEX_FILE=<repo 之外的臨時路徑>
git read-tree HEAD && git add -A
SNAP=$(git commit-tree "$(git write-tree)" -p "$(git rev-parse HEAD)" -m "SNAPSHOT: <輪次>")
unset GIT_INDEX_FILE
git tag "<輪次>-snap" "$SNAP"
```

【合成輪】在真 repo（27,606 檔）實測：

| 量 | 實測 |
|---|---|
| 牆鐘 | **2.773s** |
| 捕獲的在途工作 | `28 files changed, 4866 insertions(+), 230 deletions(-)`（＝當時全部 28 個髒檔，含未追蹤） |
| 主樹髒檔數 前/後 | 28 / 28（**未動**） |
| HEAD 前/後 | 未移動 |
| stash 堆疊深度 | 0（**不碰共用 stash stack**） |
| 新增 branch | 0 |

它值得存在的理由收斂成三條（原本四條，第四條隨 Stage 2 一起失效）：

- **有保真度**：帶著全部在途成果，包括其他包尚未提交的工作。
- **有可稽核 ref**：`SNAP` 是真 commit，可 tag、可當 `git diff` 的基準。agent 掛掉時成果不會變成「只存在於某個磁碟目錄」。
- **不需要把半套工作 commit 進 main**：`commit-tree` 不移動 HEAD、不建 branch、**不觸發 pre-commit hook**，所以半套的在途工作不必先過閘門。

### 2.3 Phase 1 的載具：**整樹拷貝**，不是 linked worktree

【複審輪】在同一個 APFS 卷上量兩種載具（真實磁碟＝`df -k` 前後差）：

| 載具 | 牆鐘 | 真實磁碟（`df` 前後差） | 帶 `.venv` | `refs/stash` |
|---|---|---|---|---|
| `git worktree add --detach SNAP` | 3.76s | **456 MB** | ❌ 需 `PYTHONPATH`（忘了＝靜默測到主樹） | 共用 |
| `cp -c -R <repo> <scratchpad>/verify-<pkg>` | 7.95s | **18.5 MB**（clonefile 共享區塊） | ✅ | **獨立 `.git`，結構上不可能共用** |

【訂正輪】本檔在真 repo 第一手複現拷貝那一列，四項全部對上：`cp -c -R` rc=0、牆鐘 **8s**、
`df` 真實磁碟增加 **19,588 KB**、`.venv` 在、且拷貝樹的 `git rev-parse --git-common-dir`
指向**它自己**（＝`refs/stash` 真的不共用，不是靠紀律）。

**採整樹拷貝**，三個理由依序遞減：`refs/stash` 結構上不共用（不是靠紀律）、`.venv` 跟著過去所以沒有「忘了帶 `PYTHONPATH` 就靜默測到主樹」這個坑、真實磁碟便宜一個數量級。

🔴 **鐵律三的自問：這在另一個平台是什麼值？**（誠實劃界，缺這段 Windows 讀者會以為也是 18.5 MB）

- `cp -c` 的 `-c` 是 **macOS APFS 的 clonefile**。語意只是「純遞迴拷貝」⇒ Windows 側對應寫法是
  `robocopy` 或 `Copy-Item -Recurse`，而**那邊沒有 clonefile**，真實磁碟就是**全額**。
- 【訂正輪】本檔第一手量到一件會讓上表被誤讀的事：**`du` 看不見 clonefile 共享**。
  64 MB 的合成資料夾，`cp -c -R` 之後 `df` 已用只增加 **8 KB**、而 `du` 仍報 **64M**；
  同一份資料 `cp -R`（不帶 `-c`）則 `df` 增加 **65,540 KB**、`du` 也報 **64M**。
  真 repo 那次拷貝同樣如此：`df` 增加 19,588 KB，而 `du` 報 **750M**。
  ⇒ 🔴 **複審輪引用的 Windows 側「`du` 顯示 758M」因此不是平台差異的證據**——
  同一支指令在 **macOS** 上對同一個 repo 也報 ~750M。那個數字兩邊都一樣，
  它量的是邏輯大小，不是佔碟。真正的結論是**「省碟」只在 APFS 成立**，
  而量它的正確儀器是 `df` 不是 `du`。**任務書引用上表時不得用 `du` 當佔碟證據。**
- 【獨立驗證輪】不採信上一格，自建 64 MB 合成資料重量一次，兩個方向都對上：
  `cp -c -R` → `df` 增加 **0 KB**、`du` 仍報 **64M**；`cp -R`（不帶 `-c`）→ `df` 增加 **65,536 KB**、`du` 也報 **64M**。
  ⇒ 「`du` 看不見 clonefile」成立，「Windows 的 `du` 讀數不是平台差異的證據」這個訂正也成立。
  並另驗那個**結構性**的一句：`cp -c -R` 出來的樹 `git rev-parse --git-common-dir` 回**它自己的** `.git`，
  而同一個 repo 的 linked worktree 回**主樹的** `.git`（絕對路徑）⇒ `refs/stash` 不共用是結構事實，不是紀律。
- ⇒ 任務書寫 Windows 側時必須寫成「**每棵驗證樹全額佔碟**」，並在開樹前檢查餘裕；
  這條也是「同一份知識不要住兩個家」的實例：載具語意寫一次，平台差異寫在它旁邊。

### 2.4 軸 B 的誠實射程（blocking ② 的處置）

上一版寫「軸 B 全解」。**那是假的。** 兩名複審者各自在快照樹與主樹各跑一次根層閘門，
拿到**同一筆**實質失敗（`tools/tests` 的檔數下限已過期）——因為別的包新增了測試檔，
而快照**忠實保存**了那個事實。

【訂正輪】本檔第一手複現同一族，而且是三筆不同的鎖：

| 陳舊的鎖 | 釘死的值（量測當時） | 現查值（量測當時） | 快照能否消解 | 獨立驗證輪重查 |
|---|---|---|---|---|
| `tools/lib/skip_tag_policy.py` 的 `_TREE_FILE_FLOORS`（`tools/tests` 那格） | 46 | **61** | ❌ | 下限已被別包改為 48，而樹**還在長** ⇒ 判準（`floor < actual × TREE_FLOOR_RATIO`，該常數＝0.8）仍成立、**仍紅**。🔴 第二位獨立驗證者把本格原本寫的「樹仍是 61」拿掉：那個數字在他量的時候已經不是 61 了，而本節的第 ① 條結論正是「這一欄天生是時變量、不得被後人當常數引用」——寫在這一欄裡的重查值自己就是反例。現查＝`tree_floor_problems()` 對現行檔數求值 |
| `tools/tests/test_subprocess_encoding_hygiene.py` 的 `tools` 掃描面下限 | 92 | **116** | ❌ | 下限已被別包重釘到 110 ⇒ **已轉綠** |
| `tools/tests/test_check_hooks_liveness.py` 的註冊基線表 | 未含本輪新 hook | 已註冊 | ❌ | 基線表已被別包補上 ⇒ **已轉綠** |

🔴 **最右欄是獨立驗證輪加的，而它本身就是本節的最強證據**（不是勘誤欄）：訂正輪量到那三筆的
**幾十分鐘之內**，其中兩筆已經被別的包各自改掉、一筆的下限值也動了。
⇒ ①「釘死的值」這一欄**天生是時變量**，本檔因此逐欄標明是哪一輪量的，並且**不得**被後人當常數引用；
②「干擾不是被消掉、只是被凍結」這件事在同一輪內就重現了兩次；
③它同時示範了爭點 3 那個「正確處置＝當輪重釘」真的會發生——**而那正好也說明快照為什麼消解不了它**：
它靠的是有人去改 repo 內容，不是靠換一棵樹。

【訂正輪】並在真的拷貝樹內把這個結論釘成可重複的觀測：同一支測試在拷貝樹連跑兩次，
輸出**只差計時字樣**；拷貝樹 vs 主樹則**只差樹根路徑前綴**，實質裁決字串
（`… 掃描檔數 <實測值> 已超過下限 <當時下限> …` 這個形態）**兩邊逐字相同**
⇒ 干擾確實整份被搬進了驗證樹，而它在那裡是**可重現**的。
🔴 **這裡刻意寫成形態而不是把當時那兩個數字嵌進句子**（獨立驗證輪訂正）：上一版嵌了，
而那一筆在數十分鐘後就因為別包重釘而**再也複現不出來**——一段用來證明「可重現」的證據
自己變成不可重現的，是本檔最不能犯的錯。

⇒ **快照消掉的是「時變成分」，不是干擾本身**：

- **消掉**：同一條指令在不同時刻跑出不同 rc（因為量測那一刻別人正在存檔）。快照樹不會動 ⇒ rc 可重現。
- **不消掉**：跨包內容干擾。它被快照**忠實保存**，一併帶進驗證樹。
- ⇒ 正確的說法是：**軸 B 買到的是「確定性」，不是「綠」。** 驗證者拿到的紅仍然可能與他無關，
  但至少那個紅是**可重現、可歸因**的；而「可歸因」正是上一版把它誤寫成「全解」的那個東西。

## 3. 三方分歧的逐點裁決（含本次訂正）

### 爭點 1 — 扇出的種子從哪來？

| 方 | 主張 |
|---|---|
| Architect | 從當前工作樹**播種**（`git diff HEAD --binary` ＋ 未追蹤複製），worker 全程 uncommitted |
| SA | 硬前提是「**各包必須 commit**」，否則驗證者審的是動工前的樹 |
| SD | 從 **HEAD**（`BASE=$(git rev-parse HEAD)`）開，agent 自己 commit，tag，cherry-pick |

**裁決：採快照 commit（§2.2），三者皆不原樣採用。** 這一點未受本次降級影響——快照仍然是唯讀驗證樹的來源。

- **駁 SD 的 HEAD 釘選**——【合成輪】實查：判準函式 `checkout_local_debt_verdict` 在**工作樹出現 7 次、在 HEAD 出現 0 次**。⇒ 從 HEAD 開的樹缺少在途成果，這不是理論風險，是當時就成立的事實。
- **駁 Architect 的播種腳本**——它要寫約 200 行載具去做 `git diff --binary` ＋未追蹤複製＋apply，而 plumbing 三行做到同一件事**且產出真 commit**。
- **駁 SA 的「先 commit 進 main」**——SA 的**目的**完全正確（驗證者必須看到被審的工作，否則是假通過），但手段有代價：把半套工作 commit 進 main 歷史，且要過 pre-commit hook。`commit-tree` 達成同一個目的而無這兩項代價。**SA 的需求被滿足，SA 的手段被換掉。**

### 🔴 爭點 2 — 收斂用 cherry-pick 還是差分 apply？（**射程已消失；本節改為登記那個粒度事實**）

**裁決：兩者都不採用——因為 Stage 2 已放棄，原 Phase 2 INTEGRATE 的 apply 站整個不存在。**

> 🔴 **本節（與爭點 8、§6）出現的「Phase 2」一律指**已刪除的**原 Phase 2 INTEGRATE**，
> 不是 §2.1 現行編號裡的 Phase 2 RE-PIN。獨立驗證輪指出這兩個名字在本檔曾同時活著、
> 讀起來直接互相矛盾（一邊說它已刪除、一邊把它列在現行階段表裡）⇒ 已逐處補上 INTEGRATE
> 全名。**不改現行編號**：RE-PIN 是留下來的階段，為了讓被刪除的東西不撞名而把留下來的
> 東西改號，是拿活的去遷就死的。

上一版在此得出一句招牌宣稱，並用它支撐 §6 的「讓一整族未來的鎖失去立案理由」：

> ~~今天寫在任務書散文裡的「包與包檔案互斥」，在 Phase 2 變成一道會 rc=1 的機械閘門，新增程式碼 0 行。~~

**這句話在檔案粒度上是假的，兩名複審者各自在不同語料上獨立重現：**

| 語料 | 形態 | 實測 |
|---|---|---|
| 合成 repo【複審輪】 | 兩包改**同一支檔的不同 hunk** | `check1_rc=0 apply1_rc=0`／`check2_rc=0 apply2_rc=0`；結果檔**同時含兩包的編輯**、**零告警** |
| 真 repo `useMacWin.md`【複審輪】 | 包 A 改檔尾、包 B 改檔首（皆從同一 `SNAP` 出發） | 對主樹 `--check` 兩包皆 **rc=0**；序列 apply 到離線副本皆 rc=0，兩個標記都在（第 3 行與第 254 行）、**零告警** |
| 合成 repo【合成輪】 | 兩包改**同一行** | `--check` rc=1、硬 apply rc=1、先落地者內容逐字保留（複審者複驗成立） |

🔴 **根因是粒度不匹配，一句話說完**：任務書散文約定的是**檔案級**互斥，而 `git apply` 是 **hunk-context 級**。
上一版只驗了「同一行」那個特例，就把結論外推到整個檔案級約定。

🔴 **為什麼這正好打在本 repo 的痛點上**（所以它不是理論瑕疵）：本 repo 真實的跨包干擾**幾乎全是「同檔不同行」**——
兩包各自重釘 `_TREE_FILE_FLOORS`（該 dict 的註解裡就記著一輪內 44→45→46 的連續重釘）、
兩包各自在 `MIN_TESTS` 那條巨型註解上加沿革、兩包各自改 `.claude/settings.json` 的不同 hook 條目。
**這一整類在上一版的模型下全部靜默通過。**

🔴 **而且它比現狀更糟一階，不是打平**：今天 last-writer-wins 產出的檔，至少有**一個** agent 端到端測過；
Stage 2 的合併體是**第一次存在於整合者的樹裡、零人測過**，唯一的網是收尾那一次全套——跑在所有人都下班之後。

**登記給未來的人（本節存在的唯一理由）**：任何人再想做 apply／patch 式收斂，第一件要面對的事就是
「`git apply --check` 不是檔案互斥偵測器」。要檔案級互斥，判準必須是**檔案集合的交集**
（例如比對兩包 `git diff --name-only` 的交集），那是另一個機制、有它自己的行數，
**不能繼續記在「新增 0 行」那一欄**。

### 爭點 3 — 那「9 支 worktree 假紅」怎麼處理？（**歸因訂正**）

Architect 與 SD 都在 HEAD 釘選樹上量到 9 筆假紅，但歸因相反：Architect 說是「看不到在途成果」，SD 說是「乾淨 checkout 沒有機器本地狀態」，並據此設計 Stage 3——把 9 支登記成具名清單、在 linked worktree 內 skip。

**裁決（訂正版）：SD 的具名 skip 清單不予採用（理由不變）；但 Architect 的歸因只成立於其中一部分——「9」是一個混合體，至少含一族是棘輪陳舊，而那一族快照結構上不消解。**

- **成立的那一半**：`checkout_local_debt_verdict` 工作樹 7 次 / HEAD 0 次【合成輪】⇒ 在途確實有一包正在讓那些判準對乾淨 checkout 免疫。這解釋了為何播種樹跑全套是 0 個 FAIL、而 HEAD 釘選樹有紅。
- 🔴 **上一版漏掉的那一半（本次訂正）**：另有一族是**棘輪陳舊**——下限／基線表被別的包的新增檔案追過（§2.4 三筆實測）。
  這一族**不是**「看不到在途成果」造成的：它是 repo 內容本身，快照會忠實帶著它過去。
  ⇒ 上一版寫的「快照式扇出讓這一族**自動消解**」對這一半**為假**。
- **兩者共通、因此仍然成立的結論**：「9」是對某一棵樹在某一刻量到的**暫態值**，不是這一族的穩態規模。
  把它固化成具名 skip 清單，正是本 repo 反覆記載的病（把過期事實釘進棘輪），且代價雙向——
  清單一旦存在，那 9 支在該樹內就再也不會出聲，包括它們真的壞掉的時候。
- **正確處置**：陳舊棘輪由**當輪重釘**解決（那是 Phase 2 RE-PIN 的工作，不是隔離的工作）；
  真正「量測機器本地狀態」的那一族另案處理，不在本 ADR 射程。

### 爭點 4 — harness 內建的 `isolation: "worktree"` 能不能直接開？

**裁決：不可直接開啟。** 【合成輪】實查到一條殘留分支，其 reflog 逐字：

```
worktree-agent-ace14fdf664c1dd04@{0}: branch: Created from origin/main
```

三項可驗事實：① 它從 **`origin/main`** 播種——不是 HEAD，更不是工作樹 ⇒ 在途成果**結構上一項都看不到**；② 它**建立具名分支**——與掌舵者明訂的「只用 main、不開 feature branch」直接抵觸；③ 它**不回收**——該 worktree 已不在登記中，分支卻仍在、落後 main 105 個 commit。

🔴 **誠實劃界**：這條分支是**舊 session 的遺留物**，機制由 reflog 推斷；沒有 Agent 工具可對**現行版本**直接呼叫驗證。但第 ②③ 項是磁碟上可查的實物，不依賴推斷。

⇒ 唯讀驗證樹一律**自行建立**（§2.3 的整樹拷貝，零 branch），不使用 harness 內建隔離。

### 爭點 5 — `.venv` 怎麼辦？（**因載具改變而訂正**）

| 方 | 主張 |
|---|---|
| Architect | `.venv/` 做成**真目錄**、內部放符號連結＋複製 `pyvenv.cfg` |
| SA | 拒絕 symlink——它正是 import 洩漏的成因 |
| SD | 不放任何 venv，絕對路徑呼叫主樹直譯器＋`PYTHONPATH` |

**裁決：三方的爭點在整樹拷貝下大部分蒸發，但洩漏的根因仍在，故仍須明文。**

【合成輪】實查該 editable 安裝的 `.pth` 內容逐字是主樹絕對路徑：

```
.venv/lib/python3.11/site-packages/_editable_impl_autoclaude.pth
→ /Users/wuweihong/Antigravity/AISDCL_Agent/AutoClaude
```

⇒ 無論用符號連結、整份複製、還是 clonefile 拷貝，只要那個 venv 被用上，`import autoclaude` 就解析到**主樹**。
SA 與 SD 各自獨立實測到同一件事（SA 用注入標記量到 False／True 相反答案；SD 量到 LEAK／ISOLATED）。

- 整樹拷貝**免掉**了「忘了帶 `PYTHONPATH`」這個 worktree 專屬的坑（venv 就在樹裡）。
- 但**沒有免掉** editable `.pth` 寫死主樹這件事 ⇒ **凡驗證標的是 AutoClaude 的 import 面，必須另外處理**（絕對路徑直譯器 ＋ 明文設 `PYTHONPATH` 指向拷貝樹）。
- 🔴 這一格的失效是**靜默**的（測到主樹原始碼、零徵狀）。上一版把它當成「Stage 2 那支包裝工具存在的主要理由」；Stage 2 既已放棄，**它現在是任務書必須逐字寫明的一條**，沒有工具在替你記得。

### 爭點 6 — 舵手會不會失去單一樹全景？（SA 的 G1）

**裁決：在本模型下這個風險不成立，而 Stage-1-only 讓它更不成立。**

【合成輪】實測快照是**拷貝不是搬移**（28→28 髒檔），主樹原封不動。而降級之後**寫檔包根本沒有離開主樹** ⇒ 舵手的 `git status`／`git diff --stat` 照常運作、讀數只增不減。SA 的 G1 精準命中了 SD 與 harness 內建的形態，**它幫我否決了另外兩個候選**。

### 爭點 7 — 護欄成本上限

SA 訂 150 行淨增為硬上限，Architect 報 ~350，SD 報 ~95。**裁決：採 SA 的 150 行上限。**
🔴 **但本 ADR 實際落地後超過它，見 §6 的實測結算——那一格刻意不寫成「符合」。**

### 爭點 8 — 第 5 類（收尾重釘）解得掉嗎？（**訂正：本 ADR 一項都沒解**）

| 方 | 主張 |
|---|---|
| Architect | 四階段讓「我是最後一個」成為**階段定義本身**，結構上消解 |
| SD | `git worktree list` 一行指令的 rc 即判準 |
| SA | 只解得掉一半；**多波次那一半結構上解不掉**，不要花預算 |

**裁決（訂正版）：SA 對。Architect 對「單波次」的論證在 Stage-1-only 之下失去前提。**

- Architect 的論證是「Phase 2 之後只有整合者持筆，這是階段定義不是待驗宣稱」。
  🔴 **但原 Phase 2 INTEGRATE 已隨 Stage 2 一起刪除**（§2.1）：寫檔包留在共用主樹，**沒有任何階段把筆收成一支**。
  ⇒ 「單波次已解」這句話**現在為假**，本次一併訂正。上一版此處寫「本 ADR 只認領單波次那一半」——
  降級之後正確的說法是：**本 ADR 對軸 C 零認領。**
- 多波次：SA 的論證無法反駁——隔離能說「現在沒人在動」，**永遠不能說「之後不會再有一波」**。這是排程語意。
- SD 的判準（用 worktree 登記表當 rc）在 Stage-1-only 下**分母歸零**（寫檔包沒有 worktree）⇒ 不採納。
- ⇒ 軸 C 移入 §8 明文未解。SA 建議的正解（讓下限隨 commit 自動導出，使「中途值」這個類別消失）方向正確且與本 ADR 正交，**列為另案**。

### 爭點 9 — 三方無分歧、直接照收的兩項

- **sparse checkout 一律拒絕**：三方獨立實測同一結論——索引仍列出全部路徑但磁碟上沒有，掃描面靜默塌陷（SD 量到同一支守衛測試由 161 支通過掉到 133 支）。有守衛甚至**逐字點名**凍結面檔案，稀疏掉會讓那支鎖由紅**轉綠**。換磁碟賠假綠，本 repo 判例裡最貴的錯。
- **`refs/stash` 是共用的**：三方各自實測（同一個 SHA／`--git-path` 指向 common dir／worktree 內 stash 讓主樹堆疊 0→1）。⇒ **隔離是工作樹級，不是 repo 級**，指令阻斷器**不可被本 ADR 取代**，也不得拿本 ADR 去砍它的行數。

### 🔴 爭點 10 — 那支指令阻斷器要不要改？（**修法已訂正並落地**）

兩名複審者**都親身被它誤攔**（都發生在自己 scratchpad 的拋棄式 repo／worktree 內，清掉零代價）。
診斷成立：它是指令字串比對，看不到指令落在哪棵樹 ⇒ 只能取最保守判準 ⇒ 必然誤攔 ⇒ 撞上本 repo 判例
「擋到讓人無法工作的守衛會被整個關掉」。

上一版的裁決是「判準加一條 `realpath(git rev-parse --show-toplevel) != realpath($CLAUDE_PROJECT_DIR)` 即放行」。
🔴 **那個修法照著做會變成一支死分支，本次訂正。** 兩個獨立理由，都是【訂正輪】第一手量的：

1. **在哪裡跑 `--show-toplevel`？** 實測 PreToolUse payload 的欄位與 hook 行程狀態：
   payload 帶 `cwd`，而 `payload["cwd"]`、`os.getcwd()`、`CLAUDE_PROJECT_DIR` **三者恆等於專案根**——
   即使被檢查的那條指令自己是 `cd /private/tmp && pwd`。⇒ 拿 hook 自己的 cwd 去問 git，答案恆為專案根、
   判準恆假、**誤擋一次都沒少，而程式碼看起來已經修好了**。那正是本 repo 反覆判紅的「鎖存在但沒有鑑別力」。
   （`--show-toplevel` 本身確有鑑別力：主樹與 linked worktree 回不同值；`--git-common-dir` 兩邊相同 ⇒ 不可用。
   問題從來不在選哪個子指令。）
2. **「只看樹就整條放行」會製造新漏擋，而它漏掉的正是事故原指令。** 動詞的危害射程不同，實測：
   - **只限當前工作樹**：在 linked worktree 內 `git checkout -- b.txt` 之後，wt 的改動消失、**主樹的未提交改動原封不動倖存**。
   - **溢出到共用 `.git`**：在同一棵 wt 內跑 `git stash -q -u --keep-index`，**主樹 stash 深度 0→1、兩邊 `refs/stash` 是同一個 SHA**。

**訂正後的修法＝動詞感知，樹從指令字串推導**（已落地在 `.claude/hooks/block_destructive_git.py`）：

| 動詞族 | 判準 |
|---|---|
| `checkout -- <path>`／`restore`／`reset --hard`／`clean`／`switch -f` | 落腳目錄不是、也不含共用工作樹 ⇒ **放行** |
| `stash` 全家 | **任何樹都擋**（換樹不會讓它變安全） |

放寬的四道前提，每一條都對應一個實測到的漏擋：① 目錄字面寫得出來且存在（`cd /不存在; git clean -fdx` 會讓 git 落在共用工作樹）；② 與專案根**互不包含**（`cd <上一層> && git clean -fdx` 會把專案整包當未追蹤內容刪掉）；③ 無 `--work-tree`／`--git-dir`／`--namespace`（實測能把危害導回任意樹，rc=0，git 自己不攔）；④ 無子殼／群組／`popd`（`cd` 作用域會提早結束）。
反向也守：`git -C <主樹>` 贏過 `cd`（實測 cwd 在別處時它照樣毀掉主樹的改動）。

**紅綠自證**【訂正輪】，同一份 payload 對修訂前／修訂後兩支檔各跑一次：

```
cd <拋棄式 worktree> && git checkout -- b.txt        修訂前 rc=2 → 修訂後 rc=0   （誤擋消失）
cd <拋棄式 worktree> && git stash -q -u --keep-index 修訂前 rc=2 → 修訂後 rc=2   （事故原指令仍擋）
```

回歸鎖在 `tools/tests/test_block_destructive_git_r83.py`（含把判準打壞就會變綠的合成注入）。
🔴 **誠實劃界**：放寬只認**字面寫出來**的目錄——`cd "$WT"` 的變數值 hook 看不到，仍然擋（fail-closed 方向）。

#### 🔴 獨立驗證輪：前提 ② 自陳成立、但有一格沒有鑑別力（已修）

不採信上面任何一句，重跑一組 24 條的判定矩陣（自建合成 repo ＋ 一棵 linked worktree，
全在 scratchpad）。結果 22 條相符、**1 條是我自己的期望寫錯**（`git -C <合成 lab 主樹>`
指的是**別的** repo，放寬是對的），**1 條是真漏擋**：

```
cd / && git clean -fdx          訂正輪 rc=0（放行）→ 獨立驗證輪修後 rc=2
cd /Users && git clean -fdx     兩版皆 rc=2（所以整條前提讀起來完全成立）
```

根因：包含判準寫 `路徑 + os.sep`，而檔案系統根的 `"/" + "/"` ＝ `"//"`，
**沒有任何路徑以 `"//"` 開頭** ⇒ 前提 ②「與專案根互不包含（**雙向**）」在 `target` 為
檔案系統根那一格**恆假**。上一層（`/Users`）擋得住，所以散文與程式碼都讀起來沒問題——
這是本 repo 反覆判紅的「鎖在、但某一格沒有鑑別力」，而它**只有把根那一格真的送進去才看得見**。
修法是把前綴統一由 `_dir_prefix()` 產生（`rstrip` 後補一個分隔符，根與非根同一條路），
並加一支具名回歸鎖 ＋ 一組反向注入（把 `_dir_prefix()` 換回舊寫法，該格必須當場變回放行）。
判準取的是 `os.path.abspath(os.sep)` 而不是字面 `/`（鐵律三：Windows 上那一格是磁碟機根）。

**危害評估（誠實劃界，不誇大）**：檔案系統根一般不是 git repo ⇒ 那條指令實際會被 git 自己
以「not a git repository」擋掉，**實害接近零**。登記它的理由不是實害，是**判準自陳與實作不符**
——一份自己說「雙向都守」的前提，在治理上就得雙向都真。

#### 🔴 獨立驗證輪：live 端到端（走真的 Bash 工具、真的已註冊 hook）

前一輪的紅綠自證是「對兩支檔各起一支 child 行程」＝離線比對；本輪補上真正經過 harness 的那一段
（在 scratchpad 的拋棄式 linked worktree 內）：

- **放行向**：`cd <絕對路徑>/wt && git checkout -- b.txt` → 指令**真的執行**（先前寫進去的標記行消失）。
- **阻擋向**：同一棵 wt 內 `cd <絕對路徑>/wt && git stash -q -u --keep-index` →
  被 `PreToolUse:Bash hook error` 攔下，訊息含溢出說明。
- 附帶結論：這同時證明該 hook 在**根層 session** 真的接上了、macOS 側的 exec-form 載具解得開
  （不是只有單元測試在替它說話）。
- **反 vacuity**：把樹判準 `is_foreign_tree()` 注入成**恆真**（＝放寬到最寬）後，
  `stash` 兩種形態**仍然全部命中**、而 worktree-confined 那族全部放行 ⇒
  「事故原指令擋得住」這件事**不依賴**樹判準的正確性，靠的是動詞分族。這是本次修法最重要的一條性質。

## 4. 兩層模型：哪些包該拿唯讀樹、哪些不該

上一版是三層（寫入層／唯讀層／整合層）。降級後**只剩兩層**——寫入層與整合層合併回主樹：

| 層 | 誰 | 在哪 | 為什麼 |
|---|---|---|---|
| **主樹層** | 並行的 N 個實作包 ＋ 收尾重釘者 | **共用主樹**，一如今天 | 隔離寫檔包買到的只有 cwd 慣例（§7），而它擋不住絕對路徑；代價（假的互斥閘門、零人測過的合併體）大於它 |
| **唯讀層** | 四方複審、獨立驗證者 | 拷貝自主樹／`SNAP` 的**唯讀樹** | ⭐ 直接解掉「驗證者不能跑全套」與「rc 隨別人存檔漂移」；**永遠不需要合併** |

**唯讀層是投報率最高、也是本 ADR 唯一認領的那一格**：不需要合併、不需要衝突處理、不需要任何新程式碼，
卻把「獨立驗證的最強證據被結構性剝奪」這件事還回來。

## 5. 落地、驗收判準與回退點

### Stage 1 — 快照 ＋ 唯讀驗證樹（**護欄層 0 行**）

- **做什麼**：只改任務書。開工前整合者跑 §2.2 那三行取得 `SNAP` 並 tag；驗證／複審包一律在 §2.3 的拷貝樹內跑全套。
- **可證偽驗收**：
  1. 🔴 **確定性判準（第三版；前兩版都因為「結構上不可滿足」而被推翻，見本條末段）**：
     在**同一棵不動的樹**上連跑兩次閘門，**rc 相同**、且輸出在**下列三類正規化之後逐字相同**——
     ① 計時字樣（`in <秒數>s`）、② 樹根絕對路徑前綴、③ **行程本地的一次性識別字**
     （`mkdtemp` 的隨機後綴／臨時目錄路徑／PID 這一類）。並印出工作樹指紋。
     軸 B 給的是確定性不是綠 ⇒ **判準不得要求 rc=0**，也不得要求「跑得出總測試數那一行」。
     🔴 **驗收者若必須再加第四類正規化，那一類本身就是一筆發現要寫進報告**（＝一個
     非確定性輸出源），不是可以順手抹掉的雜訊；反之，抹掉任何**與 repo 內容有關**的差異
     （下限值、檔數、命中清單）一律不算滿足本條——那是把被量的東西改掉。
     **明文禁止**用「中途重釘 `_TREE_FILE_FLOORS`」（或任何下限／基線）去滿足這一條——
     那不是讓量測穩定，那是改掉被量的東西，且會在主樹留下一個中途值（正是軸 C 那 11 次失守的形狀）。

     🔴 **為何上一版的判準非改不可**：它要求驗證者附「總測試數那一行的實測輸出與 rc」，而【複審輪】兩人
     各自實測**兩棵樹都印不出那一行**（根層閘門在 12.56s／12.90s 就 rc≠0 前置退出）⇒ 該判準
     **今天在任何一棵樹都不可滿足**。要求一個結構上做不到的證據，結果只會是驗證者改寫劃界或造數字。

     🔴 **那兩處正規化不是我想出來的，是量出來的**（否則本條會重蹈同一個錯）。【訂正輪】在拷貝樹內
     連跑同一支測試兩次：**未正規化時 diff 非 0**，唯一差異是 `Ran <N> tests in 7.387s` vs `… 7.260s`；

     🔴 **獨立驗證輪訂正 (a)**：那個字串當時嵌著兩個實數，而它們在同一輪內就因別包重釘而失效
     （§2.4 最右欄）⇒ 本條改寫成形態。**推論給驗收者**：判準 #1 的「逐字相同」是拿

     隨時間變假，那正是本 ADR 一路在治的病。

     🔴 **獨立驗證輪訂正 (b) — 本條被推翻的第三次，理由與前兩次同型**：訂正輪的「兩處正規化」
     是在**單一測試檔**上量出來的；獨立驗證輪把同一件事放大到多檔（一次 discover 跑掉
     162 支測試、兩次 rc 皆 0）之後，**只做那兩處正規化的 diff 非 0**，第三個變動源當場出現——
     `mkdtemp()` 的隨機後綴（實測兩次分別是 `…_ev3src2a` 與 `…_gkw4c4i4`，出現在一行
     assertion 訊息裡）。它**不是**樹根前綴、也不是計時字樣，所以照第二版寫法驗收會失敗，
     而失敗原因與 repo 內容無關 ⇒ 那又是一個「結構上不可滿足的判準」。
     補上第 ③ 類之後兩次輸出 diff 為 0。

⇒ **本 ADR 不再宣稱讓任何一族未來的鎖失去立案理由。** 它宣稱的只有一件事：
驗證者能在一棵不會動的樹上拿到可重現的 rc。

**兩件本 ADR 做不到的，照實說**：

1. 它**不減少任何一行**現存護欄。
2. 它**不關掉**「agent 用絕對路徑寫到不該寫的地方」這個洞——降級之後寫檔包連 cwd 慣例都沒有了。

## 7. 已拒絕的方案

| 方案 | 拒絕理由 |
|---|---|
| **寫入者隔離 ＋ 差分收斂（原 Stage 2）** | 互斥閘門在檔案粒度上是假的（兩份獨立實測）；合併體零人測過；剩下的價值只有 cwd 慣例。§5 |
| **直接開 harness 內建隔離** | 從 `origin/main` 播種（看不到在途）、建具名分支（違反只用 main）、不回收（殘留分支落後 105 commit）。爭點 4 |
| **HEAD 釘選式隔離** | 缺在途成果，實測製造假紅。爭點 1／3 |
| **cherry-pick 收斂** | 在必然為髒的主樹上結構性失敗（實測 `Your local changes would be overwritten`）。爭點 2 |
| **linked worktree 當驗證者載具** | 共用 `refs/stash`、無 `.venv`（忘了帶 `PYTHONPATH` 是靜默失效）、真實磁碟貴一個數量級。§2.3 |
| **sparse checkout** | 掃描面靜默塌陷，有守衛會由紅轉綠。三方一致 |
| **symlink 或複製 `.venv` 以求隔離** | editable `.pth` 寫死主樹 ⇒ import 靜默解析到主樹。爭點 5 |
| **每 worktree 一個 venv** | 分鐘級＋需網路（裸 venv 之後還要裝大量套件） |
| **容器隔離** | 本 repo 大量判準量測**主機狀態**（exec bit、工作樹行尾、launchd、排程、hook 載具存在性）⇒ 假紅假綠雙向爆炸 |
| **單寫者序列化** | 並行度歸零＝取消需求而非滿足需求 |
| **檔案租約／advisory lock** | 需新協定＋登記表＋強制點，而強制點正好落在指令阻斷器已自陳的盲區（Write 工具、Python subprocess） |
| **`--show-toplevel` 式的 hook 放行判準** | hook 自己的 cwd 恆為專案根 ⇒ 判準恆假、修法變死分支；且只看樹會把 stash 漏放行。爭點 10 |
| **再加一層 hook 攔更多動詞** | 危害動詞集合是開放的；且只覆蓋軸 A |
| **「約定大家不要亂改」** | 純文件約束對當下的模型零攔阻力，本輪事故本身就是散文約定失守 |

## 8. 殘留風險與明文未解

1. **軸 C（收尾重釘）完全未解**（爭點 8 訂正）。Stage-1-only 下沒有任何階段把筆收成一支，
   「我是不是最後一個」仍是散文。**這是本次降級付出的最大一筆代價，明文記在這裡。**
2. **共用主樹的 last-writer-wins 仍在**。兩包改同一支檔的不同行仍會靜默互相覆蓋——
   本 ADR **不改善這一點**，只是不再假裝有一道機械閘門在守它（§3 爭點 2）。
3. **`git apply --check` 不是檔案互斥偵測器**（hunk-context 級 vs 檔案級）。任何未來的 patch 式收斂第一個會踩這裡。
4. **`refs/stash` 共用**（三方實測一致）⇒ 指令阻斷器仍必要，兩者互補，不得互相抵扣行數。
5. **快照不消解棘輪陳舊**（§2.4）。驗證者仍會拿到與自己無關的紅；買到的是可重現與可歸因。
6. **editable `.pth` 寫死主樹**（爭點 5）⇒ 拷貝樹內驗 AutoClaude import 面必須明文設 `PYTHONPATH`，**失效是靜默的**。
7. **`CLAUDE_PROJECT_DIR` 在拷貝樹內指向何處**——【訂正輪】只量到「hook 行程內它等於主樹專案根」，
   **沒有量到「在拷貝樹裡跑 Claude Code 時它是什麼」**。根層 hook 的載具路徑由它起算，指錯即 fail-open
   （守衛靜默失效，表徵與修好完全相同）。**列為 Stage 1 第一個驗收項，不得假設。**
8. **Windows 側完全未涵蓋**。三輪全部在 macOS 實測。特別是：拷貝樹佔碟**全額**（§2.3）；
   hook 的 Windows 載具落在 venv 目錄下，而拷貝樹帶 venv、linked worktree 不帶 ⇒【推論】兩種載具的
   fail-open 風險不同。**上 Windows 前必須現查。**
9. **快照是快照不是同步**：`SNAP` 取完之後主樹繼續動，拷貝樹看不到。⇒ 驗證者的報告必須寫明它驗的是哪個快照。
10. **`.git/config`、`.git/info/exclude` 在 linked worktree 下共用**（拷貝樹不受此限，這是改載具的附帶好處）。
11. **scratchpad 也是共用命名空間**（SA 本回合親身踩到，本輪再次踩到）。本 ADR 只處理 git 工作樹這一面，
    scratchpad 的互斥仍靠命名慣例。

## 10. 治理登記狀態（實查）

本檔**不需要**登記進 `tools/lib/governance_docs.py`。🔴 **第二位獨立驗證者訂正此處對機制的描述**（結論不變、理由換掉）：原寫「該模組的登記 **glob** 射程是 `docs/06_quality/` 底下的 CrossPlatform 系列」——**該模組的登記面不是 glob**，是一份具名常數清單，該檔逐字寫著「為何具名而不 glob 整個 `docs/`」；glob 只在**發現面**用來反查漏登記，且錨死在 `docs/06_quality/` 這一個目錄。兩面射程都不含 ADR 目錄 ⇒ 結論成立。把具名清單說成 glob 不是措辭問題：讀者會以為「檔名長得像就會被收進去」，於是下一份 ADR 若真該登記，沒有人會去改那份清單。**未修改該檔**（它正被其他包異動）。

🔴 **ADR 目錄受另外三道鎖掃描**，本檔已據此撰寫（後續編輯者請一併遵守）：

- **路徑宣稱鎖**：反引號內「兩段以上＋已知副檔名」的路徑必須真實存在，豁免表是 shrink-only。⇒ 提議中尚未存在的檔一律以**單段檔名**書寫；本次因 Stage 2 放棄，那支不存在的工具連單段檔名都不再出現。
- **幽靈符號鎖**：反引號內的測試類名、測試方法名、底線開頭全大寫常數名，必須真的是某支 Python 檔裡的 class／def。本檔引用的每一個具名符號都已逐一現查解析得到。
- **量測 token 鎖**：LOC 四欄的 `<欄名>=<數字>` 形態會與現查值比對；三位數以上接 pytest 通過字樣的形態一律禁止（ADR 不得自建 pytest 基線的第二個家）。⇒ 本檔談測試規模時一律以「檔數／支數」敘述並指向 SSOT，不寫那兩種形態。
