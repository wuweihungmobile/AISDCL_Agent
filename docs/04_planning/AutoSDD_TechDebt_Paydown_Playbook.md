# AutoSDD 技術債結案 Playbook（可重複使用）

> **緣起**：掌舵者 2026-08-27 直接指令——「拼盡全力降低技術債，請幫我找到解方，徹底解決這個
> 問題！並將迭代解決計畫寫入 docs/04_planning 可以重複使用」。本文件是那個「解方」的載體：
> 之後每一個結案輪都照本 playbook 跑，不必重新發明流程。
>
> **SSOT 宣告**：本文件裡的每一個數字都是**量測值**（絕大多數量測於 2026-08-27，R107 輪），
> 每個數字旁都標了量法。**任何一輪動工前都必須重新現查，不得把本文件的數字當常數引用**——
> 這條紀律本身就是本 repo 付過學費的教訓（量測值被當常數引用，見 DEF-200-203）。
> 文內檔案路徑一律相對 repo 根。

## 1. 目的與觸發條件

### 1.1 何時啟動本 playbook

滿足任一條即應開「結案輪」（純結案，不開新戰場）：

| 觸發條件 | 量測指令（逐字） | 門檻（SSOT 座標，2026-08-27 實讀值） |
|---|---|---|
| 未結列逼近 warn 線 | `python tools/check_defect_log_crossref.py --unresolved-count` | warn=86／fail=98（`tools/lib/defect_ledger_index.py` 的 `UNRESOLVED_ROWS_WARN`/`UNRESOLVED_ROWS_FAIL`，行 405-406） |
| 帳本體積逼近硬牆 | `python tools/check_archive_required.py` | warn=240KiB／fail=256KiB=262,144 bytes（`tools/check_defect_log_crossref.py` 的 `_LEDGER_WARN_BYTES`/`_LEDGER_FAIL_BYTES`，行 1159-1160） |
| 掌舵者指定 | — | 直接指令即觸發 |

🔴 **兩把尺不要混淆**：歸檔（`check_archive_required` 引導的 `--apply`）只降 bytes、
**不降未結列數**；未結列只能靠真結案降。R100 交棒書曾實測硬牆判準是 `>=` 不是 `>`。

### 1.2 開場量測四件套（動工前全部附實測輸出，缺一不動工）

```powershell
# 於 repo 根目錄（Windows 用 PowerShell，絕對路徑或 Push-Location 成對）
python tools/check_defect_log_crossref.py --unresolved-count   # 未結數＋外部阻塞軌筆數
python tools/check_archive_required.py                          # bytes 線
python tools/tests/test_adr_xplat001_c1c2_lock.py --print-guard-lines  # 護欄層行數棘輪淨額
python tools/session_resume_planner.py --pace                   # 可派 agent 數（每次派工前重查）
```

另加兩項：工作樹乾淨確認（`git status`）＋ HEAD sha 記錄；護欄層棘輪的
「連續上升輪數餘裕／一次性豁免名額」現查（R104 交接書 §1.4 的形態：
`_REPIN_MAX_CONSECUTIVE_RISING_ROUNDS` 與 `_REPIN_APPROVED_ROUND_OVERAGE_MAX_ENTRIES`
住 `tools/tests/test_adr_xplat001_c1c2_lock.py`，2026-08-25 實讀值為 2 與 1，
且豁免名額當時已被 R101 用掉——**這格每輪必查，它直接決定本輪能不能淨增測試行數**）。

## 2. 根因模型：為什麼債一直降不下來（量測於 2026-08-27）

以下五條根因由 R107 architect 分析包產出，每條附量化證據與量法。
白話版一句話：**「發現太快、結案太貴、長尾搬不動、複審會再生、併列卡一半」**。

### 根因一：發現型輪是最大的入帳來源（新增的 75%）

- **量法**：對帳本各輪代表 commit 逐一 `git show`，用 crossref 自己的解析器（SSOT，
  不自寫第二份）算未結 ID 集合差集。
- **量測結果（2026-08-27）**：R89→R107 HEAD 共 16 段，累計新增 68 筆、結案 76 筆、
  淨 −8（92→84）。新增高度集中在三個發現型輪：R90 +9、R96 +15、R100 +27，
  合計 51/68＝**75%**。
- **關鍵定性**：R100 那 27 筆（DEF-200-190~217）逐列讀過，**零筆是產品功能缺陷**——
  全是配速波、護欄層治理、PRD 交付稽核、主控自身失誤等「治理系統自身的 meta 缺陷」。
  治理面越精密，可被稽核出的缺陷越多，這是**自我放大迴路**；84 筆 open 中光 R100
  一個窗口就佔 20 筆（24%）。
- **含義**：要降債，先治「入帳速度」，不是只加快結案（→ §5 發現節流閘）。

### 根因二：真結案的單價被護欄層行數棘輪稅鎖死

- **量測結果**：單線結案輪一輪只能真結 3~8 筆——R101 commit 自陳「3 真結案」（淨 −1）、
  R105 Wave1 修 7 筆（淨 −6）、R103 淨 −4（量法同根因一）。
- **成本結構（R105 交接書 §1.2~1.4 實錄）**：每筆 fixed 需回歸鎖，而新增測試觸發
  `tools/tests/` 行數棘輪 ⇒ +34 行測試就得同步搬 −43 行散文、重釘 5 處常數，
  途中還意外觸發第二道分桶棘輪（`guard_bucket_policy.py` 的 prose 桶）再修一次。
  連續上升輪數上限＝2、一次性豁免名額＝1 且已用掉（R104 §1.4 實測）。
- **含義**：就算零新增，84 筆以每輪 3~8 筆的速度也要 84÷8≈10 到 84÷3＝28 輪。
  分母側被鎖死 ⇒ 減稅（§6 路線圖第 1 條）是提高吞吐的關鍵。

### 根因三：29 筆 DEF-101 長尾結構債，單輪結構上結不掉

- **量測結果**：84 筆中 DEF-101 族 29 筆（35%；量法＝`--unresolved-count` 實跑後按族號分群）。
  這批的解鎖條件是跨輪工程或外部授權：ruff 存量分批清（DEF-101-018，帳上滾了 60+ 輪）、
  依賴白名單機械物（DEF-101-060）、dev_start.py 拆分（DEF-101-398，棘輪 headroom 0
  使人不敢碰）、凍結版例外授權（DEF-101-338）。R82 曾實測「85 筆裡 62 筆結構上結不掉」。
- **附帶損耗**：每輪對它們的處置只有「改派承接輪次」，而改派受 ROW_MAX_BYTES=700
  （`tools/lib/defect_ledger_index.py:528`）限制——頂線列不能就地追加，得另立回執新列
  （DEF-200-194 就是專為改派兩列而生的一筆新列）。**帳本治理自體產列**是純損耗。
- **含義**：長尾要「分軌」不是「改派」（→ §6 路線圖第 3 條，需掌舵者裁決）。

### 根因四：結案判準嚴＋複審再生（是品質保證的必要代價，**不建議鬆**）

- 合法狀態首詞零白名單、`partial` 僅限降級出口、fixed 必附當回合實測；複審可把 fixed
  退回 open（DEF-200-190 曾標 fixed@R100，複審判「整檔全跑非新驗證」退回）。
  四方複審自身每輪再生約 1~3 筆新列——但它真的在擋假綠（R105 四方 REJECT 揭發
  DEF-200-202 假交付）。
- **含義**：這條是 feature 不是 bug；規劃吞吐時把「複審再生 1~3 筆/輪」算進淨額預估即可。

### 根因五：「缺陷粒度太細」不成立——反向才是問題：併列壓縮使部分完成卡 open

- 帳本已在用併列（一列裝 3~4 子項：DEF-200-200 四筆併列、206 三筆併列、213 三筆併列）。
  這降低了列數，但造成「列內清掉 2/3 子項仍是 open」——結案粒度與發現粒度錯位，
  單列結案工作量不可預估。這解釋了為何 R101 一輪只真結 3 筆：不是偷懶，是每列體積不均。
- **含義**：禁新立併列＋既有併列開場拆分（→ §6 路線圖第 4 條）。

## 3. 八分類法（R107 全量驗證過的定義與標準動作）

R107 用 7 個唯讀分析包對 84 筆未結列逐筆分類，以下定義經全量驗證可用。
每輪開場對每筆未結列標一類，之後照類派工。

| 類別 | 定義 | 標準結案動作 | R107 筆數 |
|---|---|---|---|
| **already-fixed-verify-only** | 機制已被後續輪蓋好，帳本列從未回頭更新 | **針對性**驗證（指名測試/座標，禁用「整檔全跑」充當憑證——DEF-200-190 退回判例）＋改狀態欄引座標。最便宜的真結案來源，**開場先掃一遍** | 8 |
| **quick-fix** | 當輪一個窗口內可修完（S~M 級），配方明確 | 修＋RED/GREEN 自證＋結；同檔者合併同窗（省棘輪重釘次數） | 19 |
| **needs-dev** | 需真開發（新判準/新接線/重構），單包可承接 | 派工，任務書必附 verify_cmd 與鎖持有面三格（§4.4） | 35 |
| **needs-arch-decision** | 卡在設計裁決不是工程；兩個方向都有論證 | 打包成**一份裁決單**一次呈 Architect／四方；**裁決前任何包不得自行動工** | 18 |
| **needs-user** | 需掌舵者本人核准（政策裁決／凍結版例外） | 集中一份呈報單本輪一併呈；工程量多 <30 分鐘，卡的是核准 | 2 |
| **external-candidate** | 阻塞源真的在外部世界（實機/帳務/上游） | 遷外部阻塞軌（`docs/06_quality/AutoSDD_External_Blocked_Log.md`），三條件見 §4.6 末 | 1 |
| **stale-noise** | 現況已消失、列本身過期 | 複驗後結案（附「現況已不存在」的實測） | 0 |
| **duplicate** | 與他列同根因，兩個載體 | 併入單一載體，本列 closed-by-decision 附引證 | 1 |

R107 的 stale-noise 為 0 不代表以後也是 0——每輪都要重掃這一類；「修了沒人來關」
（already-fixed-verify-only）在 R107 有 8 筆＝約每 10 筆就有 1 筆是白送的結案，
證明**開場先掃 verify-only 永遠值得**。

## 4. 單線結案 SOP（每個結案輪照此跑）

### 4.1 開場量測

照 §1.2 四件套＋工作樹確認，全部附實測輸出進輪次紀錄。

### 4.2 輪型判定（三選一，寫進輪次紀錄）

1. **純結案輪**：淨額棘輪必須綠（新增 ≤ 結案），發現一律進輪內暫存清單不立列（§5）。
2. **混和輪**：須預留結案配額 ≥ 預估新增（歷史基準：複審每輪再生 1~3 筆）。
3. **發現輪**：顯式設 `AUTOSDD_NET_RATCHET_OFF=1` 並在 commit 訊息寫明理由（唯一合法出口；
   R100 先例＝掌舵者裁定發現輪淨額為正是預期）。

### 4.3 分類與批次排序（開場一次做完，不邊做邊挑）

對每筆未結列標 §3 八分類，然後照這個順序排批（**先吃白食、再吃便宜、最後吃硬骨頭**）：

1. **verify-only 批**：純驗證＋改狀態欄，零程式碼變更，未結數立刻降。
2. **文件級 quick-fix 批**：模板/帳本文檔/劃界訂正類（例：同一支模板兩筆一次編修）。
3. **代碼級 quick-fix 批**：**同檔同窗合併**——住同一支鎖檔的多筆一起改，共用一次
   棘輪重釘（R107 實例：DEF-200-166＋171 同住 `tools/tests/test_adr_xplat001_c1c2_lock.py`）。
4. **needs-dev 派工批**：依 §4.4 鎖持有面檢查決定「並行包 or 收尾單人窗口」。
5. **裁決批**：needs-arch-decision 打包一份裁決單、needs-user 打包一份呈報單，一次呈。
6. **複審批**：已修待落款的（PRD 修憲、ADR 轉 Accepted 類）湊同一場四方複審，攤薄複審成本。

### 4.4 🔴 鐵律七：鎖持有面檢查（派工前，每個標的做一次）

任務書要對每個包列出「你要動的鎖，其**常數／史料／消費端**分別住哪幾支檔」。
**三者不在同一持有面時不得派給並行包**——那件事在任何單包手上都做不完，該包只能回報
not_done，白付一次派工；淨減法（刪檔/合併鎖）只能由收尾單人窗口做（git-tracked 缺檔的
fail-loud 只有 `git rm`/stage 能消除，而並行包禁止 git 操作）。
R107 實例：DEF-101-398 與 701 同受 `SPECIAL_FILES` raw-line 棘輪 headroom 0 制約
（2026-08-27 實測 `check_loc_budget --json`：dev_start.py 1952/1952、
run_root_unittests.py 759/759），鎖面跨三持有面，只能收尾單人窗口做。

另一條並行紀律：並行結案包**只動各自認領的列與源碼**，帳本的批次寫入集中到收尾窗口
（寫帳本會改變閘門輸入，見 §8.2）。

任務書門檻三條（驗收指令派工前由主控親跑或只准引用 repo 具名腳本／外部端點輪詢間隔
下限 ≥ 快取 TTL／自造事件不得計為活體驗證）＝派工前置檢查的另一半，全文見
`AutoSDD_Iteration_Prompt_Template.md`〈🧾 派工紀律〉節（:220 起）。

### 4.5 每筆結案流程

1. **讀列＋讀被指向的證據檔**（帳本列是索引不是報告，≤700 bytes，詳情在具名證據檔）。
2. **zero-trust 現況複驗**：不採信列上任何「已修/已驗證」宣稱——對自己上一輪的宣稱亦然。
   R107 實測這一步的價值：DEF-200-209 列內半句「tools/ 面沒有 E701/E702 閘門」已過時、
   DEF-200-201 列內漏了「ceiling 已可經 env 調」這個事實——不複驗就會修錯方向。
3. **修復＋RED/GREEN 自證**：修前紅、修後綠，逐字貼輸出與 rc。
4. **回歸鎖成本預算**：新增測試行數先對棘輪餘裕現查；需抵銷時**只搬散文不動判準**
   （R105 手法：搬 docstring 內純史料進證據檔，判準本體與 WHY 理由不動），同輪一次重釘。
   ⚠️ 搬遷段落內寫出 `docs/` 目錄前綴會把 chunk 翻進 prose 桶觸發第二道分桶棘輪
   （R105 §1.3 實錄）——證據檔引用用裸檔名。
5. **狀態欄改寫**（不是追加）：見 §4.6。
6. **每批結束後跑** `python tools/check_defect_log_crossref.py`，rc=0 才進下一批。

### 4.6 帳本編輯紀律（違反即被機械鎖抓）

- **合法狀態首詞**（帳本表頭 L42 權威散文，與 `_STATUS_FIRST_WORDS` 雙向綁定）：
  `open`／`routed`／`fixed`／`wontfix`／`closed-by-decision`／`no_action_needed`／`partial`。
  `partial` 僅限 ADR-XPLAT-001 §4.3.3 降級出口；`workaround` 刻意不是合法首詞
  （正規寫法 `open（workaround-applied …）`）；自創複合詞如 `partially-fixed` 會被
  `_classify()` 靜默判成 fixed——不要發明首詞。
- **ROW_MAX_BYTES=700**：結案一律**改寫**狀態欄不得追加（R107 實測 DEF-200-023 列
  恰 700 bytes、多列餘裕 ≤11）；超長豁免列（如 DEF-101-796）另受 bytes 死結制約。
- **不動「發現情境」欄**：那是史料；只改狀態欄。
- **證據進具名證據檔**：帳本列只放索引與座標，實測輸出全文放
  `docs/06_quality/CrossPlatform_R{N}_*.md` 類具名檔。
- **帳本列禁半形 `|`**（欄位分隔符污染）。
- **家族配號**：新列一律配當前滾動家族（2026-08-27 現值 `200-`；族號現查表頭 L11~L35，
  滿 999 開下一族；`999-`/`8-`/`9-`/`000-` 是測試保留號不得配出）。
- **外部阻塞軌遷移三條件**（`tools/lib/ledger_closing_guards.py` 的
  `external_blocked_log_problems()` 機械強制）：①具名阻塞源限枚舉
  （`GitHub Actions 帳務`／`Windows 實機`／`上游套件`／`其他-<具體理由>`）；
  ②解鎖條件可機械查；③同 ID 不得雙帳並存（主帳本原列收斂為指向外部軌的索引）。
  複查逾 14 天 warn。

### 4.7 真結案 vs 假綠：否決清單

- ❌「整檔測試全跑通過」不是該列的新驗證（DEF-200-190 退回判例）——憑證必須是
  **針對性**的：指名測試類/檔＋該列訴求逐項對映。
- ❌ 憑證是**值**不是 rc（NextRunTime 判例同型）：宣稱必附當回合 tool_result 裡的數字。
- ❌ 改判型結案（closed-by-decision/wontfix）不得用來清 KPI：必寫明裁決依據與座標。
- ✅「修了沒人來關」是合法且低價的結案來源（§3 verify-only），開場先掃。
- ❌ 部分完成不得標 fixed；殘留留在原列或拆新列，禁止散文帶過。
- ❌「等 windows-compat-ci / macos-compat-ci 轉綠」不得作為任何列的結案條件——
  兩軌 2026-08-27 查證為長期紅（windows 側 8/11 起連紅 29 次），與當輪改動無關；
  驗證一律走本機閘門與本機 act。

## 5. 發現節流閘（防 R90 反效果：發現速度 > 結案速度 ⇒ 未結反增）

根因一的對症藥。R90 教訓：8 個平行發現包使未結 92→95——入帳速度才是要治的變數。

1. **結案輪禁派平行發現包**；複審/修復途中的新發現一律先進**輪內暫存清單**
   （scratchpad 或輪次證據檔的暫存節），**不直接立列**。
2. **收尾單人窗口統一裁決**暫存清單，三選一：
   - 當場可修 ⇒ **修掉，不立列**（no-defer-unless-justified 紀律的機械化：能當場驗證

3. **機械承接**：淨額棘輪（`tools/lib/ledger_closing_guards.py` 機械物①）在 commit 期
   擋「新增 > 結案」；本節把節流**前移到發現當下**，兩層互補。
4. **裁決結果逐筆留痕**：收尾 HANDOFF 必列暫存清單的裁決結果（含「當場修掉未立列」者），
   供稽核——節流不是隱匿。

## 8. 收尾章（順序錯了會白做——R96 的 19 紅就是這樣來的）

### 8.1 收尾順序（嚴格照此，不可對調）

1. **四方複審**：範圍＝本輪全部狀態欄改動＋回歸鎖 diff；審查者親跑 `git diff` 不信轉述。
2. **REJECT 處置**：假交付（DEF-200-202 型）當輪補齊；複審再生的新發現走 §5 節流閘。
   收斂上限 2 輪；仍發散即停損（R58 教訓：複審自我發散 blocking 7→1→10 無停損線，
   整輪作廢退回）。
3. **修復落地**後，**最後一次寫文件（帳本/HANDOFF/證據檔）**。
4. 🔴 **最後一次全套閘門必須在最後一次寫文件之後**——R96 教訓（DEF-200-163 家族）：
   `current_round()` 讀帳本 ⇒ **寫帳本會改變閘門判準的輸入**，R96 因先跑閘門後寫帳本
   吃了 19 紅。順序＝改文件 → 跑全套 → 綠了才 commit；commit 後又改任何文件就得重跑。
5. **commit / push**：push 觸發 pre-push 全套可能超過 2 分鐘，timeout 設 480000~570000ms；
   push 後**必等雲端 CI completed** 才收輪（R74 教訓：沒等結論就收＝把紅留給下輪開場）。
   windows/macos-compat-ci 慢性紅先查歷史再歸因（2026-08-27 查證兩軌長期紅與當輪無關）。
6. **HANDOFF**（`docs/04_planning/R{N}_HANDOFF.md`）。

### 8.2 HANDOFF 必含（四項＋三附件）

- 四項：已驗證什麼（附輸出+rc）／還沒做什麼／下一步的確切指令／禁止事項
  （例：不准 `--no-verify`、不准 `AUTOCLAUDE_SKIP_HOOKS=1`）。
- 附件一：帳本前後量測（未結 X→Y、新增/結案/淨額，`--unresolved-count` 前後兩次實跑）。
- 附件二：護欄層淨額落款（`<!-- guard-total:R{N} -->` 註記，同輪多列合併）＋棘輪重釘清單。
- 附件三：輪內暫存清單的裁決結果逐筆列出（含「當場修掉未立列」者，供稽核）。
