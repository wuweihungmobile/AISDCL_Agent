### 0.2 探針最小重現碼（複審者請自己跑一次，不要採信本文件）

```python
import sys
sys.path.insert(0, r"<repo>/tools/lib")   # 🔴 這幾支模組彼此用裸名 import
import quota_policy as P
p = P.DEFAULT_POLICY

def cell(band, horizon, m198=False, bd=False):
    m = P._mult(horizon, p)
    m_cap = min(1.0, m) if m198 else m            # m198 ＝ 主提案 M198-1
    if bd: m_cap, m = max(1.0, m_cap), max(1.0, m)  # BD-1 ＝ 乘數地板抬到 1.0
    base = P._base_cap(band, p)
    cap = None if base is None else P._clamp(int(base * m_cap), p)
    return cap, P._bound(P._clamp(int(P._base_rec(band, p) * m), p), cap)
```

上限夾層（§4.3）的等價式，本檔全部數字皆由它與 `cell()` 組出：

```python
prop = min(p.cap_notice if c_bd is None else c_bd, p.cap_notice)
cap  = c0 if c0 is None else max(c0, prop)        # 只准往上推到 cap_notice
rec  = max(r0, min(r_bd, p.cap_notice))           # 🔴 只准往上；不得用 ceil 去夾原值
rec  = rec if cap is None else min(rec, cap)
```

🔴 **這一行註解是本輪探針自己撞出來的**：第一版夾層寫成 `min(max(r0, r_bd), ceil)`，被本檔自己的方向鎖抓到 **`free × near` 的 rec 由 16 收緊到 8**〔本輪實測逐字 `方向鎖違反 = [('收緊', 'free', 'near', None, 16, None, 8)]`〕——那正是主提案 §7 P6 在守的掌舵者錨點①。改成上式之後 20 格**零違反**〔本輪實測逐字 `方向鎖違反 = （無）`〕。⇒ **「放寬用的夾層會反過來收緊」不是假想風險，本輪真的發生過一次。**

### 1.1 掌舵者 2026-08-28 晚間指令（**逐字保真，兩則**）〔他包回報：由派工者轉交，本輪未見原始逐字稿〕

🔴 第二則指令本身就是本檔的授權：**掌舵者要求的是「把這個需求情境入憲」，不是「這一次幫我多派幾個 agent」**。⇒ 本檔的產物必須是**可重複使用的機制條文**，不是一次性的操作。

### 1.2 這不是一次性需求，是重複出現的操作情境

〔實讀 `docs/04_planning/R107_RESUME.md:92-93`〕逐字：

⇒ 同一個情境在 **R107 與 R108 兩輪連續出現**，兩次都是掌舵者口頭下令、兩次都沒有任何機制載體。第二次出現時把它入憲，是正確的時點。

### 1.3 先行裁決：目標成立，錯的是代理變數

〔實讀 `docs/04_planning/AutoSDD_TechDebt_Paydown_Playbook.md:248`／`:257`〕與主提案 §5（`:450`）〔實讀〕：R107 判定「先慢後快」不適宜，**錯不在目標，錯在用「時刻」當代理變數而不用「燃燒證據」當主控訊號**。

⇒ 本檔對這句話的承接方式，與主提案 (a)(b)(c) **不同軸**：

| | 主控訊號 | 誰授權放寬 | 條文落點 |
| :---- | :---- | :---- | :---- |
| 主提案 (b) 自動突刺 | 六條件（`bursting_ok()`，含燃燒證據） | **機制自己**（證據制） | PRD §4.2.5 R-4.2.5-1~3（主提案 §6.4） |
| 主提案 (a) thrifty floor | 該軸自己的 `burn_step == −1` | **機制自己**（證據制） | PRD §4.2.8 R-4.2.8-2（主提案 §6.5） |
| **本檔 清倉模式** | **一則顯式指令** | **操作者本人**（指令即證據） | PRD **§4.2.9（新增）** |

🔴 **與 (b) 的劃界必須寫進條文**（否則兩條放寬路徑會互相冒領）：
- (b) 是**六條件全成立才放行**、任一輸入不可得即 fail-closed；清倉模式是**指令在效期內就放行**，但放寬**有界且逐軸**。
- 清倉模式**不是**一個新的 FSM 狀態。PRD §3.2 的 `BURSTING`（`:192`／`:206`〔實讀〕）是狀態機的字；清倉模式是**授權疊層**（authorization overlay），套在 `decide()` 產出之後，不進狀態機、不改 `draining()`／`reset_branch()` 任何一格。
- 兩者可以同時成立（指令在效期內、六條件也通過），此時取**較鬆者**——但仍受本檔 §4.3 的上限夾層與 §5 四條底線約束。

### 2.3 🔴 本輪拿到的關鍵新事實：**擋住清倉的不是那個 cap 階梯，是跨窗攤提**

上表 `five_hour`／`session` 兩軸的**原始水位是 49%**，而 `pct_band` 的四個錨點是 50／70／85／95〔現查碼 `quota_policy.py:216-219`〕⇒ **49% 本來落在 `free` 帶（cap 不設限）**。它們之所以顯示 `band=prepare cap=1`，來源是 `note=amortized`——`quota_pace.band_inputs()`（`:358`〔現查碼〕）把餵給 `pct_band` 的水位上調了。攤提那一行自己說出了算式：本窗配額 27.2pp、已用 49pp、餘裕 **−21.8pp**。

而**攤提的長窗供給軸（`total_kind`）是 `weekly_scoped`（Fable，91%，只剩 9pp）**——不是掌舵者點名的 `weekly_all`（56%，剩 44pp）。

🔴 **這一格是刻意裁決過的，不是漏修**〔現查碼 `quota_pace.py:300-308`，`amortize()` 上方註解逐字〕：

> `quota_policy._in_cap_gate()`（R98）把同一批軸排除在 **cap 聚合**外。兩邊不同**不是漏修**：`binding` 與攤提問的是兩個不同的問題，而攤提這一側納入它的方向是**保守側**……⇒ 它結構上不可能替任何人核准超支，而把排除搬過來是**拿掉一個煞車**＝放寬。

⇒ **對本檔的直接後果（必須寫進條文，不能藏在附註）**：清倉模式若只放寬「時間視野乘數」那一層，在**本輪這個真實情境下幾乎無效**；要真的有效就必須碰攤提那一層，而攤提那一層的供給軸今天是一條**指令沒點名、且本檔 §5 底線③ 明文不納入**的 scoped 軸。逐格量測見 §4.4。

### 2.4 「沒有輸入面可以表達清倉」的三層論證〔現查碼〕

| 層 | 今天有什麼旋鈕 | 為什麼不能拿來表達清倉 |
| :---- | :---- | :---- |
| `Policy`（門檻的唯一的家，`quota_policy.py:213`） | `pace_far`／`cap_*`／`max_fanout` 等 | 全部是**全域常數**：調它們＝對所有軸、所有時刻、所有帳號同時生效，而清倉是**一次、一個視窗、一組軸**的事。這正是主提案 §3.4 判過的「用錯旋鈕」 |
| `fanout_cap_override`（`AUTOSDD_QUOTA_FANOUT_CAP`，`:242`） | 有一個 env 上限旋鈕 | 它**只收緊不放寬**（`:432-437` 逐字：「覆寫是上限，不是拿去參與乘法的 base……只收緊、不放寬」）⇒ 結構上不可能表達放寬 |
| `decide()` 的參數（`:597`） | `ratio`／`ratio_note`／`active_model` | 三者都是**觀測值或本次呼叫的性質**，沒有一個能承載「操作者授權」。而 `Policy` 明文是「全部門檻的唯一的家」⇒ 授權旗標放進 `Policy` 會把一個**授權事實**偽裝成一個門檻 |

⇒ 缺的不是一個數字，是一個**授權事實的載體**。§3 就是設計它。

## 3. 觸發載體：比較表與建議案

### 3.1 三個候選

| 候選 | 誰／何時可稽核 | 綁定 reset 視窗 | 過期自動失效 | 模型碰不碰得到 | 判 |
| :---- | :---- | :---- | :---- | :---- | :---- |
| **(i) env 旗標**（`AUTOSDD_QUOTA_BURNDOWN=1`） | ❌ 沒有「誰」也沒有「何時」 | ❌ 表達不了 | ❌ **跨窗殘留**：設在 `.env` 就永久生效，設在行程環境就跟著 session 生死，兩種都不是「一個 reset 視窗」 | ⚠️ `.env` 是 `Write`／`Edit` 碰得到的檔 | ❌ |
| **(ii) state 落款檔**（帶指令逐字、發令時刻、視窗指紋、到期時刻、發令時的讀數） | ✅ 五欄俱全 | ✅ 以**被點名軸的 `resets_at` 伺服器原字串**為鍵 | ✅ **結構性**：新視窗的 `resets_at` 是另一個字串 ⇒ 舊落款自動不匹配 | ⚠️ 同上（見 §3.4 誠實劃界） | ✅ **建議** |
| **(iii) CLI 顯式子命令**（`--burn-down --until-reset <kind>`） | ✅ 進 session 逐字稿 | ✅ 參數帶 | ✅ 由它寫出 (ii) | — | ✅ **建議：作為 (ii) 的唯一寫入口** |

**⇒ 建議案（一句話）**：**載體＝(ii) 帶「被點名軸 `resets_at` ＋ 方案指紋 ＋ 指令逐字」的 state 落款檔，唯一寫入口是 (iii) 的顯式 CLI 子命令；env 只保留一個「只准關不准開」的 kill-switch（`AUTOSDD_QUOTA_BURNDOWN_OFF`，沿用 `ENV_SPEC` 既有 `escape` 分類，`quota_policy_env.py:120-131`〔現查碼〕的五個 `_OFF` 先例）。**

### 3.2 落款欄位（規範性；🔴 一個都不可省，各自有一條它擋掉的失效）

| 欄位 | 內容 | 它擋掉什麼 |
| :---- | :---- | :---- |
| `directive_verbatim` | 掌舵者指令逐字原文 | 事後爭議「這段高燒是誰要的」 |

| `axis_kind` | 被點名的軸（例：`weekly_all`） | 「清倉」被讀成「全部軸一起放寬」 |
| `until_resets_at` | 該軸的 `resets_at`，**伺服器原字串、不轉本地、不重新格式化** | 跨窗殘留（`quota_policy.py:40-42`〔現查碼〕既有紀律） |
| `core_signature` | 發令當時的方案指紋（`quota_gate.core_signature()` `:303`〔現查碼〕） | 換帳號／換方案之後舊授權還活著 |
| `readings_at_issue` | 發令當時的逐軸 `(kind, pct, resets_at)` | 事後無法判斷「當時真的有 45pp 要蒸發嗎」 |

**落款檔的家**：持久目錄（SSOT＝`tools/lib/endurance_env.py`，逃生口 `AUTOSDD_TRACE_DIR`，唯讀時退回暫存並出聲）。🔴 **刻意不住 `%TEMP%`**：`degraded_stamp_path()`（`quota_gate.py:526`〔現查碼〕）那一族是 TTL 閂鎖、重開機即消失是正確的；而**一則授權必須活過一次重開機**（它的效期是 reset 視窗，不是行程壽命）。

### 3.3 生效判準（**全部合取，任一不成立即整段不套用 ⇒ 退回今天的行為**）

```

             ∧ AUTOSDD_QUOTA_BURNDOWN_OFF 未設
             ∧ core_signature(本次讀數) == 落款.core_signature
             ∧ 落款.axis_kind 仍出現在本次讀數
             ∧ now < parse_aware(落款.until_resets_at)          ← 過期即失效
             ∧ parse_aware(落款.until_resets_at) 解得出          ← 解不出＝拒絕武裝
```

🔴 兩條沿用既有判例、不新發明：
- **「解不出時刻一律拒絕武裝，不准退回假設」**——CLAUDE.md〈額度哨兵〉逐字判詞；本檔把它套在 (iii) 的寫入端（解不出 ⇒ 非零 rc、不寫落款）與消費端（解不出 ⇒ 不生效）**兩側**。
- **fail-closed 的方向**：判準是「放寬」方向的唯一一個，任何不確定一律退回今天的行為（同 `bursting_ok()` 檔頭 `:583-584`〔現查碼〕「不傳＝不放行」）。

### 3.4 🔴 誠實劃界：沒有任何載體能在機械上證明「是人下的令」

落款檔是磁碟上的一份 JSON，模型也寫得出來。⇒ **本檔不宣稱載體具有防偽性質**（那會是 `DEF-200-190`「自陳＝承諾不是機制」的同型假話）。它交付的是三件真的做得到的事：

1. **可稽核**：五個欄位讓事後回溯有座標（誰、何時、哪個視窗、當時水位、指令原文）。
2. **偽造成本非零且可對帳**：`readings_at_issue` 必須與同一時刻的燃燒落款自洽，`core_signature` 必須與當時的軸集合一致 ⇒ 偽造要同時偽造兩份互相獨立的痕跡。
3. **失效可偵測**：授權過期／指紋改變／解不出時刻，三者都讓授權**靜靜地不生效**而不是**靜靜地生效**——方向正確的那一邊。

## 4. 語意：放寬什麼、放寬多少

> 詞彙一律沿用主提案 §4.2.2-c 的運算元對映（`C_cap ↔ cap`、`C_target ↔ rec`）。

### 4.1 qualifying 軸（**逐軸判定，不是全域開關**）

```
軸 x 是 qualifying ⇔ 清倉授權生效（§3.3）
                    ∧ x.kind == 落款.axis_kind            ← 只放寬被點名的那一軸
                       ∨（x 與被點名軸的 resets_at 相同 且 x ∈ cap gate）  ← 同窗鄰軸（見下）
                    ∧ x.band != halt 且 x.pct < halt_pct   ← 底線①
                    ∧ x.kind ∉ FALLBACK_KINDS              ← 底線②
                    ∧ x.kind ∉ MODEL_SCOPED_KINDS（除非指令明文點名）  ← 底線③
                    ∧ x 的距 reset 分鐘數解得出且 ≥ 0       ← 時鐘偏移不得換來放寬
```

- **「同窗鄰軸」為什麼要有**〔本輪實測〕：掌舵者點名的是 `weekly_all`，而它今天的 cap 已經是 16（`notice × near`）⇒ 只放寬它**一格都不會動**。真正 binding 的是 `five_hour`／`session`（cap=1）。⇒ 若不允許放寬「同一個 reset 時刻的鄰軸」，這條條文對立案情境**結構上零作用**。
- **「同窗鄰軸」的邊界**：`weekly_all` 與 `weekly_scoped`／`seven_day` 的 `resets_at` 皆為 518 分鐘後〔本輪實測〕⇒ 同窗鄰軸的定義會把 `weekly_scoped` 掃進來，而底線③ 把它擋掉（`MODEL_SCOPED_KINDS` 那一條合取項）。**兩條規則的交互必須明文，不能靠讀者推導** ⇒ 已寫成上式的合取序。
- 🔴 `five_hour`／`session` 的 `resets_at` 是 158 分鐘後，**與被點名的週軸不同窗** ⇒ **它們今天不是 qualifying 軸**。這是本條文對立案情境**仍然治不到**的第二個原因（第一個是 §2.3 的攤提）。誠實記在 §9-1，不用「同窗鄰軸」的定義去偷偷放寬。

### 4.2 兩個放寬動作（BD-1 授權；BD-2 帶結構守門）

**BD-1（時間視野乘數地板，S 級，本檔授權）**：qualifying 軸的 `_mult(horizon)`（`quota_policy.py:394`〔現查碼〕）**下界抬到 1.0**（中性），即 `far`／`none` 的 ×0.5 減速被收回。

- **與主提案 (a) thrifty floor 的關係**：**同一個動作、不同的授權來源**。(a) 的授權是該軸自己的 `burn_step == −1`；BD-1 的授權是指令。⇒ 落地時**共用同一個實作落點**（`quota_pace.effective_horizon()` 的乘數地板，主提案 §5.1 `:463`〔實讀〕），不新開第二個家。
- **地板永遠不是加速**：BD-1 只把減速收回中性，**不把 `pace_near` 的 ×2 送給遠期軸**。這條與主提案 R-4.2.8-2 逐字同款（`:727`〔實讀〕）。

**BD-2（跨窗攤提的上調暫停，本檔**授權但帶結構守門**）**：qualifying 軸若同時滿足下列**全部**條件，該軸餵給 `pct_band` 的水位改用**原始 pct**（即攤提的上調對它暫停）：

```
攤提存在（Amort is not None）
∧ 攤提的 total_kind（長窗供給軸）**也是** qualifying 軸        ← 結構守門
∧ total_kind ∈ cap gate（非 FALLBACK、非未命中的 MODEL_SCOPED）  ← 結構守門
∧ total_kind 的 resets_at 在授權效期內
```

- **實作形態＝既有機制的第二個分支，不新發明**：`quota_pace.amort_relaxed()`（`:345`〔現查碼〕）今天已經在做「條件成立 ⇒ 攤提只出聲、不收緊」這件事（R95：長窗自軸未達 converge 錨點）。BD-2 是給它**加一個 OR 分支**，而不是新開一條路。
- 🔴 **`amortize()` 的取數面一個字不動**：`quota_pace.py:300-308` 的既有裁決（攤提納入 model-scoped 軸＝保守側、刻意不排除）**本檔不觸碰、不引用來反對、不旁路**。BD-2 改的是「要不要施加上調」，不是「上調從哪些軸算出來」。
- 🔴 **今天這道守門結構上不會通過**〔本輪實測〕：攤提的 `total_kind` 是 `weekly_scoped`，它被 `_in_cap_gate()`（`quota_policy.py:582`〔現查碼〕）排除、且被底線③ 排除 ⇒ **BD-2 對本輪的立案情境不觸發**。這是**刻意的 fail-safe**，代價是條文治不到立案情境；解除路徑是一次明示裁決（§11 QB2），不是把守門拿掉。

### 4.3 上限夾層（**放寬的方向鎖**）

```
ceil = cap_notice（現查 Policy.cap_notice；🔴 不是 max_fanout）
cap_bd(x) = cap_x                              若 cap_x is None（本來就不設限，不動）
          = max(cap_x, min(cap_relaxed_x, ceil))  否則
rec_bd(x) = max(rec_x, min(rec_relaxed_x, ceil))，再夾 cap_bd(x)
非 qualifying 軸：逐格不動
跨軸聚合：仍是既有的 min（cap）／既有的 rec 聚合律 —— 本段不改聚合，只改逐軸輸入
```

**為什麼上限是 `cap_notice` 而不是 `max_fanout`（＝「保留一層」）**，四條理由：

1. **掌舵者要的是「把額度用完」，不是「拆掉煞車」**。`max_fanout` 是加速後的絕對上界；清倉是一則授權，不是把系統推到極限。
2. **零新常數**：`cap_notice` 是既有欄位（`quota_policy.py:222`〔現查碼〕）、語意對（notice＝「開始注意、少派」那一帶的 base cap，也就是節流帶最寬的那一格）。同主提案 (c) 複用 `cap_prepare` 的判例（`:527`〔實讀〕）。
3. **它讓 `cap` 永不變成 `None`**。🔴 **語意本版寫足（三審 QA：上一版那句「不製造新的『不設限』格」有兩種讀法）**：夾層的行為是**兩條，各自封閉**——(a) 原本 `cap` 為有限值的格，只准往上推、**上界卡在 `cap_notice`** ⇒ 推不出 `None`；(b) 原本 `cap` 已是 `None`（free 帶四格）的格，**逐格不動** ⇒ 也不會被夾成有限值。⇒ 「不製造新的 `None` 格」指的是 (a)，且同時保證 (b) 不反向收緊（那正是 §0.2 撞到過的那個方向）。
   - 🔴 **但「本檔不惡化它」這句只對 `cap` 面成立，對 `rec` 面不成立（三審 Architect A6，本版照實劃界）**：主提案 §6.9 標為「待承重」的那個已知缺口是「PRD §11.2〈重置後不暴衝〉在 `_cap_for(BAND_FREE, *)` 四格皆 `None` 之下**沒有落點**」，而 §4.4 值域表逐字顯示 BD 在**那四格裡的兩格**把 `rec` 推高了：`free × far` 與 `free × none` 皆 **(None, 4) → (None, 8)**〔本輪實測〕。⇒ 誠實的說法是：**清倉在一個「重置後不暴衝」結構上無人守的缺口上，把建議派工數加了一倍**；它不新增 `None` 格（cap 面不惡化），但 rec 面確實往缺口的方向動了。三件事一起交出去：① 這兩格的 `cap` 仍是 `None`＝該缺口**本來就**沒有煞車，BD 不是它的成因；② `rec` 的上界仍受 `ceil = cap_notice` 夾住（8，不是 `max_fanout` 16）；③ 這一格**不由本檔自行結案**——它是主提案 §10 **Q6 (i)**（free 帶那一格另立缺陷列）的下游，若 Q6 (i) 落地後給了 free 帶一個有限 cap，本檔的夾層自動退回 (a) 那條路。**在 Q6 裁決之前，任何「清倉不惡化重置後不暴衝」的宣稱都必須加上「只對 cap 面」這五個字。**
4. **它讓主提案 M198-1 的判準不受損傷**〔本輪實測〕：M198-1（cap 側乘數夾上界 1.0）落地後，qualifying 軸的 cap 乘數上下界在 1.0 重合 ⇒ `cap == base_cap ∈ {None, 8, 4, 2}` ⇒ **`cap ≥ max_fanout` 的格數 = 0**、**相對 M198-1 收緊的格數 = 0**、**錨點①（`free × near`）= `(None, 16)` 逐格不變**。

🔴 三條要求，各自對應一個既有判例：

1. **必須帶「原值 → 放寬值」兩個數**，不得只寫「已放寬」。同主提案 M198-2／P7 的判詞（`:291`／`:811`〔實讀〕）：「不得只寫『無節流』——否則它自己就變成一個沒有值可以對帳的宣稱」。
2. **必須同時說出「哪些軸沒被放寬、為什麼」**。理由是主提案 §8-7①（`:839`〔實讀〕）點出的同型病：**「授權在但結構上沒生效」與「沒有授權」在畫面上必須分得開**——而 §4.2 已經證明「授權在但一格都沒放寬」是**今天最可能發生的那個結果**。
3. **授權過期後這一段必須消失**。留著就是一句假話（同本檔多處引用的「訊息裡混一句假話比少一欄更難看見」判例）。

### 6.2 燃燒落款必須帶得回溯（`quota_pace.row_of()` `:555`〔現查碼〕）

`row_of()` 今天只落 `ts/pct/live/fp`。清倉模式需要新增一格 `bd`（生效中＝落款 id，否則 `null`）⇒ **事後可從落款回溯「這段高燒是指令授權的」**。

🔴 **與主提案 W0 同窗**：主提案 §9 的 W0 就是「`row_of()` 落 `resets_at`」（`:850`〔實讀〕）。兩者動同一個函式、同一個消費端（`quota_gate.record_burn()` `:334`〔現查碼〕）⇒ **鐵律七**：不得拆給並行包，必須同窗處理。

### 6.3 §9 指標（兩個，成對才有意義）

- `autosdd_burndown_relaxed_decisions_total`（counter）：清倉授權生效**且真的放寬了至少一軸**的決策次數。
- `autosdd_burndown_authorized_but_inert_total`（counter）：清倉授權生效**但一軸都沒放寬**的決策次數。

🔴 **為什麼要成對**：只有第一個，條文「治不到事情」是靜默的；兩個一起，`inert / (relaxed + inert)` 就是「這條條文有沒有在做事」的直接量測。§4.2／§4.4 已預告這個比值**今天會是 1.0**。

## 9. 誠實劃界

1. 🔴 **本條文對立案情境（2026-08-28 那一則指令）今天治不到，原因具名兩條**〔本輪實測〕：
   - **(a) 被點名軸不是 binding 軸**：掌舵者點名 weekly all-models（`weekly_all` 56%／剩 518 分），而它的 `cap` 已經是 16；真正 binding 的是 `five_hour`／`session`（`cap=1`），它們的 `resets_at` 在 158 分鐘後、**與被點名軸不同窗** ⇒ 依 §4.1 不是 qualifying 軸。
   - **(b) 擋住它的是攤提，而攤提的長窗供給軸是 `weekly_scoped`（Fable 91%）**——一條指令沒點名、且底線③ 明文不納入的 scoped 軸 ⇒ BD-2 的結構守門不通過。
   - ⇒ **BD-1 單獨落地只把 binding 軸的 `cap` 由 1 推到 2、`rec` 維持 1**〔本輪實測〕。**本檔不假裝這是「治好了」**，也不為了讓它好看而放寬守門。升為裁決項 QB2。
2. **本檔沒有量到任何「清倉模式若生效會燒掉多少額度」**。§4.4 的值域表回答的是「cap／rec 會變成幾」，不是「實際會多消耗幾 pp」——後者需要 per-agent 燃燒率，而 `row_of()` 今天連 `resets_at` 都不落（主提案 §8-3 已記；本檔 §6.2 的 `bd` 欄與那一格同窗）。
3. **§1.1 的指令逐字與當時量測是〔他包回報〕**：本輪未見原始逐字稿。本輪重跑的 `--pace` 與立案摘要的**結論**逐字一致（`cap=1 recommended=1 band=prepare binding=five_hour`），但水位已漂移（55%→56%、8h55m→518 分）⇒ **不得**把本輪的數字寫成當時的數字。
4. **載體不具防偽性質**（§3.4）。本檔交付「可稽核／偽造可對帳／失效可偵測」，**沒有**交付「這一定是人下的令」。任何實作或文件把它讀成後者即為假話。
5. **「同窗鄰軸」是本檔發明的新概念，沒有既有判例**。它的必要性有實測支撐（不許放寬鄰軸 ⇒ 條文對立案情境零作用），但它的**邊界**（`resets_at` 完全相等？容差幾秒？）本檔取「伺服器原字串完全相等」＝最嚴的那一種，理由是零容差不需要發明一個容差值。若伺服器對同窗軸回出微秒級差異，這條會靜默不觸發——**失效方向是保守側，但確實會靜默**，記為觀察項。
6. **BD-1 與主提案 (a) 共用實作落點，這是優點也是風險**：兩者共用乘數地板 ⇒ 落地時**必須同窗**（否則第二個落地的那一方會發現地板已經在了，而它的紅綠自證會恆綠）。⇒ 併批時 (a) 與 BD-1 的判準必須**各自帶自己的授權來源**進判準（(a) 注入 `burn_step == −1` 且無授權落款；BD-1 注入 `burn_step == 0` 且有授權落款），否則兩條判準互為彼此的假綠。
7. **本檔零測試、零閘門**：一支測試都沒跑，也沒有宣稱任何測試通過（架構輪紀律）。唯一跑過的是兩支唯讀探針與一次 `--pace`。
8. **`BURNDOWN_CAP_CEILING` 的出廠值（`cap_notice`）是設計論證不是量測**：本 repo 沒有任何資料回答「清倉時該放到幾」。誠實的說法是：`cap_notice` 是**保留一層**的保守側選擇（它讓 cap 永不變 `None`、永不觸及 `max_fanout`），而 env 鍵只准調小就是為了讓這個選擇的錯誤方向可控。同主提案 §8-6c 對 `W_TOTAL_FLOOR_MINUTES` 的劃界形態。
9. 🔴 **底線④（must-finish）蓋得住的時間，遠小於一則授權的效期——這一格必須明說（三審 Architect A7）**。must-finish 收緊層的觸發條件是「`T_rem` 落在 `T_WRAP_MINUTES` 之內」，而主提案 §10 **Q5** 的建議出廠值是 **5 分鐘**（`FANOUT_WINDOW_SECONDS/60`，30 分那個選項留給 W6）；而清倉授權的效期上界是**被點名軸的下一次 reset**——本輪立案情境實測 **518 分鐘**〔本輪實測 `--pace` 逐字〕，月桶軸更可達 43200 分鐘（§11 QB5 已引）。⇒ **底線④ 只在授權效期的最後那一小段（出廠值下＝5 分鐘，約立案情境的 1%）提供保護**；在那之前的數百分鐘裡，「派了也做不完」這件事**沒有任何一層在管**——`cap`／`rec` 兩欄都只由水位與 horizon 決定，不看「這一批工作來不來得及做完」。
   - **為什麼還是要有底線④**：它守的是**順序**（收緊層必須在放寬層之後求值），而順序是結構性的：沒有它，連最後那 5 分鐘也會被清倉蓋掉。⇒ 它是**必要但遠不充分**，本檔不把它寫成「派了也做不完結構上不可能發生」。
   - **不由本檔擴大射程**：把 `T_WRAP_MINUTES` 調大（例：30 分）在本 repo 是一次**獨立裁決**（主提案 Q5，且它與掌舵者錨點① 打架）；用清倉授權去帶一個自己的收尾窗＝製造第二個家。⇒ **登記為觀察項並指向 Q5**，同時建議在 §6.1 的出聲行裡把「本次授權效期還剩幾分鐘」與「must-finish 門檻幾分鐘」**兩個數並列印出**，讓這個落差在畫面上可見而不是靠讀條文推導。
