### 2.1 `DEF-200-105`（新）交棒書 §5.1 前兩行在 repo root **結構上不可執行**

R85 交棒書 §5.1 是「R86 首日照著跑」的清單，前兩行實測皆失敗：

| 行 | 實測 | 根因 |
|---|---|---|
| `docker compose -f docker-compose.ci.yml up -d` | `rc=1`，逐字 `no such file or directory` | 該檔實住 `AutoClaude/`，repo root 一支都沒有 |
| `python -m alembic upgrade head` | 於 root `rc=255`（`No 'script_location' key`）；改到 `AutoClaude/` 後仍 `rc=2`（`缺少 PostgreSQL DSN`） | `alembic.ini` 住 `AutoClaude/`；**且即使 cd 對了也還需先注入 DSN** |

**為什麼它值得立案而不是隨手改掉**：這是 R85 §6 教訓 5（「做了但不落磁碟＝沒發生」）的**反向孿生**——
交棒書把**沒跑過的指令**寫成了「照順序跑」的清單，而它自己那一輪的 §0 明文要求「凡本檔寫出的 rc 都是真跑過的」。

### 2.2 `DEF-200-106`（新）配速演算法：一個絕對 horizon 門檻在兩類軸上造成**相反**的極端

現行係數（SSOT＝`tools/lib/quota_policy.py`，現查 `--print-env-example`）：
`FAR_HORIZON_MINUTES=360`／`PACE_FAR=0.5`／`ACCEL_WINDOW_MINUTES=30`／`PACE_NEAR=2`。

實測（`FAR` 門檻相對各軸窗長的位置）：

| 軸 | 窗長 | FAR 門檻佔窗長 | 後果 |
|---|---|---|---|
| `five_hour`／`session` | 300 分 | **120%** | reset 距離**最多**只有 300 分 < 360 ⇒ **5 小時軸結構上永不判為 far、永不減速** |
| `seven_day`／`weekly_all` | 10080 分 | **3.6%** | **96.4% 的時間恆為 far** ⇒ 週軸吃**恆定** ×0.5，不是「依 reset 距離動態調節」 |

⇒ 同一個常數在兩種窗長上**雙向失效**。這使訴求 6b 要的「近 reset 就加速」在週軸上**結構上不可能發生**，
而 R85 §4 政策 P-1 記下的「週軸 ≥50% 時 5 小時軸的加速表現不出來」只是這個病的**下游表徵**，不是根因。

**修法方向（交 SA／Architect 判定，不由舵手指定實作）**：horizon 門檻應**相對於各軸窗長**
（例：剩餘時間 < 窗長 x% ⇒ near、> y% ⇒ far），而不是所有軸共用一個絕對分鐘數。

### 2.3 `DEF-200-107`（新）配速演算法對**燃燒率**完全失明——`pct` 單獨看沒有意義

實測（週軸，當回合）：

```
週窗 08-09 02:00 → 08-16 02:00
已過時間 54.4%   已用額度 74.0%   ⇒ 超前 +19.6pp
剩餘 26.0% 要撐 3.19 天           ⇒ 日均可用 8.2%/天
```

⇒ 今天 `cap=2` **恰好是對的答案，但它是用錯的理由算出來的**：
演算法只看瞬時 `pct`，沒有把「已過時間比例」放進去。
反例（同一個 `pct` 應該給出不同的 cap，而現行演算法會給同一個）：

| 情境 | 應該 | 現行演算法 |
|---|---|---|
| 用 74%、只過 20% 時間（嚴重超速） | 比現在**更嚴** | `cap=2` |
| 用 74%、已過 90% 時間（其實很省） | 比現在**更寬** | `cap=2` |

**這一筆的價值在於它是掌舵者提供的 CLI 畫面觸發的**：對帳本身零誤差
（`session.pct=1.0` 對 CLI `1% used`、reset 台北 23:00 對 CLI `1 hr 38 min`，`source=endpoint`／`http_status=200`），
但**為了證明取數沒錯而做的驗算，反而暴露了消費那些數字的演算法有缺陷**。

🔴 **附帶的黃金基準**：訴求 6z 的調研結論是「查不到任何官方通道能回答個人訂閱帳號的當前水位＋reset」。
掌舵者這次貼出的 CLI 畫面是 repo 至今**唯一一筆外部獨立校準基準**，必須落成可重跑的回歸憑證，
不能只活在對話裡（同 R85 教訓 5）。

### 2.4 `DEF-200-108`（新）配速演算法缺**跨窗攤提**；以及 `cap` 是併發旋鈕卻被用來保護總量配額

**觸發**：掌舵者於本輪中途回報「`Resets in 45 min / 14% used`，配速好像做得不好」。
順著它取到 repo 至今**從未有過**的一組資料。

#### (a) 兩軸換算比 `r`（同載具、同機器、間隔 52 分鐘的兩次量測）

| 時刻 | `session`／`five_hour` | `seven_day`／`weekly_all` |
|---|---|---|
| 21:24 | 1% | 74% |
| 22:16 | **16%** | **75%** |

⇒ **短窗 +15pp 對應長窗 +1pp ⇒ `r ≈ 15:1`**（用滿整個 5 小時窗 ≈ 只花週配額 6.7pp）。
🔴 **`r` 不得寫成常數**：這是 **n=1** 的觀測，且未控制當時在跑幾個 agent。
正解是從落款軌跡的相鄰差分推估，樣本不足時走保守側（假設 `r` 小＝短窗很貴）。

#### (b) 缺失的維度＝跨窗攤提（本窗到底能燒多少）

```
長窗剩餘 25%，距 reset 3.15 天 ≈ 15.1 個 5 小時窗
⇒ 每窗分攤的長窗配額 = 25 / 15.1 = 1.66pp
⇒ 換成短窗刻度 = 1.66 × r(15) = 約 25%
⇒ 本窗已用 16% ⇒ 本窗餘裕 ≈ 9pp，而本窗只剩 42 分鐘
⇒ 用完那 9pp 所需併發度（以實測燃燒率 15pp/52分/2~3 agent 回推）= 2~3
```

⇒ **今天 `cap=2` 在數量上恰好正確，但它是用錯的理由算出來的**
（現行值來自 `far` 的恆定 ×0.5，與攤提毫無關係）。這與 §2.3 是同一個病的兩面：
瞬時 `pct` 與絕對 horizon 都答不出「本窗還能燒多少」。

#### (c) 缺陷 C：`cap` 是**併發度**旋鈕，被用來保護**總量**配額

- `cap` 管**速率**（同時幾個 agent）；週配額管**總量**（7 天內總共多少）。
- 降 `cap` 只讓同批工作**花更久**，總消耗不變；串行化還會**增加**總消耗
  （舵手在每批之間重讀狀態、重寫任務書，context 反覆重載）。
- ⇒ 正確分工：**併發度 ← 短窗（速率）**；**本輪總共派幾包 ← 長窗（總量）**。
- 🔴 **本條不得被讀成「所以 cap 可以放大」**：攤提算出來的今天仍是 2~3。
  缺陷 C 要的是**旋鈕語意分離**，不是放寬。

#### (d) 掌舵者不滿的**直接原因**是畫面沒說出因果

`16% used／45 分鐘 reset` 卻只能派 2 個，而畫面只印 `binding=seven_day`
⇒ 讀起來像程式抓錯或過度保守。**輸出必須印出攤提中間量**，一行回答
「為什麼短窗空著也不能衝」。這一項與 §2.2／§2.3 同包處置。
