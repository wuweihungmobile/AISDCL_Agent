## 3. 回滾步驟（Step-by-Step）

### Step 1: 回滾決策（{N 分鐘}）

```
1.1 確認回滾觸發條件已達標
    - 查看監控儀表板：{URL}
    - 確認觸發條件符合 RB-TRIG-{NNN}

1.2 🔴 Human 確認：回滾授權（{N 分鐘內必須決定}）
    - 決策者：{角色}
    - 授權方式：{Slack 命令 / 操作介面}
```

### Step 2: 流量回滾（{N 分鐘}）

```
2.1 立即停止新流量進入新系統
    - 命令: {切換命令}
    - 預期: 新系統收到 0% 流量

2.2 將 100% 流量切回舊系統
    - 命令: {路由命令}
    - 驗證: curl {舊系統健康端點}
    - 預期: HTTP 200

2.3 確認舊系統正常運行
    - 監控：錯誤率 < {%}，P95 < {N}ms
    - 冒煙測試：{測試命令}
```

### Step 3: 資料回滾（若需要）

```
3.1 評估資料狀態
    - 雙寫期間：舊系統資料仍為主，無需回滾
    - 單寫新系統期間：需從快照還原
    
3.2 從快照還原（若需要）
    - 快照位置: {storage path}
    - 還原命令: {命令}
    - 預計時間: {N 分鐘}
    - ⚠️ 警告：此操作將丟失快照後的新資料

3.3 資料完整性驗證
    - 執行: DATA-INTEGRITY-TEST 全套
    - 標準: 差異 = 0 與快照一致
```

### Step 4: 回滾後驗證（{N 分鐘}）

```
4.1 業務功能冒煙測試
    - 執行: {測試腳本}
    - 標準: 所有關鍵業務流程通過

4.2 監控觀察期（{N 分鐘}）
    - 錯誤率穩定 < {%}
    - P95 延遲 < {N}ms
    - 無異常事件

4.3 通知所有利害關係人
    - 訊息: "系統已回滾至舊版本，原因：{觸發條件}"
    - 頻道: {Slack/Email}

4.4 🔴 Human 確認：回滾完成，系統穩定
```
