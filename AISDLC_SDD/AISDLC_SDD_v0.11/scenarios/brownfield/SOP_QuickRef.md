# Brownfield Project - 快速參考指南
# Quick Reference Guide

**版本**: v0.01
**閱讀時間**: 5 分鐘
**適用情境**: 既有系統修改、功能增強、Bug 修復

---

## 🎯 一頁總覽

### 適用場景
✅ 在既有系統增加新功能
✅ 修改現有功能邏輯
✅ 技術債務改善
✅ Bug 修復與補丁
✅ 功能停用/刪除（Deprecation）
✅ 跨平台擴展（Web → Mobile/Desktop）
✅ 合規驅動變更

### 不適用場景
❌ 全新專案（請用 Greenfield）
❌ 大規模程式碼重構（請用 Refactoring）
❌ 僅效能優化（請用 Performance）
❌ 全技術棧遷移（請用 Migration）

### 📌 情境區分指引
| 你的需求 | 適用情境 |
|---------|---------|
| 在既有系統修 Bug / 加功能 | **Brownfield** ✅ |
| 大規模程式碼重構 / 降技術債 | Refactoring |
| 全技術棧遷移（前後端+DB） | Migration |
| 重構 + 順便加新功能 | Refactoring + Greenfield 組合 |
| 舊系統維護 + 部分重構 | **Brownfield** + Refactoring 組合 |

## ⚠️ Brownfield 特殊注意

### 黃金法則

```yaml
1. 先理解，再修改
   ❌ 直接改 code
   ✅ 先分析程式碼 → 理解邏輯 → 規劃修改

2. 最小影響原則
   ❌ 大範圍重構
   ✅ 只改必要部分，隔離影響

3. 保持向後相容
   ❌ Breaking changes
   ✅ 漸進式改進，保留舊介面

4. 充分測試
   ❌ 手動測試幾個案例
   ✅ 回歸測試 + 新功能測試

5. 功能停用前必做依賴普查（新增）
   ❌ 直接刪除代碼
   ✅ 普查代碼/外部API/DB FK/SEO 依賴 → 確認資料保留合規 → 再移除

6. 跨模組重用前先做架構決策（新增）
   ❌ 直接讓模組 A 依賴模組 B 的 Service
   ✅ 評估直接依賴 vs 抽象共用層 → 複用 2+ 次選共用層 → 記錄 ADR
```

## 📊 影響分析矩陣

| 變更類型 | 風險等級 | 測試策略 | 部署建議 |
|---------|---------|---------|---------|
| UI 調整 | 🟢 低 | 前端測試 + 視覺回歸 | 直接部署 |
| 新增功能 | 🟡 中 | 單元+整合測試 | Feature Flag |
| 修改邏輯 | 🟡 中 | 回歸測試 | 灰度發布 |
| 資料庫變更 | 🔴 高 | 完整測試 + 資料遷移測試 | 藍綠部署 |
| API 變更 | 🔴 高 | API 測試 + 相容性測試 | 版本控制 |
| 功能停用 | 🔴 高 | 回歸測試 + 依賴檢查 | 漸進停用 |
| 跨平台擴展 | 🟡 中 | 跨平台整合測試 | 分階段發布 |
| 合規變更 | 🔴 高 | 合規驗證 + 審計追蹤 | 強制部署 |

## 🎯 快速決策樹

```
修改既有系統時:

Q1: 會影響現有功能嗎？
├─ 是 → 需要回歸測試 + Feature Flag
└─ 否 → 可以獨立開發和測試

Q2: 會變更資料庫 Schema 嗎？
├─ 是 → 需要資料遷移腳本 + Rollback Plan
└─ 否 → 正常部署流程

Q3: 會變更 API 介面嗎？
├─ 是 → 需要版本控制或向後相容設計
└─ 否 → 內部變更，影響較小

Q3.5: 是否跨模組重用既有整合？（新增）
├─ 是 → 評估抽象化決策：見 SOP.md 步驟 4.3「共用服務抽象化決策指引」
└─ 否 → 繼續

Q4: 是否為功能停用/刪除？
├─ 是 → 🔴 先執行「依賴普查」+ 「資料保留合規確認」→ 參考情境 E
└─ 否 → 繼續

Q5: 是否涉及跨平台（Mobile/Desktop）？
├─ 是 → 載入 sd-mobile-architect，確認「新平台前置作業清單」，參考情境 F
└─ 否 → 繼續

Q6: 是否為合規/法規驅動？
├─ 是 → 載入 compliance-officer，參考情境 G
└─ 否 → 繼續

Q7: 有充分的測試嗎？
├─ 是 → 可以信心部署
└─ 否 → 補充測試案例
```

## 🛠️ 實作建議

### 新增功能 (建議模式)

```yaml
策略: 隔離新舊程式碼

範例 - 增加優惠券功能:

❌ 錯誤做法:
直接修改既有的 checkout.js，混入優惠券邏輯

✅ 正確做法:
1. 建立新模組 coupon.service.js
2. checkout.js 僅呼叫 coupon API
3. 使用 Feature Flag 控制啟用
4. 新舊邏輯可以快速切換

程式碼:
if (featureFlags.couponEnabled) {
  discount = await couponService.apply(cart);
} else {
  discount = 0; // 舊邏輯
}
```

### 修改邏輯 (建議模式)

```yaml
策略: 擴展而非修改 (Open/Closed Principle)

範例 - 修改訂單狀態機:

❌ 錯誤做法:
直接改 order.updateStatus() 函數

✅ 正確做法:
1. 保留原有函數
2. 新增 order.updateStatusV2()
3. 逐步遷移呼叫者
4. 確認無問題後移除舊函數
```

## ⚠️ 常見陷阱

### 1. 未充分理解就修改
```
症狀: 改了 A 導致 B 壞掉

預防:
- 使用依賴分析工具
- 搜尋全域引用
- 跑完整測試套件
```

### 2. 破壞向後相容性
```
症狀: API 變更導致客戶端錯誤

預防:
- API 版本控制 (/api/v1, /api/v2)
- Deprecation 機制
- 充分的遷移期
```

### 3. 資料遷移失敗
```
症狀: 部署後資料不一致

預防:
- 先在 staging 環境測試遷移
- 準備 Rollback 腳本
- 資料備份
```

### 4. 功能停用遺漏隱性依賴（新增）
```
症狀: 刪除模組後其他功能報錯（共用組件消失）

預防:
- 停用前執行完整依賴普查（SOP.md 情境 E）
- grep 全專案搜尋被停用模組的引用
- 確認資料保留合規（不可直接刪法規要求保留的資料）
```

### 5. 跨模組重用造成高耦合（新增）
```
症狀: 修改電商模組意外破壞民宿付款功能

預防:
- 2+ 模組重用時提取共用抽象層
- 記錄 ADR 說明架構決策
- 多領域系統 Coupling 評分依特殊指引計算
```

### 6. 第三方 Webhook 靜默失敗（新增）
```
症狀: Stripe 付款成功但訂單狀態未更新（Webhook 失敗但無告警）

預防:
- 部署後設定 Webhook 事件監控
- 監控「無 Webhook 事件但有業務活動」告警
- 48 小時內每日手動檢查第三方 Dashboard
```

## 📋 Pre-deployment Checklist

```yaml
程式碼:
□ Code Review 通過
□ 符合 Coding Standards
□ 無 console.log / debugger
□ 依賴版本鎖定

測試:
□ 單元測試通過
□ 整合測試通過
□ 回歸測試通過
□ 手動測試關鍵路徑

文檔:
□ CHANGELOG 更新
□ API 文檔更新（如有變更）
□ Runbook 準備（部署步驟）

部署:
□ Rollback Plan 準備
□ 資料庫遷移腳本測試
□ 監控和告警就緒
□ Stakeholder 已通知
```
