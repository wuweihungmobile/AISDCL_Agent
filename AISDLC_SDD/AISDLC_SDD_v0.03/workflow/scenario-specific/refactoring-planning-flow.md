# Refactoring Planning Flow
# 程式碼重構規劃流程

## Workflow 名稱
**refactoring-planning-flow** - 代碼重構系統規劃流程

## 描述
系統性規劃代碼重構，包含品質分析、目標設定、策略制定、逐步重構、驗證和前後對比。

## 適用場景
- **使用時機**：代碼品質改善、技術債清理、架構優化、部分技術棧替換（單層框架替換）
- **適用專案**：維護專案、Legacy 系統改造、代碼質量提升、單層框架替換
- **執行頻率**：按需執行或定期（每季度）
- **⚠️ 不適用**：全技術棧遷移（前後端+DB 同時替換）→ 請使用 [Migration SOP](../../scenarios/migration/SOP.md)

## 觸發條件
- 代碼品質問題嚴重
- 維護成本過高
- 技術債累積到臨界點
- 部分技術棧替換（如僅換前端框架、僅換後端框架、僅換 DB）

---

# 角色與責任

## 主要負責人
**Agent 角色**：SD (System Designer) + Code-Analyzer
**責任**：代碼品質分析、重構策略制定

## 參與者
- **Dev-Senior**：重構實作指導
- **QA**：測試保護網建立
- **Technical-Writer**：文檔更新
- **SA** (X-Large 規模)：需求重新分析與業務邏輯提取
- **BA** (X-Large 規模)：業務邏輯完整性驗證
- **DevOps** (技術棧遷移時)：CI/CD 重建與部署策略
- **Mobile-Architect** (涉及行動平台時)：行動端架構設計

## SDD SCG 閘門整合（v0.01）

> 重構以 Business Invariants（INV-XXX）為邊界，確保重構前後業務行為不變。

| 步驟 | 對應 SCG 閘門 | 強制產出 |
|------|-------------|---------|
| 業務不變量提取 | **🔴 SCG-0 凍結** | INVARIANT-SPEC（INV-XXX 清單） |
| 重構設計 | **SCG-1 準備** | 重構 ADR + Strangler Fig 策略 |
| 不變量測試保護 | SCG-1 通過後 | Invariant Test Contract（ITC） |
| 重構實作審查 | **🔴 SCG-4 閘門** | 實作與 Invariants 一致性確認 |

**🔷 整合閘門**：SCG-0（Invariants 凍結）→ SCG-1（重構設計）→ SCG-4（PR 審查）
**📌 SDD 規則**：參考 `scenarios/refactoring/SDD_REFACTORING_ENHANCEMENT.md`


# 執行步驟

## 步驟 1：代碼品質深度分析 (1-1.5 小時)
**執行者**：Code-Analyzer + SD
**🆕 技術棧遷移時額外載入**：Performance-Engineer（效能基準線建立）

**作業內容**：
1. Code Smell 檢測
2. 架構問題識別
3. 可測試性分析
4. 技術債量化
5. 效能熱點分析
6. 🆕 效能基準線建立（技術棧遷移時：回應時間、吞吐量、資源使用率）

**確認點** 🔴：品質分析確認
- 審查品質儀表板
- 確認問題優先級
- 補充背景資訊

**產出**：代碼品質分析報告、Code Smell 清單、技術債評估

## 步驟 2：重構目標設定與範圍界定 (30-40 分鐘)
**執行者**：SD + Dev-Senior

**作業內容**：
1. 設定 SMART 目標
2. 劃分重構範圍
3. 階段劃分（Phase 1/2/3...）
4. 評估投資回報
5. 識別風險

**確認點** 🔴：目標與範圍確認
- 審查重構目標
- 確認階段規劃
- 確認時程可行性

**產出**：重構目標文件、階段規劃、ROI 分析

## 步驟 3：重構策略制定 (1-1.5 小時)
**執行者**：SD + Dev-Senior

**作業內容**：
1. 選擇重構模式（絞殺者/分支抽象/平行運行等）
2. 設計重構技術手法
3. 設計測試策略
4. 制定風險緩解措施

**確認點** 🔴：策略確認
- 審查重構策略
- 確認技術手法
- 確認測試策略

**產出**：重構策略文件、技術手法指南、測試策略

## 步驟 4：逐步重構實作指引 (40-60 分鐘)
**執行者**：Dev-Senior

**作業內容**：
1. 拆解重構步驟
2. 設計檢查清單
3. 提供程式碼範例
4. 識別常見陷阱

**確認點** 🔴：實作指引確認
- 審查步驟拆解
- 確認檢查清單完整
- 確認程式碼範例

**產出**：重構實作計畫、步驟檢查清單、程式碼範例

## 步驟 5：驗證與品質確認 (30-40 分鐘)
**執行者**：QA + Code-Analyzer

**作業內容**：
1. 設計驗證策略
2. 定義品質指標基準線
3. 設計自動化驗證
4. 設定驗收標準

**確認點** 🔴：驗證計畫確認

**產出**：驗證計畫、品質指標基準線、驗收標準

## 步驟 6：前後對比與成果展示 (30 分鐘)
**執行者**：Code-Analyzer + Technical-Writer

**作業內容**：
1. 生成對比報告
2. 量化改善指標
3. 程式碼範例對比
4. ROI 計算

**產出**：重構成果報告、前後對比分析

## 步驟 7：部分技術棧替換專項（僅單層技術棧替換時）
**執行者**：SD + SA + Dev-Senior
**🆕 涉及行動平台時額外載入**：Mobile-Architect、Integration-Specialist（硬體整合）

> **⚠️ 全技術棧遷移（前後端+DB 同時替換）請使用 [Migration SOP](../../scenarios/migration/SOP.md)**
> 本步驟適用於部分技術棧替換（如僅換前端框架、僅換後端框架、僅換 DB），
> 提供框架映射與業務邏輯提取指引。

**作業內容**：
1. 替換層的框架映射表（舊→新元件/API/Schema 對應）
2. 第三方依賴替代方案
3. 業務邏輯提取與驗證
4. 資料庫 Schema 轉換規劃（僅涉及 DB 替換時，觸發 `/database-migration`）
5. 平台擴展架構設計（如新增 Android/macOS，觸發 `/mobile-development`）
6. 🆕 硬體整合評估（掃碼器、NFC、藍牙等，觸發 Integration-Specialist）

**與 SOP 階段的對應關係**：
| Workflow 步驟 7 子項 | 對應 SOP 階段 | 說明 |
|---------------------|-------------|------|
| 1-3 框架映射與業務邏輯 | SOP 階段 2 步驟 2.5.1 | 技術棧相容性分析 |
| 4 DB 轉換 | SOP 階段 2 步驟 2.5.2 → 階段 4 步驟 4.2.1 Phase B | 分析→策略→執行 |
| 5-6 平台擴展 | SOP 階段 2 步驟 2.5.3 → 階段 4 步驟 4.2.1 Phase E | 分析→架構→開發 |

**確認點** 🔴：技術棧替換映射確認
- 審查映射完整性
- 確認業務邏輯無遺漏
- 確認替換策略可行（DB/API/前端逐層驗證）

**產出**：技術棧替換映射報告、DB 遷移計畫（如適用）、業務邏輯清單

## 步驟 8：知識沉澱與回顧 (30 分鐘)
**執行者**：Technical-Writer + SD

**作業內容**：
1. 彙整重構過程中的經驗教訓（Lessons Learned）
2. 更新重構 Playbook（成功模式與失敗案例）
3. 建立團隊知識庫條目
4. 重構前後指標對比總結
5. 後續建議（如未完成項目、長期改善方向）

**產出**：經驗教訓文檔、Playbook 更新紀錄、後續建議清單

# 輸出與交付

## 主要交付物
- 代碼品質分析報告（含 Code Smell 清單、技術債評估）
- 重構目標文件（含 SMART 目標、ROI 分析）
- 重構策略文件（含技術手法、風險緩解）
- 重構實作計畫（含步驟檢查清單）
- 驗證計畫（含品質指標基準線、驗收標準）
- 前後對比報告（含量化改善指標）
- 技術棧遷移映射報告（僅技術棧遷移時）
- 經驗教訓文檔與 Playbook 更新紀錄

## 交付標準
- 目標明確可量化
- 策略可執行
- 風險可控
- ROI 為正
