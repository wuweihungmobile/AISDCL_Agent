# =============================================================================
# Workflow 基本資訊
# =============================================================================

## Workflow 名稱
**使用者故事與系統設計工作流程 (User Story and System Design)**

## 描述
此工作流程接收來自需求驗證與文檔化的正式 PRD 和 FRD，將其轉化為：
1. **具體的使用者故事（User Stories）**：以使用者價值為導向的開發任務
2. **詳細的驗收標準（Acceptance Criteria）**：明確的測試和驗證標準
3. **系統設計規範（SRD）**：完整的技術架構和實現指導
4. **開發計畫**：可執行的 Sprint 規劃和資源配置

強調：
- **使用者價值導向**：每個故事都有明確的業務價值
- **技術可行性**：設計方案經過充分驗證
- **場景適配**：根據不同開發場景應用特定設計模式
- **雙主要 Agent 協作**：SA 和 SD 平等協作，確保需求和技術的完美結合

## 適用場景

### 通用開發場景
- **Greenfield Project**：新專案的完整設計（從零開始）
- **Brownfield Project**：現有系統的增量設計（考慮現有架構）
- **Refactoring**：重構的設計規範（保持功能不變，優化架構）

### 專業場景
- **Integration**：第三方整合的介面設計和資料流設計
- **Performance**：性能優化的設計策略和監控設計
- **Testing**：測試驅動的設計（TDD）和可測試性設計
- **DevOps**：基礎設施即代碼設計和 CI/CD 流程設計
- **Documentation**：文檔系統的資訊架構設計
- **Frontend**：前端架構和組件設計
- **Backend**：後端服務架構和 API 設計

## 觸發條件
- `validation-documentation` workflow 完成並交付正式文檔
- PRD 和 FRD 已通過所有驗證和人類確認
- 需要開始具體的開發規劃和系統設計時
- 技術團隊準備就緒，可開始設計工作

## 步驟 1：Epic 拆解與使用者故事映射
**描述**：將 FRD 中的功能需求拆解為 Epics 和具體的使用者故事

**執行者**：SA Agent (主導)、PM/PO Agent (價值指導)

**具體作業**：

### 1.1 Epic 識別與定義
- **基於 FRD 識別主要功能模塊**：
  - 將相關功能需求組合為 Epic
  - 每個 Epic 代表一個大的功能領域
  - Epic 大小適合 1-3 個 Sprint 完成

- **為每個 Epic 定義業務價值**：
  - 業務價值陳述（Business Value Statement）
  - 目標使用者群體
  - 預期業務成果（如：提升轉換率 10%）

- **建立 Epic 間的依賴關係**：
  - 識別前置 Epic（必須先完成的）
  - 識別可並行 Epic
  - 建立 Epic 依賴圖

### 1.2 使用者故事分解

**標準格式**：
```
As a [使用者角色]
I want to [功能描述]
So that [業務價值/目的]
```

**分解原則**：
- **獨立性（Independent）**：故事之間盡量獨立
- **可協商（Negotiable）**：細節可討論
- **有價值（Valuable）**：對使用者有明確價值
- **可估算（Estimable）**：可評估工作量
- **小型化（Small）**：適合單個 Sprint
- **可測試（Testable）**：有明確驗收標準

**粒度控制**：
- 單個故事：1-5 Story Points
- 避免過大（>8 points）或過小（<0.5 points）
- 複雜故事進一步拆分

### 1.3 故事編號與分類

**編號規範**：
- Epic: `EP-001`, `EP-002`, ...
- User Story: `US-001`, `US-002`, ...
- Sub-task (如需要): `ST-001-01`, `ST-001-02`, ...

**分類維度**：
- **功能模塊**：登入、儀表板、報表等
- **優先級**：P0 (Must Have), P1 (Should Have), P2 (Could Have)
- **故事類型**：Feature (功能), Bug Fix (修復), Tech Debt (技術債), Spike (探索)

### 1.4 初步工作量估算

**估算方法**（與 Dev-Senior 協作）：
- **Planning Poker**：團隊共識估算
- **Story Points**：相對複雜度（Fibonacci: 1, 2, 3, 5, 8, 13）
- **T-shirt Sizing**：XS, S, M, L, XL（初步快速估算）

**估算考量**：
- 技術複雜度
- 未知因素
- 依賴關係
- 團隊經驗

### 1.5 建立故事與需求的映射關係

**追蹤矩陣更新**：
| FRD 需求 ID | Epic ID | User Story ID | 故事描述 | Story Points | 優先級 | Sprint |
|-------------|---------|---------------|----------|--------------|--------|---------|
| FR-001 | EP-001 | US-001 | ... | 3 | P0 | Sprint 1 |
| FR-002 | EP-001 | US-002 | ... | 5 | P0 | Sprint 1 |

**🔴【人機協作確認點 1】使用者故事映射確認**：
- **暫停流程**，呈現故事映射結果
- **呈現內容**：
  ```
  ## Epic 分解結構

  ### EP-001: [Epic 名稱]
  - **業務價值**：[描述]
  - **目標使用者**：[角色]
  - **預期成果**：[量化指標]
  - **包含故事**：US-001, US-002, US-003 (共 3 個)
  - **預估 Story Points**：13 points
  - **依賴**：無 / 依賴 EP-XXX

  ### EP-002: [Epic 名稱]
  ...

  ## 使用者故事清單（按優先級）

  ### P0 - Must Have (共 X 個故事)
  **US-001**: [故事標題]
  - As a [角色]
  - I want to [功能]
  - So that [價值]
  - Story Points: 3
  - 依賴: 無

  **US-002**: [故事標題]
  ...

  ### P1 - Should Have (共 Y 個故事)
  ...

  ## 映射關係圖
  [視覺化呈現：FRD 需求 → Epic → User Story]

  ## 工作量估算摘要
  - 總 Story Points: X points
  - 預估 Sprint 數: Y sprints (假設每 Sprint velocity = Z points)
  - P0 故事: A points
  - P1 故事: B points
  - P2 故事: C points
  ```

- **人類需要確認（使用編號選項）**：
  ```
  請評估使用者故事映射並選擇：

  1. ✅ Epic 分解合理，故事定義準確，粒度適當
  2. 📝 Epic 分解合理，但以下故事需調整：
     [請列出故事 ID 和調整建議]
  3. 🔄 某些 Epic 的價值定位需重新考慮：
     [請說明哪些 Epic 和調整方向]
  4. ✂️ 故事粒度過大，需進一步拆分：
     [請列出需拆分的故事 ID]
  5. 🔗 故事粒度過小，建議合併：
     [請列出需合併的故事 ID]
  6. 💬 其他情況：[請說明]

  您的選擇：___

  ## 工作量估算確認
  總 Story Points [X] 是否合理？
    [1=合理 / 2=過於樂觀，建議增加 ___% / 3=過於保守，可減少 ___%]

  預估 Sprint 數 [Y] 是否可接受？
    [1=可接受 / 2=需壓縮到 ___ sprints / 3=需延長到 ___ sprints]
  ```

**檢查點**：
- [ ] Epic 和使用者故事分解完整
- [ ] **人類使用者已確認故事映射的合理性**
- [ ] 每個故事都有明確的業務價值陳述
- [ ] 故事粒度適合開發實施（1-5 points）
- [ ] 故事與需求的映射關係清晰
- [ ] 工作量估算獲得團隊認同
- [ ] Epic 依賴關係已識別

**品質標準**：
- 每個使用者故事都有清晰的業務價值（So that 子句）
- **故事定義經人類確認符合使用者需求**
- 映射關係完整且可追蹤（100% FRD 需求覆蓋）
- **INVEST 原則達成率 ≥ 90%**

## 步驟 2：驗收標準定義與測試場景識別
**描述**：為每個使用者故事定義詳細的驗收標準和測試場景

**執行者**：SA Agent (主導)、QA Lead (測試專業)

**具體作業**：

### 2.1 驗收標準制定

**Given-When-Then 格式**：
```
AC-001-1: [驗收標準標題]
Given [前置條件/上下文]
When [使用者操作/觸發事件]
Then [預期結果/系統行為]
```

**編號規範**：
- 格式：`AC-{US編號}-{序號}`
- 範例：`AC-001-1`, `AC-001-2`, `AC-002-1`

**制定原則**：
- **明確性**：無歧義，可直接測試
- **可測試性**：有明確的驗證方法
- **完整性**：覆蓋正常和異常場景
- **獨立性**：每個 AC 可獨立測試

### 2.2 邊界條件定義

**正常流程驗收條件**：
- 標準使用場景的預期行為
- 成功路徑的驗證

**異常情況處理**：
- 錯誤輸入的處理
- 系統異常的反饋
- 使用者錯誤操作的提示

**邊界值和極限情況測試**：
- 最小值、最大值測試
- 空值、null 處理
- 特殊字符處理
- 並發和高負載情況

### 2.3 測試場景規劃

（與 QA Lead 協作）

**測試場景類型**：
1. **Smoke Test**：基本功能驗證
2. **Functional Test**：完整功能測試
3. **Regression Test**：回歸測試
4. **Integration Test**：集成測試
5. **Performance Test**：性能測試（如適用）
6. **Security Test**：安全測試（如適用）

**自動化測試可行性評估**：
- **高自動化優先級**：
  - API 測試
  - 單元測試
  - 回歸測試套件
- **中自動化優先級**：
  - UI 測試（關鍵路徑）
  - 集成測試
- **手動測試**：
  - 探索性測試
  - 使用者體驗測試
  - 特殊場景驗證

### 2.4 驗收標準可測試性驗證

**檢查清單**：
- [ ] 每個 AC 都有明確的驗證方法
- [ ] 測試資料需求已定義
- [ ] 測試環境需求已明確
- [ ] 自動化測試覆蓋率目標已設定
- [ ] 測試工具和框架已選定

# 協作與整合
# =============================================================================

## 前置 Workflows
- **validation-documentation**：提供經驗證的 PRD 和 FRD 文檔

## 後續 Workflows
- **development-implementation**：基於使用者故事和 SRD 進行具體開發
- **acceptance-testing**：基於驗收標準進行測試驗證
- **api-specification**：（並行或後續）生成詳細的 API 規格文檔

## 並行 Workflows
*無強制並行 workflow，但 API 規格可在本 workflow 執行期間並行撰寫*

## Agent 協作規則

- **雙主要 Agent 模式**：SA Agent 和 SD Agent 平等協作
  - SA Agent 主導：使用者故事、驗收標準
  - SD Agent 主導：系統設計、技術規範
  - 共同決策：技術複雜度評估、設計取捨

- **設計協作**：技術設計需要業務需求的充分理解，確保技術方案符合業務目標

- **人機協作協議**：關鍵設計決策需要人類確認，確保方案的合理性和可接受性

- **場景特定協作**：根據適用場景動態引入專業 Agent
  - Integration → Integration Specialist
  - Performance → Performance Engineer
  - DevOps → DevOps Engineer
  - Web/Mobile → 平台特化 SD Agent

## 場景特定工作流調整

### Greenfield Project
- 更注重架構設計的前瞻性和可擴展性
- 技術選型更靈活
- 更多的設計自由度

### Brownfield Project
- 必須評估現有架構和代碼
- 增量設計，考慮向下相容
- 重點：與現有系統的整合

### Refactoring
- 明確保留功能和重構範圍
- 設計漸進式重構路徑
- 重點：改進架構，不改變功能

### Integration
- Integration Specialist 深度參與
- 重點：API Gateway、資料轉換、錯誤處理

### Performance
- Performance Engineer 深度參與
- 重點：快取策略、資料庫優化、非同步處理

### DevOps
- DevOps Engineer 深度參與
- 重點：容器化、CI/CD、監控架構

# 品質控制與監控
# =============================================================================

## 品質檢查點

- **使用者故事完成後**：檢查故事的業務價值和可執行性（INVEST 原則）
- **系統設計完成後**：檢查架構的合理性和技術可行性
- **最終交付前**：進行完整的品質審查和可執行性驗證
- **多 Agent 驗證後**：確認共識達成或分歧已解決

## 風險控制

### 風險 1：故事粒度問題
- **緩解措施**：建立明確的故事拆分標準（1-5 Story Points）
- **檢測機制**：故事點分布監控

### 風險 2：技術複雜度過高
- **緩解措施**：及時識別高風險技術點，制定 POC 計畫
- **檢測機制**：技術風險評估矩陣

### 風險 3：設計與需求不一致
- **緩解措施**：SA 和 SD 持續協作，定期對齊
- **檢測機制**：需求追蹤矩陣驗證

### 風險 4：計畫不可行
- **緩解措施**：多輪評估，團隊 Velocity 數據支持
- **檢測機制**：Sprint 規劃審查

### 風險 5：API 規格遺漏
- **緩解措施**：強制檢查點，系統包含 API 時必須完成 API 規格
- **檢測機制**：驗收條件檢查清單

## 成功指標

- **故事完整率**：100% 的功能需求都轉化為使用者故事
- **驗收標準覆蓋率**：100% 的使用者故事都有明確的驗收標準（≥ 3 AC/Story）
- **設計評審通過率**：系統設計通過所有技術和業務評審
- **計畫執行成功率**：開發計畫的實際執行符合預期 ≥ 90%
- **開發團隊滿意度**：對交付物的滿意度 ≥ 4.5/5.0
- **INVEST 原則達成率**：≥ 90% 的故事符合 INVEST 原則
- **API 規格完整性**：系統包含 API 時，100% API 端點有詳細規格
