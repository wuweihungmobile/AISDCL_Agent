## 🎯 文檔目的

本範本協助 **QA-Tester Agent** 在 **Stage 9（測試與驗證）** 執行效能測試時，系統化規劃並驗證系統效能需求（NFR-PERF），確保上線前達成效能目標。

**核心原則**: **Performance Testing Early（提前效能測試，避免上線後效能問題）**

## 📊 效能測試類型（4 大類）

### 1️⃣ 負載測試（Load Testing）

**定義**: 模擬預期使用者負載，驗證系統在正常與峰值負載下的表現

**目標**:
- 驗證系統能否滿足 NFR-PERF 效能需求
- 識別效能瓶頸（CPU、Memory、Database、Network）
- 建立效能基準（Baseline）

**測試場景**:
- **正常負載**: 模擬日常平均使用者數量
- **峰值負載**: 模擬尖峰時段（如促銷活動、節日）使用者數量

**測試指標**:
| 指標 | 目標值 | 測試方法 |
|------|--------|---------|
| **回應時間 (Response Time)** | < 200ms (p95) | API 監控 |
| **吞吐量 (Throughput)** | > 1000 requests/sec | 負載測試工具 |
| **錯誤率 (Error Rate)** | < 0.1% | 錯誤日誌統計 |
| **並發使用者數 (Concurrent Users)** | > 1000 users | 虛擬使用者模擬 |

---

### 2️⃣ 壓力測試（Stress Testing）

**定義**: 超過系統設計容量的極限測試，找出系統崩潰點

**目標**:
- 識別系統最大承載能力
- 驗證系統在極限負載下的降級行為
- 測試故障恢復能力（Failover & Recovery）

**測試場景**:
- **超載測試**: 持續增加負載直到系統崩潰
- **尖峰測試**: 短時間內突然增加大量負載
- **持久測試**: 長時間高負載運行（檢測記憶體洩漏）

**測試指標**:
| 指標 | 觀察項目 | 預期行為 |
|------|---------|---------|
| **崩潰點 (Breaking Point)** | 最大 RPS | > 2000 requests/sec |
| **降級行為 (Degradation)** | 超載時回應時間 | 優雅降級（非直接崩潰） |
| **恢復時間 (Recovery Time)** | 負載降低後恢復時間 | < 5 分鐘 |
| **記憶體洩漏 (Memory Leak)** | 長時間運行記憶體變化 | 記憶體使用穩定 |

---

### 3️⃣ 容量規劃（Capacity Planning）

**定義**: 評估系統資源需求，規劃未來擴容策略

**目標**:
- 預測系統資源需求（CPU、Memory、Storage、Network）
- 規劃 Auto Scaling 策略
- 評估成本效益（Cost-Performance Trade-off）

**測試場景**:
- **資源使用率測試**: 不同負載下資源使用率
- **擴容測試**: 驗證 Auto Scaling 機制
- **成本模擬**: 預估未來 6-12 個月資源成本

**測試指標**:
| 資源 | 當前使用率 | 擴容閾值 | 預估成長率 | 預估成本 |
|------|-----------|---------|-----------|---------|
| **CPU** | 40% | 70% | 每月 +10% | $500/月 |
| **Memory** | 50% | 80% | 每月 +8% | $300/月 |
| **Database** | 30% | 70% | 每月 +15% | $800/月 |
| **Storage** | 20% | 80% | 每月 +20% | $200/月 |

---

### 4️⃣ 耐久測試（Endurance Testing / Soak Testing）

**定義**: 長時間運行系統，檢測記憶體洩漏與效能衰退

**目標**:
- 檢測記憶體洩漏（Memory Leak）
- 驗證系統穩定性（長時間運行無崩潰）
- 識別效能衰退問題（Performance Degradation）

**測試場景**:
- **長時間運行**: 持續運行 24-72 小時
- **正常負載**: 模擬日常平均負載
- **監控資源**: 持續監控 CPU、Memory、Disk、Network

**測試指標**:
| 指標 | 監控週期 | 預期行為 |
|------|---------|---------|
| **記憶體使用率** | 每小時記錄 | 無持續上升趨勢 |
| **回應時間** | 每小時記錄 | 無明顯衰退 |
| **錯誤率** | 每小時記錄 | 維持 < 0.1% |
| **Database 連線數** | 每小時記錄 | 無連線洩漏 |

### 測試場景設計

#### 場景 1: 負載測試 - 正常負載

**測試目標**: 驗證系統在日常負載下的效能表現

**負載配置**:
- **虛擬使用者數**: 500 users
- **持續時間**: 30 分鐘
- **Ramp-up 時間**: 5 分鐘（逐步增加至 500 users）
- **請求分佈**:
  - 60% GET /api/products（商品列表）
  - 20% POST /api/orders（建立訂單）
  - 15% GET /api/orders/:id（查詢訂單）
  - 5% DELETE /api/orders/:id（取消訂單）

**驗收標準**:
- [ ] p95 回應時間 < 200ms
- [ ] p99 回應時間 < 500ms
- [ ] 錯誤率 < 0.1%
- [ ] CPU 使用率 < 70%
- [ ] Memory 使用率 < 80%

---

#### 場景 2: 負載測試 - 峰值負載

**測試目標**: 驗證系統在尖峰時段的效能表現

**負載配置**:
- **虛擬使用者數**: 1500 users
- **持續時間**: 15 分鐘
- **Ramp-up 時間**: 3 分鐘
- **請求分佈**: 同場景 1

**驗收標準**:
- [ ] p95 回應時間 < 300ms
- [ ] p99 回應時間 < 800ms
- [ ] 錯誤率 < 0.5%
- [ ] Auto Scaling 觸發（增加至 4+ instances）
- [ ] Database Read Replicas 分散負載

---

#### 場景 3: 壓力測試 - 超載測試

**測試目標**: 找出系統崩潰點，驗證降級行為

**負載配置**:
- **虛擬使用者數**: 持續增加（500 → 3000 users）
- **增加速率**: 每分鐘 +200 users
- **持續時間**: 直到系統崩潰或錯誤率 > 5%

**驗收標準**:
- [ ] 崩潰點 > 2000 users
- [ ] 超載時有優雅降級（Rate Limiting 429 回應）
- [ ] 負載降低後 5 分鐘內恢復正常
- [ ] 無資料遺失或損毀

---

#### 場景 4: 耐久測試 - 長時間運行

**測試目標**: 檢測記憶體洩漏與效能衰退

**負載配置**:
- **虛擬使用者數**: 500 users（正常負載）
- **持續時間**: 48 小時
- **監控頻率**: 每 30 分鐘記錄一次指標

**驗收標準**:
- [ ] 48 小時內無系統崩潰
- [ ] Memory 使用率無持續上升趨勢
- [ ] 回應時間無明顯衰退（< 10% 增長）
- [ ] Database 連線數穩定（無連線洩漏）

### 容量規劃建議

**當前容量評估**:
- **當前負載**: 500 concurrent users
- **系統容量**: 2000 concurrent users（壓力測試結果）
- **容量餘裕**: 4x（足夠應付未來 6 個月成長）

**擴容觸發條件**:
- CPU 使用率 > 70%（持續 5 分鐘）
- Memory 使用率 > 80%
- 回應時間 p95 > 300ms

**Auto Scaling 配置建議**:
```yaml
Auto Scaling Policy:
  Min Instances: 2
  Max Instances: 10
  Target CPU: 60%
  Scale Out: +2 instances when CPU > 70%
  Scale In: -1 instance when CPU < 30% (cooldown: 10 min)
```
