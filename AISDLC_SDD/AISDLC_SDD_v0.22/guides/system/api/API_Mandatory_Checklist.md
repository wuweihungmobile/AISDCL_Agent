## 🎯 使用時機

### 必須使用此清單的情況

- ✅ **Stage 5 (SRD 與 API 規格)**: 產出 API Specification 時
- ✅ **Stage 7 (最終驗證)**: 文檔一致性檢查時
- ✅ **任何涉及 API 變更**: 新增、修改、刪除 API 端點時
- ✅ **Code Review**: 審查 API 實作是否符合規格

### 不需要使用的情況

- ❌ 純前端專案（無 API 呼叫）
- ❌ 僅使用第三方 API（無自建 API）

## ✅ Pre-Development 檢查清單

**在開始開發 API 之前，確認以下項目已完成：**

### 1. API 設計基礎 (必要)

- [ ] **API 索引檔案已建立**: `API_Index.md` 列出所有端點
- [ ] **命名規範已確認**: 使用 RESTful 命名（小寫、複數形式、連字號）
- [ ] **版本策略已決定**: URL版本 `/api/v1/` 或 Header版本
- [ ] **認證方式已設計**: JWT / OAuth 2.0 / API Key

### 2. 錯誤處理標準 (必要)

- [ ] **錯誤碼規範已定義**: 參考 `API_Error_Codes.md`
- [ ] **錯誤回應格式統一**: `{ "error": { "code": "", "message": "" } }`
- [ ] **HTTP 狀態碼對應已明確**: 4xx 用戶端錯誤 / 5xx 伺服器錯誤

### 3. 文檔結構 (必要)

- [ ] **使用統一模板**: `API_Specification_Template.md`
- [ ] **每個端點獨立文檔**: `API_{Module}_{Endpoint}.md`

## ✅ 每個 API 端點檢查清單

**每個 API 端點的規格文檔必須包含以下項目：**

### 1. 基本資訊 (必要 - 5項)

| 項目 | 狀態 | 說明 |
|------|------|------|
| [ ] **端點路徑** | 必要 | 如 `POST /api/v1/users` |
| [ ] **HTTP 方法** | 必要 | GET / POST / PUT / PATCH / DELETE |
| [ ] **功能描述** | 必要 | 一句話說明此 API 的用途 |
| [ ] **認證需求** | 必要 | 是否需要認證、所需權限 |
| [ ] **速率限制** | 必要 | 如 `100 requests/min` |

### 2. 請求規格 (必要 - 4項)

| 項目 | 狀態 | 說明 |
|------|------|------|
| [ ] **Headers** | 必要 | Content-Type, Authorization 等 |
| [ ] **Path Parameters** | 視情況 | 如 `/users/{id}` 中的 `id` |
| [ ] **Query Parameters** | 視情況 | 如 `?page=1&limit=10` |
| [ ] **Request Body** | 視情況 | JSON Schema 定義 |

### 3. 回應規格 (必要 - 4項)

| 項目 | 狀態 | 說明 |
|------|------|------|
| [ ] **成功回應** | 必要 | 狀態碼 + 回應格式 + 範例 |
| [ ] **錯誤回應** | 必要 | 所有可能的錯誤碼和說明 |
| [ ] **欄位說明** | 必要 | 每個回應欄位的型別和說明 |
| [ ] **範例** | 必要 | 實際的 JSON 請求/回應範例 |

### 4. 驗證規則 (必要 - 3項)

| 項目 | 狀態 | 說明 |
|------|------|------|
| [ ] **必填欄位** | 必要 | 標記哪些欄位為 required |
| [ ] **資料型別** | 必要 | string / number / boolean / array / object |
| [ ] **驗證限制** | 必要 | 長度、格式、範圍等限制 |

### 5. 追蹤資訊 (建議)

| 項目 | 狀態 | 說明 |
|------|------|------|
| [ ] **關聯 User Story** | 建議 | 如 `US-001` |
| [ ] **關聯測試案例** | 建議 | 如 `TC-API-001` |
| [ ] **版本變更記錄** | 建議 | 何時新增/修改 |

## ✅ Pre-Delivery 檢查清單

**在交付 API 規格文檔之前，執行以下驗證：**

### 1. 完整性檢查 (必要)

- [ ] **所有 API 端點都有文檔**: 無遺漏的 API
- [ ] **API Index 與實際端點一致**: 索引檔案已更新
- [ ] **所有錯誤碼都有定義**: 無未定義的錯誤碼

### 2. 一致性檢查 (必要)

- [ ] **命名風格一致**: 所有端點使用相同命名規範
- [ ] **回應格式一致**: 分頁、錯誤、成功回應格式統一
- [ ] **與 SRD 一致**: API 規格與系統設計文檔一致
- [ ] **與 User Story 對應**: 每個 API 都能追溯到需求

### 3. 品質檢查 (必要)

- [ ] **範例可執行**: 範例請求可實際呼叫
- [ ] **無錯別字和格式錯誤**: 文檔品質良好
- [ ] **技術細節準確**: 資料型別、欄位名稱正確

### 4. 安全檢查 (必要)

- [ ] **敏感資料已標記**: 密碼、Token 等不會在範例中外洩
- [ ] **權限控制已定義**: 每個端點的授權需求明確
- [ ] **速率限制已設定**: 防止濫用的限制已定義

## ⚠️ 常見遺漏項目

**以下是最常被遺漏的項目，請特別注意：**

### Top 5 遺漏項目

| 排名 | 項目 | 影響 | 解決方法 |
|------|------|------|----------|
| 1 | **錯誤回應規格** | 前端無法正確處理錯誤 | 列出所有可能的錯誤碼 |
| 2 | **分頁參數** | 大量資料無法分頁 | 定義 page/limit/offset |
| 3 | **速率限制** | 容易被 DDoS 或濫用 | 每個端點設定限制 |
| 4 | **欄位驗證規則** | 前後端驗證不一致 | 明確定義每個欄位限制 |
| 5 | **認證失敗處理** | 401/403 混淆 | 區分認證失敗和授權失敗 |

### 常見錯誤範例

**❌ 錯誤：沒有定義錯誤回應**
```markdown
## 回應
### 成功回應 (200 OK)
{ "user": { "id": 1, "name": "John" } }
```

**✅ 正確：完整定義錯誤回應**
```markdown
## 回應
### 成功回應 (200 OK)
{ "user": { "id": 1, "name": "John" } }

### 錯誤回應
| 狀態碼 | 錯誤碼 | 說明 |
|--------|--------|------|
| 400 | INVALID_INPUT | 輸入資料格式錯誤 |
| 401 | UNAUTHORIZED | 未提供有效認證 |
| 403 | FORBIDDEN | 無權存取此資源 |
| 404 | USER_NOT_FOUND | 使用者不存在 |
| 500 | INTERNAL_ERROR | 系統內部錯誤 |
```
