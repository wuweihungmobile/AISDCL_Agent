# Tech Stack Selection Flow
# 技術選型流程

## Workflow 名稱
**tech-stack-selection-flow** - 系統性技術選型流程

## 描述
基於需求、團隊技能和專案特性，系統性選擇最適合的技術棧，包含研究、評估、對比和決策。

## 適用場景
- **使用時機**：新專案啟動、技術升級、架構重構
- **適用專案**：Greenfield 專案、技術遷移專案
- **執行頻率**：專案啟動時、重大技術決策時

## 觸發條件
- 專案需求已明確
- 需要選擇技術棧
- 團隊技能已盤點

---

# 角色與責任

## 主要負責人
**Agent 角色**：SD-Architect + Dev-Senior
**責任**：技術研究、方案對比、決策建議

## 參與者
- **PM/PO**：業務需求說明、成本預算
- **DevOps**：基礎設施考量
- **Dev**：實作可行性評估

## SDD SCG 閘門整合（v0.01）

> 技術選型必須以 ADR 記錄每個架構決策，所有 ADR Accepted 後才能通過 SCG-2。

| 步驟 | 對應 SCG 閘門 | 強制產出 |
|------|-------------|---------|
| 技術需求分析 | **SCG-1 準備** | 技術約束清單（輸入 SRD） |
| 技術選型與評估 | **SCG-1/2 準備** | ADR（每個選型決策） |
| 架構可行性驗證 | **🔴 SCG-2 凍結** | ADR 全部 Accepted + C4 Container |

**🔷 整合閘門**：SCG-1（設計凍結準備）→ SCG-2（架構凍結，ADR 全通過）
**📌 SDD 規則**：每個技術選型必須有對應 ADR，使用 `/adr-generate`


# 執行步驟

## 步驟 1：技術需求分析 (30-40 分鐘)
**執行者**：SD-Architect + SA

**作業內容**：
1. 分析功能需求對技術的要求
2. 分析非功能需求（效能/安全/擴展性）
3. 分析整合需求
4. 識別技術約束
5. 定義技術選型標準

**確認點** 🔴：技術需求確認
- 審查技術需求清單
- 確認選型標準

**產出**：技術需求清單、選型標準

## 步驟 2：技術棧研究與候選清單 (1-1.5 小時)
**執行者**：SD-Architect + Dev-Senior

**作業內容**：
1. 前端技術研究
2. 後端技術研究
3. 資料庫技術研究
4. 基礎設施選項研究
5. 第三方服務研究
6. 建立候選清單（每類 2-3 個選項）

**產出**：技術棧候選清單、初步研究報告

## 步驟 3：技術方案對比分析 (1.5-2 小時)
**執行者**：SD-Architect + Dev-Senior

**作業內容**：
1. 建立對比維度（效能/成本/學習曲線/社群/成熟度）
2. 對比前端技術（React vs Vue vs Angular）
3. 對比後端技術（Node.js vs Python vs Java vs Go）
4. 對比資料庫（PostgreSQL vs MySQL vs MongoDB）
5. 評估整合複雜度
6. 評估長期維護成本

**確認點** 🔴：對比分析確認
- 審查對比矩陣
- 確認評估維度完整
- 補充考量因素

**產出**：技術對比矩陣、優缺點分析

## 步驟 4：團隊技能與學習曲線評估 (30-40 分鐘)
**執行者**：SD-Architect + Dev

**作業內容**：
1. 盤點團隊現有技能
2. 評估各技術學習曲線
3. 估算學習時間成本
4. 識別技能 gap
5. 制定培訓計畫（如需要）

**確認點** 🔴：技能評估確認

**產出**：團隊技能矩陣、學習曲線評估、培訓計畫

## 步驟 5：技術驗證（POC/Spike） (1-2 天，可選)
**執行者**：Dev-Senior + Dev

**作業內容**：
1. 識別需要驗證的技術風險
2. 設計 POC 範圍
3. 執行技術 Spike
4. 驗證關鍵技術可行性
5. 記錄驗證結果

**產出**：POC 報告、技術驗證結果

## 步驟 6：成本效益分析 (40-60 分鐘)
**執行者**：SD-Architect + PM/PO

**作業內容**：
1. 計算授權成本
2. 計算基礎設施成本
3. 計算學習成本
4. 計算維護成本
5. 評估長期 ROI

**確認點** 🔴：成本分析確認

**產出**：成本分析報告、ROI 評估

## 步驟 7：技術決策與 ADR (30-40 分鐘)
**執行者**：SD-Architect

**作業內容**：
1. 綜合所有分析結果
2. 提出推薦方案
3. 說明決策理由
4. 識別技術風險和緩解措施
5. 撰寫 ADR（Architecture Decision Record）

**確認點** 🔴：技術決策確認
- 審查推薦方案
- 確認決策理由充分
- 討論風險緩解
- 最終確認技術選擇

**產出**：技術選型報告、ADR、風險緩解計畫

# 輸出與交付

## 主要交付物
- 技術需求清單
- 技術對比矩陣
- 團隊技能評估
- POC 報告（如有）
- 成本分析報告
- 技術選型報告
- Architecture Decision Records (ADR)

## 交付標準
- 技術選擇有充分理由
- 考慮團隊技能
- 成本可接受
- 風險可控
- ADR 完整記錄

## 決策維度權重（範例）
| 維度 | 權重 | 說明 |
|------|------|------|
| 符合需求 | 30% | 功能和非功能需求滿足度 |
| 團隊技能 | 25% | 學習曲線和現有技能匹配度 |
| 成本 | 20% | 總擁有成本（TCO） |
| 生態系統 | 15% | 社群活躍度、函式庫豐富度 |
| 長期維護 | 10% | 技術成熟度、更新頻率 |

# 常見技術選型場景

## 場景 A：初創團隊 MVP
**推薦**：
- 前端：React + Next.js（快速開發）
- 後端：Node.js + Express（全棧 JS）
- 資料庫：PostgreSQL（穩定可靠）
- 部署：Vercel + Railway（簡單快速）

## 場景 B：企業級應用
**推薦**：
- 前端：React + TypeScript
- 後端：Java Spring Boot（成熟穩定）
- 資料庫：PostgreSQL + Redis
- 部署：Kubernetes

## 場景 C：高效能系統
**推薦**：
- 後端：Go / Rust（高效能）
- 資料庫：PostgreSQL + Redis Cluster
- 訊息佇列：Kafka
- 部署：Kubernetes + 自動擴展

# 品質控制

## 決策檢查清單
- [ ] 所有技術需求已涵蓋
- [ ] 至少對比 2-3 個方案
- [ ] 團隊技能已評估
- [ ] 成本分析已完成
- [ ] 關鍵技術已驗證（POC）
- [ ] 技術風險已識別
- [ ] ADR 已撰寫
- [ ] 團隊共識已達成

## 避免的陷阱
- ❌ 盲目追求新技術
- ❌ 忽視團隊學習成本
- ❌ 過度設計
- ❌ 未考慮長期維護
- ❌ 技術選擇無文檔記錄
