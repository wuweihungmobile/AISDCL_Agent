基於 AISDLC v0.09 框架設計的智能需求提取流程，支持多種輸入形式（截圖、文字、混合），通過強化的人機協作機制和零臆測原則確保需求理解準確性。

# =============================================================================
# Workflow 基本資訊
# =============================================================================

## Workflow 名稱
**統一需求提取工作流程 (Unified Requirements Extraction)**

## 描述
此工作流程專門處理各種形式的需求輸入，包括純文字描述、截圖（PPT/Figma/UI 設計稿）、以及混合輸入。核心特色是**"零臆測原則"** - 所有不確定的推斷都通過人機協作點獲得人類確認，確保需求理解準確性，防止 AI 幻覺。

適用於 10 大開發場景的需求收集階段。

## 適用場景
- **Greenfield Project**：新專案的初始需求收集
- **Brownfield Project**：現有系統的需求分析和文檔化
- **Refactoring**：重構前的需求重新梳理
- **Integration**：第三方整合的需求分析

### 輸入類型支援
- **純文字輸入**：使用者需求描述、功能說明、業務流程文字
- **純截圖輸入**：PPT 截圖、Figma 設計稿、原型圖、UI 界面截圖（1-N 張）
- **混合輸入**：截圖配合文字說明
- **多源輸入**：來自不同渠道的多個輸入項

### 需求複雜度
- 單一功能、複雜流程、多模塊需求

## 觸發條件
- 收到任何形式的需求輸入需要分析時
- 需要從視覺材料提取功能需求時
- 多個輸入之間關聯關係不明確時
- 需求資訊不完整需要人類補充時
- 專案啟動或進入需求分析階段

- 主導整個人機協作過程
- 確保零臆測原則執行
- 應用編號選項協議與人類互動

- **BA Agent (Business Analyst)**

  - 責任：協助人機協作確認點管理，確保人類輸入得到正確記錄

  - 配置：`agent/core/03.pm-po-agent-zh.yaml`
  - 責任：提供業務優先級和價值判斷指導

# =============================================================================
# 輸入與前置條件
# =============================================================================

## 支持的輸入類型
### 1. 純文字輸入
- 使用者需求描述
- 功能說明文檔
- 業務流程文字
- Email 或 Slack 訊息中的需求

### 2. 純截圖輸入
- PPT 簡報截圖（1-N 張）
- Figma/Sketch 設計稿
- 原型圖（Wireframe/Mockup）
- UI 界面截圖
- 競品功能截圖

### 3. 混合輸入
- 截圖配合文字說明
- 設計稿 + 業務規則描述
- UI 圖 + 互動流程描述

### 4. 多源輸入
- 來自不同渠道的多個輸入項
- 多位 stakeholder 提供的資訊
- 跨系統的需求彙整

## 輸入處理要求
- 每個輸入項都需要明確編號和分類
- 缺失的背景資訊需要標記
- 輸入間的關聯關係需要識別
- 所有推測內容必須標記並尋求確認

## 前置條件
- SA Agent 具備基本的業務領域理解能力
- 人類使用者可配合進行多輪確認和資訊補充
- 有足夠時間進行充分的人機協作
- 已載入 AISDLC v0.02 agent 配置

## 所需資源
- **工具和系統**：文檔協作平台、截圖查看工具
- **時間資源**：預估 2-4 小時（依輸入複雜度）
- **人力資源**：領域專家、產品負責人可隨時回應

# =============================================================================
# 執行步驟
# =============================================================================

## 步驟 1：輸入接收與初步解析
**描述**：接收各種形式的輸入並進行初步分類和編號

**執行者**：SA Agent (主導)

**具體作業**：
1. **輸入分類與編號**
   - 文字輸入：編號為 `TXT-001`, `TXT-002`...
   - 截圖輸入：編號為 `SCR-001`, `SCR-002`...
   - 混合輸入：標記為 `MIX-001` (包含 TXT + SCR)
   - 記錄輸入的原始形式和來源

2. **初步內容識別**
   - **文字內容**：提取關鍵詞、業務術語、功能描述
   - **截圖內容**：識別 UI 元素、頁面類型、操作流程、視覺層級
   - **記錄可識別的明確資訊**（不進行推測）

3. **輸入完整性評估**
   - 標記資訊完整度（高/中/低）
   - 識別明顯缺失的關鍵資訊
   - **不做推測**，僅標記"資訊不足，需詢問"
   - 準備首輪人機確認

**🔴【人機協作確認點 1】輸入理解與完整性確認**：
- **暫停流程**，呈現解析結果
- **呈現內容**：
  ```
  ## 輸入分類清單
  1. TXT-001: [來源] - [簡短描述]
  2. SCR-001: [來源] - [簡短描述]
  ...

  ## 初步理解
  - 從 TXT-001 識別到：[列出明確可識別的內容]
  - 從 SCR-001 識別到：[列出 UI 元素、頁面特徵]

  ## 關聯推測 (需確認)
  - 可能的關聯：[描述輸入間可能的關係]
  - ⚠️ 此為推測，請確認是否正確
  ```

- **人類需要確認（使用編號選項）**：
  ```
  請選擇以下選項（輸入編號）：

  1. ✅ 輸入分類正確，內容理解準確，輸入完整
  2. 🔄 輸入分類正確，但內容理解有誤，需修正：[請說明]
  3. ➕ 理解正確，但需補充以下資訊：[請說明]
  4. 🔁 需要重新分析，提供更多背景：[請說明]
  5. 💬 其他情況：[請說明]

  您的選擇：___
  ```

**檢查點**：
- [ ] 所有輸入都已正確分類和編號
- [ ] **人類使用者已確認輸入理解準確性**
- [ ] 需要補充的資訊已明確記錄
- [ ] 輸入間關聯關係已獲得人類確認
- [ ] 使用編號選項協議與人類互動

**品質標準**：
- 分類準確且無遺漏
- **人類確認記錄詳細且可追蹤**
- 缺失資訊識別完整
- **零臆測：未經確認的內容明確標記為"推測"**

---

## 步驟 2：需求識別與映射分析
**描述**：從各種輸入中識別可能的需求，分析需求間關係

**執行者**：SA Agent (主導)

**具體作業**：
1. **需求提取策略**
   - **單張截圖分析**：深度識別所有功能點和 UI 元素
   - **多張截圖分析**：判斷是否為同一流程或獨立功能
   - **文字輸入分析**：提取功能需求和業務規則
   - **混合輸入分析**：將文字與截圖內容匹配

2. **需求映射關係判斷**
   - `1 輸入 → 1 需求`：簡單功能
   - `1 輸入 → N 需求`：複雜頁面或多功能描述
   - `N 輸入 → 1 需求`：完整流程的多個環節
   - `N 輸入 → N 需求`：多個獨立功能
   - **標記推測的映射關係，必須獲得確認**

3. **確定性程度標記**
   - ✅ **高確定性**：明確可識別的需求（基於明確的文字或 UI）
   - ⚠️ **中確定性**：需要輕微推斷的需求（基於上下文）
   - ❌ **低確定性**：需要大量假設的需求（**禁止自行推測，必須詢問**）

**🔴【人機協作確認點 2】需求映射與關係確認**：
- **暫停流程**，呈現需求分析結果
- **呈現內容**：
  ```
  ## 需求提取清單

  ### 從 TXT-001 識別的需求：
  - REQ-001: [需求描述] - 確定性：✅ 高
  - REQ-002: [需求描述] - 確定性：⚠️ 中（推測：[說明推測內容]）

  ### 從 SCR-001 識別的需求：
  - REQ-003: [需求描述] - 確定性：✅ 高
  - REQ-004: [需求描述] - 確定性：❌ 低（不確定：[說明不確定點]）

  ## 映射關係分析
  - TXT-001 + SCR-001 → REQ-001 (完整登入流程)
  - SCR-002 → REQ-005, REQ-006 (儀表板包含兩個功能模塊)

  ## 推測內容標記
  ⚠️ 以下內容為推測，請確認：
  1. [推測 1] - 基於 [理由]
  2. [推測 2] - 基於 [理由]
  ```

- **人類需要確認（使用編號選項）**：
  ```
  請選擇以下選項（可多選，用逗號分隔，如：1,3）：

  1. ✅ 需求識別準確，映射關係正確
  2. 🔄 需求識別正確，但映射關係需調整：[請說明]
  3. ❌ 部分需求識別錯誤，需要修正：[請說明]
  4. ➕ 遺漏重要需求，需要補充：[請說明]
  5. 💬 其他情況：[請說明]

  您的選擇：___

  ## 對推測內容的確認
  推測 1: [1=正確 / 2=錯誤，應為___]
  推測 2: [1=正確 / 2=錯誤，應為___]
  ```

**檢查點**：
- [ ] 需求識別覆蓋所有輸入內容
- [ ] **人類使用者已確認需求映射準確性**
- [ ] 需求間關係已明確定義
- [ ] **推測內容已獲得人類驗證或修正**
- [ ] 所有低確定性需求已轉換為明確需求

**品質標準**：
- 需求提取準確且完整
- **映射關係經人類確認無誤**
- 確定性標記客觀合理
- **推測內容≤10%，且全部獲得確認**

## 步驟 3：資訊缺失識別與補充
**描述**：識別關鍵資訊缺失，主動詢問人類補充

**執行者**：SA Agent (主導)

**具體作業**：
1. **關鍵資訊缺失檢查**（5W1H 方法）
   - **Who (使用者角色)**：誰使用這些功能？哪些使用者角色？
   - **What (功能範圍)**：具體要實現什麼功能？邊界在哪？
   - **When (時機觸發)**：什麼時候觸發？有時間限制嗎？
   - **Where (資料來源)**：資訊從哪裡來？存到哪裡？
   - **Why (業務規則)**：為什麼這樣設計？有什麼約束？
   - **How (流程邏輯)**：完整的操作步驟是什麼？異常處理如何？

2. **假設內容識別**
   - 列出所有基於推測的內容
   - 評估假設對需求理解的影響程度
   - 標記高風險假設（影響重大的推測）
   - **計算假設比例：目標<10%**

3. **缺失資訊優先級排序**
   - **P0 (Critical)**：必須了解的核心資訊（影響系統設計）
   - **P1 (High)**：重要但可暫時假設的資訊（影響功能細節）
   - **P2 (Medium)**：有助於完善理解的補充資訊（影響 UX）

**🔴【人機協作確認點 3】關鍵資訊補充**：
- **暫停流程**，詢問缺失的關鍵資訊
- **呈現內容**：
  ```
  ## 資訊缺失清單

  ### P0 - Critical（必須補充）
  1. 使用者角色資訊：
     - 不清楚：[具體問題]
     - 當前假設：[假設內容]
     - 影響：[對系統設計的影響]

  2. 業務流程細節：
     - 不清楚：[具體問題]
     - 可能的理解：
       選項 A：[描述] - 技術影響：[說明]
       選項 B：[描述] - 技術影響：[說明]

  ### P1 - High（建議補充）
  3. 資料來源：
     - 不清楚：[具體問題]

  ### P2 - Medium（可選補充）
  4. 異常處理方式：
     - 不清楚：[具體問題]

  ## 當前假設內容
  ⚠️ 以下為假設（共 X 項，佔比 Y%）：
  1. [假設 1] - 風險等級：高/中/低
  2. [假設 2] - 風險等級：高/中/低
  ```

- **人類需要提供（使用編號選項）**：
  ```
  ## P0 - Critical 確認（必填）

  1. 關於使用者角色：
     選項 1：[選項描述]
     選項 2：[選項描述]
     選項 3：其他，請說明：___
     您的選擇：___

  2. 關於業務流程：
     選項 1：採用選項 A
     選項 2：採用選項 B
     選項 3：其他，請說明：___
     您的選擇：___

  ## P1 - High 確認（建議填）

  3. 關於資料來源：
     [開放式回答或提供選項]

  ## P2 - Medium 確認（可選）

  4. 關於異常處理：
     [開放式回答]

  ## 假設內容確認
  假設 1: [1=確認正確 / 2=修正為___]
  假設 2: [1=確認正確 / 2=修正為___]
  ```

**檢查點**：
- [ ] 所有關鍵缺失資訊都已識別
- [ ] **人類使用者已提供必要的補充資訊（P0 全部，P1 大部分）**
- [ ] 高風險假設已通過人類確認或修正
- [ ] 補充資訊已正確整合到需求理解中
- [ ] **假設內容比例≤10%**

**品質標準**：
- 資訊缺失識別全面且準確
- **人類提供的資訊完整記錄**
- 假設內容最小化（目標≤10%）
- **所有 P0 資訊必須獲得明確答案**

## 步驟 4：需求整理與初步文檔生成
**描述**：基於確認的資訊整理需求，生成初步需求文檔

**執行者**：SA Agent (主導)、PM/PO Agent (業務價值)

**具體作業**：
1. **需求分類整理**
   - **功能需求 (Functional Requirements)**：具體的功能點和操作
   - **非功能需求 (Non-Functional Requirements)**：性能、安全、可用性等
   - **業務規則 (Business Rules)**：約束條件和處理邏輯
   - **使用者體驗需求 (UX Requirements)**：界面和交互要求
   - **整合需求 (Integration Requirements)**：第三方 API、外部系統

2. **需求優先級初步排序**（與 PM/PO Agent 協作）
   - **P0 (Must-Have)**：核心功能，無此功能系統無法上線
   - **P1 (Should-Have)**：重要功能，顯著影響使用者體驗
   - **P2 (Nice-to-Have)**：優化功能，提升競爭力
   - 考慮技術實現復雜度
   - 考慮使用者影響程度

3. **初步文檔結構生成**
   - 使用 AISDLC v0.02 PRD 模板結構
   - 填入已確認的需求內容
   - 標記仍需進一步確認的內容
   - 建立需求追蹤矩陣（Traceability Matrix）

**🔴【人機協作確認點 4】需求整理與優先級確認**：
- **暫停流程**，呈現整理後的需求
- **呈現內容**：
  ```
  ## 需求分類結果

  ### 1. 功能需求 (Functional Requirements)
  - FR-001: [需求描述] - 優先級：P0
  - FR-002: [需求描述] - 優先級：P1
  ...

  ### 2. 非功能需求 (Non-Functional Requirements)
  - NFR-001: [需求描述] - 優先級：P0
  ...

  ### 3. 業務規則 (Business Rules)
  - BR-001: [規則描述]
  ...

  ### 4. 使用者體驗需求 (UX Requirements)
  - UX-001: [需求描述]
  ...

  ## 優先級排序理由
  - P0 需求：[說明為何這些是核心功能]
  - P1 需求：[說明業務價值和使用者影響]
  - P2 需求：[說明優化方向]

  ## 初步文檔框架
  - 章節結構：[列出 PRD 章節]
  ```

# 品質控制與監控
# =============================================================================

## 品質檢查點
- **步驟 1 完成後**：檢查輸入解析的準確性和人類確認的完整性
- **步驟 2 完成後**：驗證需求識別覆蓋率和映射關係正確性
- **步驟 3 完成後**：驗證關鍵資訊缺失是否已得到有效補充
- **步驟 4 完成後**：確認需求整理完整性和優先級合理性
- **最終交付前**：確保所有需求都有明確的輸入源追蹤和人類確認

## 風險控制
### 風險 1：人類不確定或無法回答
- **緩解措施**：提供更詳細的背景資訊和分析，必要時分步驟確認
- **升級機制**：若持續無法決定，提供多個可行方案供後續階段驗證

### 風險 2：資訊嚴重缺失
- **緩解措施**：主動暫停流程，要求提供必要資訊後再繼續
- **備選方案**：標記為"待補充"，在後續 validation workflow 中處理

### 風險 3：輸入內容衝突
- **緩解措施**：明確標識衝突點，要求人類澄清和決策
- **記錄機制**：詳細記錄衝突內容和解決方案

### 風險 4：理解分歧
- **緩解措施**：詳細記錄不同理解可能性，由人類選擇正確解讀
- **驗證機制**：在後續確認點重新驗證理解一致性

### 風險 5：假設內容過多（>10%）
- **緩解措施**：強制觸發額外確認點，直到假設比例降至可接受範圍
- **警告機制**：當假設比例>5% 時發出警告

## 成功指標
- **人類參與度**：100% 的關鍵確認點都有人類參與
- **理解準確率**：95% 的需求理解在後續階段無需重大修正
- **資訊完整度**：90% 的關鍵資訊（P0+P1）通過人機協作得到補充
- **追蹤完整性**：100% 的需求都能追蹤到輸入源和確認過程
- **假設比例**：≤10%，且全部獲得人類確認
- **編號選項使用率**：100% 的人類互動使用編號選項協議

# =============================================================================
# 人機協作強化協議 (Anti-Hallucination Measures)
# =============================================================================

## 核心原則
- **零臆測原則**：任何不確定的內容都必須詢問，禁止自主推測
- **編號選項協議**：每個詢問都提供具體編號選項和影響分析
- **過程透明**：所有分析過程和確認結果都詳細記錄
- **迭代優化**：基於人類反饋持續改進理解和分析品質

## 主動詢問觸發條件
- **資訊不完整**：缺少關鍵業務資訊
- **邏輯不清晰**：存在多種理解可能性
- **內容衝突**：輸入間存在矛盾
- **假設過多**：需要推測的內容超過 5%（警告）或 10%（強制確認）
- **影響重大**：理解錯誤會顯著影響後續開發

## 30 分鐘硬性超時機制
- 每個確認點等待人類回應最多 30 分鐘
- 超時後自動暫停 workflow，記錄當前狀態
- 提供恢復指令：`繼續執行 requirements-extraction，從確認點 X 開始`

## 多 Agent 交叉驗證
對於關鍵決策，啟用多 Agent 交叉驗證：
- SA Agent 提出理解
- BA Agent 驗證業務邏輯
- PM/PO Agent 驗證業務價值
- 若存在分歧，強制人類確認

## 文檔一致性閘門
在交付前，自動檢查：
- 需求 vs. 輸入源的一致性
- 需求間的邏輯一致性
- 假設內容比例（必須≤10%）
- 所有 P0 資訊的確認狀態
