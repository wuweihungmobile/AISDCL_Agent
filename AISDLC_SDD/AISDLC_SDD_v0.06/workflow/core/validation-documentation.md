# =============================================================================
# Workflow 基本資訊
# =============================================================================

## Workflow 名稱
**需求驗證與文檔化工作流程 (Requirements Validation and Documentation)**

## 描述
此工作流程接收來自統一需求提取的初步需求，通過**多層次驗證機制**確保需求完整性、準確性和可行性，最終生成符合 AISDLC v0.02 標準的正式 PRD 和 FRD 文檔。

強調：
- **零臆測驗證**：所有驗證結論必須基於明確證據
- **多 Agent 交叉驗證**：從業務、技術、測試、整合等多角度驗證
- **場景特定檢查**：根據不同開發場景應用特定驗證規則
- **100% 人類確認**：所有關鍵決策都經過人類確認

## 適用場景

### 通用場景
- **Greenfield Project**：新專案的需求標準化和文檔生成
- **Brownfield Project**：現有系統的需求重新梳理和規範化
- **Refactoring**：重構前的需求驗證和基準建立

### 專業場景
- **Integration**：第三方整合需求的特別驗證（API、認證、資料格式）
- **Performance**：性能需求的量化驗證和基準定義
- **Testing**：測試策略需求的驗證和測試覆蓋率定義
- **DevOps**：CI/CD 和基礎設施需求的可行性驗證
- **Documentation**：文檔需求的完整性和可維護性驗證

## 觸發條件
- `requirements-extraction` workflow 完成並交付需求提取報告
- 初步需求文檔需要正式驗證和標準化
- 需要生成可用於後續開發的正式文檔時
- 需求變更後需要重新驗證時

## 步驟 1：需求完整性驗證
**描述**：系統性檢查需求的完整性，確保所有關鍵方面都已涵蓋

**執行者**：SA Agent (主導)、BA Agent (協助)、QA Lead (測試性)

**具體作業**：

### 1.1 需求覆蓋度檢查
- **功能需求完整性**：
  - 核心功能：必備的主要功能
  - 輔助功能：支援性功能
  - 邊界情況：異常場景和極端情況

- **非功能需求檢查**：
  - 性能要求：響應時間、吞吐量、並發用戶數
  - 安全要求：認證、授權、加密、資料保護
  - 可用性要求：正常運行時間、容錯能力
  - 相容性要求：瀏覽器、設備、平台
  - 可擴展性：未來增長的支撐能力

- **使用者角色覆蓋**：
  - 所有使用者類型的需求都已考慮
  - 角色權限和職責明確定義
  - 角色間的互動關係清晰

- **業務流程完整性**：
  - 端到端流程無斷點
  - 分支和異常路徑完整
  - 流程間的銜接順暢

### 1.2 資訊一致性驗證
- **需求間無矛盾衝突**：
  - 功能需求間的邏輯一致
  - 非功能需求間無衝突
  - 優先級設定合理

- **與輸入源資訊一致**：
  - 需求描述與原始輸入匹配
  - 無誤解或曲解原意
  - 推測內容已獲確認

- **術語定義統一**：
  - 建立術語表（Glossary）
  - 業務術語使用一致
  - 技術術語準確無歧義

### 1.3 關鍵資訊查缺
- **驗收標準定義**（與 QA Lead 協作）：
  - 每個功能需求都有明確的 AC
  - AC 可測試且可量化
  - AC 覆蓋正常和異常場景

- **邊界條件說明**：
  - 輸入限制和範圍
  - 資料量限制
  - 系統負載限制

- **異常處理機制**：
  - 錯誤處理策略
  - 使用者提示和反饋
  - 日誌和監控需求

- **依賴關係聲明**：
  - 內部依賴（需求間）
  - 外部依賴（第三方服務、系統）
  - 技術依賴（框架、工具）

### 1.4 場景特定檢查

#### Integration 場景額外檢查
（由 Integration Specialist 執行）
- [ ] API 端點和方法明確定義
- [ ] 認證機制和憑證管理清晰
- [ ] 資料格式和轉換需求完整
- [ ] 錯誤處理和重試機制定義
- [ ] Rate limiting 和配額考量

#### Performance 場景額外檢查
（由 Performance Engineer 執行）
- [ ] 性能指標量化且可測量
- [ ] 基準線和目標值明確
- [ ] 負載場景和測試數據定義
- [ ] 可擴展性需求清晰
- [ ] 性能監控和告警需求

#### DevOps 場景額外檢查
（由 DevOps Engineer 執行）
- [ ] 部署環境和配置需求
- [ ] CI/CD 流程需求
- [ ] 監控和可觀測性需求
- [ ] 災難恢復和備份需求
- [ ] 基礎設施即代碼需求

## 步驟 2：業務邏輯與流程驗證
**描述**：深度驗證業務邏輯的正確性和業務流程的完整性

**執行者**：SA Agent (主導)、BA Agent (業務驗證)、PM/PO Agent (價值確認)

**具體作業**：

### 2.1 業務流程驗證
- **端到端流程邏輯檢查**：
  - 繪製完整的業務流程圖
  - 驗證流程節點的邏輯順序
  - 確認分支和循環條件正確
  - 檢查流程終止條件

- **角色權限和職責驗證**：
  - 每個流程步驟都有明確的執行者
  - 權限設定符合業務規則
  - 角色職責無重疊或遺漏

- **業務規則執行檢查**：
  - 業務規則完整且無歧義
  - 規則之間無衝突
  - 規則執行時機明確
  - 規則例外處理清晰

- **異常場景處理驗證**：
  - 識別所有可能的異常場景
  - 每個異常都有處理策略
  - 異常恢復路徑明確
  - 使用者提示和反饋適當

### 2.2 業務價值確認
（與 PM/PO Agent 協作）
- **與業務目標的一致性**：
  - 需求支撐業務目標達成
  - 優先級反映業務重要性
  - 無偏離業務戰略的需求

- **ROI 和商業可行性評估**：
  - 實現成本與價值的匹配度
  - 投資回報預期合理
  - 市場時機和競爭力考量

- **使用者價值評估**：
  - 解決真實的使用者痛點
  - 提升使用者體驗顯著
  - 使用者採用度預期良好

### 2.3 使用者體驗驗證
- **使用者操作流程合理性**：
  - 操作步驟簡潔高效
  - 學習曲線合理
  - 符合使用者習慣

- **界面交互邏輯檢查**：
  - 互動反饋及時明確
  - 錯誤提示友好可理解
  - 導航結構清晰

- **使用者任務完成的便利性**：
  - 關鍵任務流程順暢
  - 減少不必要的步驟
  - 提供便利的快捷方式

## 步驟 4：優先級排序與發佈計畫
**描述**：確定需求優先級，制定合理的實現和發佈計畫

**執行者**：SA Agent (主導)、PM/PO Agent (業務決策)、BA Agent (協調)

**具體作業**：

### 4.1 優先級評估標準
建立多維度評估框架：

- **業務價值影響度**（40% 權重）：
  - 直接收益（營收、成本節省）
  - 戰略重要性
  - 市場競爭力提升

- **使用者需求緊迫性**（30% 權重）：
  - 使用者痛點嚴重程度
  - 使用者需求頻率
  - 使用者滿意度影響

- **技術實現複雜度**（20% 權重）：
  - 開發時間和成本
  - 技術風險
  - 依賴關係影響

- **依賴關係影響**（10% 權重）：
  - 是否為其他需求的前置條件
  - 阻塞其他開發的可能性

### 4.2 多維度優先級分析

#### MoSCoW 分析
- **Must Have (P0)**：無此功能系統無法上線
  - 核心業務流程必備功能
  - 法規遵循必要功能
  - 安全和穩定性基礎功能

- **Should Have (P1)**：重要功能，顯著影響使用者體驗
  - 主要使用者場景的重要功能
  - 顯著提升效率的功能
  - 競爭力關鍵功能

- **Could Have (P2)**：優化功能，提升競爭力
  - 增強使用者體驗的功能
  - 未來擴展預留功能
  - Nice-to-have 功能

- **Won't Have (此版本不做)**：
  - 價值低或時機未到
  - 技術風險過高
  - 資源不足無法實現

#### 價值/成本矩陣分析
```
高價值/低成本 → P0/P1 優先
高價值/高成本 → P1/P2 評估 ROI
低價值/低成本 → P2 或後續版本
低價值/高成本 → Won't Have
```

#### 風險/收益評估
- 高收益/低風險：優先實現
- 高收益/高風險：需要風險緩解措施
- 低收益/低風險：排期靈活
- 低收益/高風險：通常不做

### 4.3 發佈計畫建議

#### MVP (最小可行產品) 範圍界定
- **核心功能集**：
  - 滿足最基本業務需求
  - 使用者可完成關鍵任務
  - 可收集真實使用者反饋

- **MVP 驗證目標**：
  - 業務假設驗證
  - 使用者接受度測試
  - 技術架構驗證

#### 分階段發佈策略
- **Phase 1 (MVP)**：
  - 範圍：[列出 P0 需求]
  - 目標：[業務目標]
  - 時程：[預估時間]

- **Phase 2 (Enhanced)**：
  - 範圍：[列出 P1 需求]
  - 目標：[優化和擴展]
  - 時程：[預估時間]

- **Phase 3 (Optimized)**：
  - 範圍：[列出 P2 需求]
  - 目標：[完善和優化]
  - 時程：[預估時間]

#### 里程碑和檢查點設定
- **Development Milestones**：
  - M1: 核心功能開發完成
  - M2: 集成測試完成
  - M3: UAT 完成

- **Quality Gates**：
  - 每個里程碑的品質標準
  - 進入下一階段的條件

### 4.4 依賴關係分析
- **需求依賴圖**：
  - 識別前置需求
  - 規劃實現順序
  - 避免阻塞

  - 第三方服務就緒時間
  - 技術組件開發順序

## 品質檢查點

- **文檔生成完成後**：檢查格式規範性和內容完整性

## 風險控制

### 風險 1：驗證不充分
- **緩解措施**：建立檢查清單，確保所有方面都得到驗證
- **檢測機制**：驗證覆蓋率指標監控

### 風險 2：文檔品質問題
- **緩解措施**：使用標準模板，進行格式和內容雙重檢查
- **檢測機制**：Technical Writer 審查（如可用）

### 風險 3：人機協作不足
- **緩解措施**：確保關鍵點都有人類參與，記錄完整
- **檢測機制**：確認點完成率監控（目標 100%）

### 風險 4：Agent 協作衝突
- **緩解措施**：建立明確的責任分工和決策機制
- **升級路徑**：由人類使用者最終裁決

### 風險 5：場景特定需求遺漏
- **緩解措施**：場景識別和對應 Agent 啟動機制
- **檢測機制**：場景特定檢查清單

### 風險 6：追蹤鏈斷裂
- **緩解措施**：自動化追蹤矩陣生成和完整性檢查
- **檢測機制**：追蹤完整性百分比監控（目標 100%）

# 30 分鐘硬性超時機制
# =============================================================================

- 每個確認點等待人類回應最多 30 分鐘
- 超時後自動暫停 workflow，記錄當前狀態
- 提供恢復指令：`繼續執行 validation-documentation，從確認點 X 開始`
- 超時記錄：包含時間戳、確認點 ID、當前進度
